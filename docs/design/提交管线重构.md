# 设计：提交管线重构——Adjudicator + Journal 分离

> 目标：使提交管线具备多节点扩展的接缝。
> 参考：Aurora DSQL（OCC + 批序裁决）、FoundationDB（Resolver）、
> [SOTA 调研](../research/SOTA分布式事务技术调研-2026.md)。

## 现状问题

当前 `commit_tx` 把 OCC 验证、memtx 安装、WAL 帧编码、水位推进绑在一个
函数里。这个设计单节点正确且高效，但**无法多节点化**——验证和安装必须
在同一进程内。多节点需要把"验证+授序"（裁决）与"安装+持久"（日志）
分离为两个可独立部署的阶段。

## 重构方案

```rust
/// 裁决结果：多数派持久后才能安装
pub struct Adjudication {
    pub ts: u64,
}

/// Adjudicator trait——冲突裁决 + 授序（可分布化）
pub trait Adjudicator: Send + Sync {
    /// 对写集做 OCC 验证并授 ts。
    /// 返回 Err(40001) = 冲突，Err(e) = 其他错误。
    fn adjudicate(&self, txn: &TxnView, branch: &str) -> Result<Adjudication>;
}

/// Journal trait——提交日志（可替换为 Raft 多副本 / 单节点 WAL）
pub trait Journal: Send + Sync {
    /// 持久化一个已裁决的批次（多数派持久 = ACK）
    fn append(&self, batch: &JournalBatch) -> Result<()>;
    /// 重放 [from_ts, ∞)
    fn replay(&self, from_ts: u64, sink: &mut dyn FnMut(&JournalBatch)) -> Result<()>;
    /// 当前持久化水位
    fn durable_watermark(&self) -> u64;
}
```

### 提交管线（重构后）

```
commit_tx(txn):
  1. adjudication = adjudicator.adjudicate(txn)     // OCC 验证 + 授 ts
  2. journal.append(JournalBatch{ts, records})      // 持久化（多数派/WAL 组提交）
  3. memtx.install(txn, adjudication.ts)            // 内存安装
  4. pending 登记                                     // checkpoint 原料
  5. watermark.store(adjudication.ts)               // 可见性推进
```

### 多节点扩展路径

| 阶段 | Adjudicator | Journal |
|------|-------------|---------|
| M1（当前）| 进程内（memtx shard 锁）| WalWriter（单节点）|
| P2'（多节点）| 独立服务（RPC 上送读写集）| 3 副本 Quorum Append |
| P3（远期）| 分布式 Resolver（按 key 分片）| openraft 多副本 |

关键：**接口不变，实现替换**。上层 SQL/KV 代码不感知 Adjudicator/Journal
是进程内还是跨节点。

## JournalBatch 格式

```text
JournalBatch:
  ts u64 (复合时间戳)
  branch_len u16 + branch bytes
  records_len u32
  × records:
      table_id u32
      n_ops u32
      × ops: key_len u32 + key bytes | val_len u32 + val bytes (或 0xFFFFFFFF)
```

与 WAL TXN 帧的 payload 格式一致——**WAL 段 = Journal 批次的物理序列化**。
这消除了"WAL 段 + Journal"的双写冗余：Journal 的物理载体就是 WAL 段，
只是被赋予了"多副本提交日志"的角色。
