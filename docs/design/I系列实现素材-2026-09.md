## 0. 前提修正（执行前必读）

两个常被误引的前提，规划任务时以本节为准：

1. **refs 不是 prolly map**。分支→commit 映射在 `Manifest.refs: BTreeMap<String, BranchHead>`
   （`objstore/manifest.rs:93`，JSON 序列化 + CAS 提交）。prolly map 只有一棵：
   `Commit.root` = 表目录 map（表名 → TableEntry，`versioned/mod.rs:153-230`）。
   引用 dolt 的 address_map 类比时注意这个差异。
2. **`cambium.last_merge_conflicts` 视图不存在**（仅 spec/03 §6 提及）。现状：行冲突
   `Vec<MergeConflict>` 在 `versioned/merge.rs:259-269` 被压缩成字符串摘要（冲突数+前 3 个 key），
   完整 base/left/right 值被丢弃；`engine.rs:1049-1055` 直接 40001 abort。
   I-2 的第一步就是把这个信息接住。

**测试组织约定**（新代码必须遵循，详例见各 tests 文件头注）：
- 测试名 = 行为语句或缺陷描述；文件头注写明不变式编号/账本缺陷号/评审轮次/诚实边界；
- mock store 模式 = `inner: MemoryObjStore + Atomic 旋钮 + 路径前缀过滤`，经 `StoreConfig::Obj` 注入；
- 差分/夹具必须断言被测路径真的参与（账本 #25 元教训；ap_txn.rs:29-42 的门断言是标准配方）；
- 协议级任务附变异自检；slt 只收确定性语义（每文件独立内存库、禁自动 checkpoint）。

### 2.2 攻击场景构造（审计用例设计）

前提：manifest 版本推进源 = 每次 checkpoint / refs 变更 / 墓碑压缩发布（update_manifest 闭包 engine.rs:1505-1524 等）。
GC 删除条件 = 版本号 < latest−16 **且** 已过 `gc_retention_ms`（默认 24h，engine.rs:70-72）。

```
写者 W：load_latest 读到 ver=N（LIST，:1211）
  → BarrierStore 挂起 W 于"构造 new manifest 之后、put_if_absent 之前"
其他写者：推进 ≥17 个版本（N+1..N+17，含 tombstone 压缩触发 gc_sweep）
时钟注入：跨过 gc_retention_ms → gc_sweep 删除 ≤ N+1 的版本
唤醒 W：put_if_absent(ver=N+1) —— N+1 已被删 → 不存在 → 假成功
```

### 2.3 审计清单（结论文档必须逐项回答）

1. 复活的 N+1 对象在 LIST 权威读下永远是"旧版本"（load_latest 取 max）——**主读路径是否真的免疫**？
2. 复活版本是否可被其他路径采纳：`update_manifest` 的"自采纳缓存"（写后不 LIST）、backup、只读副本、恢复路径？
3. 两个停顿写者同时复活相邻版本号 → 影子谱系（各自认为自己是 N+1/N+2 链）的可能性？
4. putid 反查（Uncertain 消解）在复活场景的行为？
5. 与 slatedb RFC 0026 的差异：dendro 的 LIST 权威读是否已结构性消除主危害，剩余危害面是什么？

### 2.4 修复方案草案（坐实时）

持久边界（低水位）对象 `manifest/boundary`（或随版本化的 Tombstone 风格记录）：
GC 删旧 manifest 前**先推进边界**；`ManifestStore::commit` 成功后 `check(ver) ≥ boundary`，
落后按冲突处理回到乐观循环（复用 :1210-1238 循环，重试即重读最新）。
回归 `stalled_writer_cannot_revive_deleted_manifest_version`（multi_node.rs，夹具 `opts(dir, ttl)` :9）+ 变异自检。
产出同时登记 VERIFICATION.md I-D3（F-6 ③预建落点）。

## 4. I-3 删除的时间语义（分解 a–d，ADR 先行）

### 4.1 现状事实（锚点）

- 内存：`VerCell{ts, val: Option<...>}`（memtx.rs:19-23）——**删除时刻在内存已存在**（val=None 即墓碑，ts 即删除时刻）；

## 5. I-4 链式累积哈希审计链

### 5.1 挂点决策（重要：避开帧格式竞争）

推荐挂 **commit_tx Pass2 + manifest**，不挂 WAL 帧层：
- 计算：`alh_n = H(n, alh_{n-1}, tx_digest)`，n = 事务 ts（engine.rs:1847-1951，Pass2 安装 :1926-1948）；
  H 复用 `Hash::of`（format/hash.rs:13-20，SHA-512 截 160bit）；
- 携带：`BranchHead` 加 `alh_head`（manifest.rs:29-52，serde default 兼容先例 :45/:51）；
  回写点 = `checkpoint_locked_inner` 的 update_manifest 闭包（engine.rs:1505-1524）+ `write_branch_commit`（:1131-1198）；
- 校验：恢复重放时顺带验证链连续（recovery.rs:37-128，Txn 帧解码 :81-104）+ SQL 校验命令
  （`AUDIT VERIFY BRANCH` 类语句，REOPEN 先例 sql/mod.rs:511-524）；
- 截断点记入 manifest：WAL 前缀回收处（engine.rs:1468-1501）声明"截断 = 放弃该区间可证明性"。

### 5.2 v2（AHtree Merkle 化）预留

digest 流（每 commit 一个 32B digest）本身可按 chunk 上传对象存储——v1 顺手把 digest 追加进
checkpoint 的 CHECKPOINT 帧或独立 `audit/{branch}/{seg}` 对象，v2 Merkle 化时直接消化。

### 5.3 验收

- 链头连续性：N 连续提交后 alh_head 与逐条重算一致；
- **篡改注入必红**：TamperStore（F-1）改写历史段/manifest 链头 → 校验命令报错（变异自检：禁用校验 → 该测试红）；
- 截断后证明边界：GC 前缀回收后校验从截断点重新起算，明确放弃区间。

## 6. I-5 chunk 打包 pack + conjoiner（分解 a–e）

### 6.1 上传/读取链（改造接缝）

```
Chunker::put 缓冲（chunker.rs:59-83，buffered :46）→ flush（:86-90）
→ NodeStore::put_nodes_batch（store.rs:59-68）/ put_node（:38-55）
→ CasStore::put_batch（cas.rs:71-131：三重去重 :76-83 + PAR=8 逐组 join :87-113）
→ obj.put_no_sync + sync_batch
读：NodeStore::get_node（store.rs:74-87，miss→cas.get→validate）；CasStore::get/has（cas.rs:50-67）
寻址：chunk_path = objects/{s[..1]}/{s[1..]}.chunk（cas.rs:45-48）
```

### 6.2 关键决策

- **新容器类型并存**（`packs/{hash}.pack` + 索引对象 `packs/{hash}.idx`：sorted addr → (pack, offset, len)，
  dolt table file 的 prefix 二分+suffix 风格），**不改写现有 `objects/` 布局**——存量 chunk 照旧寻址，

- 影响面清单（执行时逐项适配）：cas.rs get/has/put_batch/chunk_path 四点、NodeStore.get_node miss 解码、
  cached.rs（整对象缓存→range 缓存，get_range 全实现已支持 mod.rs:56）、recovery.rs:26 存在性检查、
  backup.rs、gc.rs 测试的路径断言（:78/:169-174 的 `list_prefix("col/")`/`obj.get(seg1_path)` 类）。

### 6.3 分解
