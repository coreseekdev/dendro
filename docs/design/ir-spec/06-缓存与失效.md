# 06 缓存与失效

> 原则：缓存对象必须是**纯函数的输入**——schema 语义零漂移。
> 两级缓存对应两种失效语义，不可混用。

## 1. 两级缓存

| 级 | 内容 | 键 | 失效语义 | 状态 |
|----|------|----|---------|------|
| **L1（v2a）** | 纯 AST（未绑定） | `(xxh3(sql), dialect)` | **无需失效**（AST 不含 schema 信息，执行期实时绑定） | 已上线 |
| **L2（v2b）** | 绑定产物：`ScalarProgram` + ColId→列偏移映射 + 表 TableId 解析 | `(xxh3(sql), dialect, catalog_version)` | catalog_version 推进即整体 miss | 本 spec |

- **为什么 L1 不失效**：I-E4 已固化（纯 AST 免疫 DDL 漂移）。
- **为什么 L2 必须失效**：绑定产物**含** schema（列偏移、TableId）——
  DDL 后旧绑定是错误计划。PG 的 schema cookie 是同构机制。
- L2 miss 后回退路径：L1 命中 → 重新绑定 → 填 L2。两级共存，
  L2 未命中的开销 = 一次 L1 查找 + 绑定（无 tokenize/parse）。

### 1.1 参数化与 prepared（评审 P0-3 修正——否则 v2b 对扩展协议倒退）

现状 prepared = AST 缓存 + **执行前把 $n 替换为字面量**再走普通执行
（mod.rs substitute_params；pgwire 扩展协议真实走此路）。若 L2 键含
替换后 SQL：同模板不同参数 → 按文本命中 = **串值错结果**；若编译在
替换前：指令集须有 Param 槽（已加，03 §1）。**定案**：
- L2 缓存"**含占位符的模板**"：绑定/编译在模板上做一次，ScalarProgram
  含 `Param(u16)` 步，槽位表随模板缓存；
- `exec_prepared` 改为"模板编译一次 + 执行期 bind 参数数组"（Ctx 携带）；
- 未替换占位符直接执行的 08P01 错误（expr.rs:13-15）语义保留：
  非法槽位号在 bind 期报同码错误。
- **过渡条款**：若 v2b 未完成 prepared 改造，明写"prepared 保留 AST
  直评（双求值器）"，且差分语料必须覆盖 prepared × 普通执行对拍
  （双路径漂移看护）——不允许静默双轨。

## 2. catalog_version 的定义（关键决策）

**版本来源：manifest version。**

- manifest version 是**单调递增**的（CAS 提交），且任何 DDL
  （CREATE/DROP/ALTER/TRUNCATE，含 branch 的 DDL 分支创建）必经
  manifest CAS——所以 manifest version 是"schema 可能已变"的
  充分上界信号。
- 粒度取舍：表级 version（更细）需要 catalog 反查 DDL 触及表——
  v1 用全局 manifest version（粗但绝对正确）；表级细化进 v3
  （收益：高频 DDL 环境下 L2 命中率）。
- 会话侧获取：执行期读 `db.state`（ArcSwap<DbSnapshot>）的当前
  manifest version——一次原子读，无锁。

## 3. 失效矩阵（完备性论证）

| 事件 | manifest version | L2 影响 | 正确性 |
|------|-----------------|---------|--------|
| CREATE TABLE | ↑ | 全部 miss | 新表不在旧绑定中 ✓ |
| DROP TABLE | ↑ | 全部 miss | 旧绑定不再解析 ✓ |
| ALTER ADD COLUMN（pk 保持，#18 修复后）| ↑ | 全部 miss | 列偏移更新 ✓ |
| INSERT/UPDATE/DELETE | **不推进**（数据非 schema）| 无影响 | 绑定只含 schema 不含数据 ✓ |
| checkpoint / 段物化 | **看情况**（checkpoint 提交新 manifest）| 可能 miss | **可容忍**：miss 只损失绑定时间，不损失正确性；但高频 checkpoint 会打爆 L2 命中率 → 见 §4 |
| CREATE BRANCH / 切分支 | ↑ 或无 | 会话分支变化另处理 | 见 §5 |
| SET statement_timeout 等会话态 | 无 | 无影响 | 会话态不进缓存键 |

**⚠️ 口径问题（评审 P1-1 确认并扩大）：manifest version 不可用作 L2 键**：
- 后台 checkpoint 默认 30s 周期（checkpoint_interval_s=30）必推进
  manifest version → L2 每 ≤30s 整体清零，形同虚设；
- `gc_sweep`（墓碑清理后 update_manifest）与 `MERGE`（两分支强制
  checkpoint）同样推进——失效矩阵补齐此两行；
- **现状缺陷（B3 前置小 PR 修复）**：update_manifest 存入 DbSnapshot
  的 m.version 是提交前克隆（旧值）——本进程 DDL 后快照 version 滞后
  一次写，"一次原子读"原语当前不成立。修法：commit 返回的 new_ver
  写入快照（或 DbSnapshot 增 version 字段）。
**对策（Q1 定案建议）**：独立 `schema_version`，**反向白名单**推进
——仅 ddl.rs catalog_commit 族 + CREATE/DROP VIEW + branch 创建可
bump；checkpoint（含 MERGE 内嵌）、DROP BRANCH 墓碑、gc_sweep 压缩
一律不 bump。多节点下 schema_version 可见性跟随 fencing 单写者
（lease 持有者 bump，读者从 manifest 快照读）。

## 4. 内存界（S-3）

- L2 上限 1024 条（AST 比 L1 的 4096 小一个量级：L2 条目更大——
  步列表 + 绑定映射）；满即整体清空（与 L1 同策略，摊销 O(1)）；
- 单条目尺寸上界：步列表步数 ≤ 1024（编译期硬断——防恶意巨型
  表达式撑爆缓存与解释循环；超限走逐次编译不缓存）；
- prepared 语句（sess.prepared）**不走 L2**：它有自己的生命周期
  （连接断开即释放），但其内含的 ScalarProgram 引用同一编译器产物。

## 5. 分支与缓存的交互

- 绑定解析的是 `sess.branch` 的表——不同分支同名表 schema 可不同；
  **L2 键不含分支名**会导致串计划。方案：键加 `branch` 分量，或
  （推荐）L2 条目记录绑定时的 `(branch, catalog_version)`，命中校验
  两者。前者简单，后者命中率略高——v1 用前者（分支数有 S-3 上限，
  键空间可控）。

## 6. 实现前必须回答

1. `schema_version` 的推导：manifest diff 扫描（读 manifest 内容）
   vs DDL 提交路径显式 bump（改 catalog_commit 签名）？后者侵入小、
   语义准——推荐后者，需列全 DDL 调用点（ddl.rs 全部 + branch 创建）。
2. 并发下 schema_version 的可见性：与 manifest version 同源
   （ArcSwap 快照内携带）即可，无需独立原子——确认 DbSnapshot 结构
   的扩展点。
3. L2 条目被逐出后 prepared 语句的引用怎么办？（建议：prepared 持
   Arc，缓存逐出只影响缓存自身——prepared 生命周期独立，无悬挂。）
