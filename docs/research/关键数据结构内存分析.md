# 关键数据结构内存分析（实测，2026-09-19）

> 数据面：`cargo run --release --example memstruct -- [N] [val_bytes]`
> （独立进程 RSS 增量法； jemalloc 默认臂）。精打细算的前提是知道
> 每个结构的真实价。

## 实测（N=200K，值 64B，单版本）

| 结构 | RSS 实测 | 口径对照 | 结论 |
|------|----------|----------|------|
| **memtx 条目（单版本）** | **1708B/条** | 裸载荷 64B → **26.7×**；`memtx.pending` meter 只计 87B（载荷）——**结构开销是计量盲区** | 最大优化标的 |
| SqlValue 物化行（4 列 2 文本 64B） | 256B/行 | `rows_bytes` 结构口径 240B → **1.1×** | 健康（分配器/对齐仅 10%） |
| CHECKPOINT 瞬时 | +177MB / 200K 条 | 完成后 pending 归零 | 物化瞬时成本（段+树+CAS 缓冲） |

## memtx 1708B/条的分解（单版本一条）

写路径全链路的驻留叠加：

1. **memtx 表**：`BTreeMap<Box<[u8]>, Arc<VersionVec>>`
   - BTreeMap 节点摊销 ~50B + key Box 分配（头部+对齐）
   - `Arc<VersionVec>`（Arc 头 16B + Vec 24B）
   - `Arc<VerCell>`（16B + ts 8B + Option<Arc> 8B）
   - `Arc<Vec<u8>>`（16B + Vec 24B + 行编码字节）
   - 单条 ≈ 5 次堆分配 + ~250B 结构固定开销
2. **branch.pending 克隆**：`HashMap<u32, BTreeMap<key, Mutation>>`
   再存一份 key + `Mutation::Put(Vec<u8>)` 值克隆（+~220B/条）
   ——与 memtx 是**两份独立拷贝**（Arc 未共享）
3. **WAL writer 缓冲 + INSERT 批的 SQL 文本/AST 驻留碎片**

## 优化候选（按 ROI 排序，均待 A/B 验证）

| 候选 | 做法 | 预期收益 |
|------|------|----------|
| P0 pending 与 memtx 共享 | `Mutation::Put(Arc<Vec<u8>>)`——pending 与 VerCell 共享同一值（消除整份克隆） | −220B/条（~13%） |
| P0 计量口径诚实化 | `memtx.pending` desc 改"载荷字节"；新增 `memtx.entries` census（条目数）——结构开销按本档案系数外推 | 感知正确性 |
| P1 VerCell 瘦身 | 单版本热路径 inline：值 ≤16B 存 VerCell 内（SSO），ts 用 u32 epoch（复合时间戳已有 epoch 高位——可复用） | −2 次分配/条 |
| P1 key 存储紧凑化 | `Box<[u8]>` → 段内 arena/内联 ≤24B（rowid 主键场景 key 恒定 8-16B） | −1 分配/条 |
| P2 值域压缩 | memtx 值 >1KB 时 LZ4（段侧 FSST 已有；memtx 是热路径——阈值门控） | 大值场景 |
| P2 BTreeMap 替代 | 分片 BTreeMap → swiss-table + 有序游标（读写比感知）——大改，先测 BTreeMap 节点占比 | 待测 |

## 与 SOTA 的对照

见《内存优化SOTA调研-2026.md》：Hyper 系 memory-optimized MVCC 的
版本链布局（version-aware placement）、MVCC GC（版本回收时机）是
memtx 多版本场景的直接参照；单版本 26× 的开销在 SOTA 文献口径下
属偏高（Hyper 口径 ~3-6× 载荷）——主因是双份克隆与 Arc 层叠，
恰好是 P0/P1 候选。
