# 内存优化 SOTA 调研（2026-09-19）

> 触发：持续优化 dendro 内存管理与感知；含压缩内存方向。实现前
> 记录——每个方向的落地都需过 A/B 基线（RSS 治理 vs 时延）。

## 1. MVCC 版本链内存（memtx 直接对标）

- **Hyper 系 memory-optimized MVCC**（TUM, VLDB p2797）：版本数据
  与索引分离的紧凑布局，磁盘系统移植其内存优化——口径上版本链
  结构开销 ~3-6× 载荷。dendro memtx 实测 26.7×（单版本，含双份
  克隆）——差距即优化空间（见《关键数据结构内存分析》P0/P1）。
- **Scalable Version-aware Data Placement**（2026-05）：按版本可见
  性分区放置（旧版本冷区）——memtx 多版本热/冷分层参照：已
  checkpoint 覆盖的版本可降级为紧凑形态（去 Arc、位压缩 ts）。
- **MVCC GC**（VLDB p128，HTAP 场景）：版本回收时机 = 活跃读快照
  下界——dendro 的 watermark 语义已具备，缺的是**回收执行**的
  内存收益度量（配合 memprof 观测）。
- **TiKV In-Memory Engine**： RocksDB 之上按 region 热副本驻留 +
  LRU 淘汰——dendro 列存段 + page cache 天然同构；启示：memtx
  也可做"热表驻留、冷表仅段"的分级（分支级开关）。

## 2. 压缩内存（列存侧已有基础）

- **Oracle Memory Speed HCC**（2026-02）：SIMD + 字典编码提升列存
  内存压缩比——dendro 段内 FSST/位打包同路线；可补：**字典全局
  共享**（跨段字典合并，段间重复 URL/Title 的字典去重）。
- **Adaptive Compression**（EDBT 2024）：按列统计自适应选码——
  段物化时按列 min/max/ndv 选 FSST/位打包/LZ4 的自动决策（当前
  按类型固定）。
- **memtx 热路径压缩**：阈值门控（>1KB 值 LZ4）——热路径解压成本
  需 A/B；冷版本（被 checkpoint 覆盖的 VerCell）压缩无此顾虑。

## 3. 结构/分配器层

- jemalloc 已默认开（A/B：RSS 治理 86%，时延 0.86×——已入档）。
- **arena/池化**：bumpalo 作用域 arena 用于查询批（P2 性能项）。
- **Cloudflare 一致性哈希优化**（同目录另档）：数据结构排布的
  数学化压缩思路（6B 而非 8B）——对 VerCell/ts/key 定宽字段
  的启示：ts 的 epoch 高位复用（u32 epoch + u32 seq 替代 u64
  双份）。

## 4. 感知层（已落地，持续项）

memprof 三层 + 三表面；本批发现的结构开销盲区（pending 只计
载荷）→ 计量口径诚实化 + entries census；后续每加一个结构优化，
配一个 meter/census 与 A/B 基线（纪律：无观测不优化）。
