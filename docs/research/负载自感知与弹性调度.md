# 设计：负载自感知与弹性调度（k8s 风格）

> 前置阅读：[多节点 TP 事务调研](多节点TP事务调研.md)（P0-P3 演进路线）。
> 本文回答：**TP 侧负载压力大时，Dendro 如何把"压力"变成外部调度器（K8s
> HPA/KEDA/Operator）可以消费的信号与事件，并定义与之配套的伸缩动作。**
> 2026-09 · 设计文档（含实施清单，未含实现承诺）。

---

## 1. 框架：弹性 = 信号 → 决策 → 执行 的闭环

```
┌─────────────── Dendro 节点（自感知）───────────────┐
│  引擎内部计数器/直方图（§2）                          │
│    commit 延迟、组提交队列、pending 字节、冲突率、      │
│    WAL 水位差、缓存命中、S3 字节/请求数 …              │
│                │                                    │
│        ┌───────┴────────┐                           │
│        ▼                ▼                           │
│  /metrics          /readyz  ← 反压入口（摘流量）       │
│  (Prometheus)      (readiness)                      │
└────────┼──────────────────┼─────────────────────────┘
         ▼                  ▼
┌──── 决策器（k8s 侧）────────────────────────────────┐
│  HPA        ：Deployment 读副本，按 QPS/p99/CPU      │
│  KEDA       ：按 Prometheus 查询驱动任意伸缩          │
│  DendroOperator（CRD）：分支放置再均衡 = 租约转移       │
└────────┼──────────────────┼─────────────────────────┘
         ▼                  ▼
   执行器：加/减读副本      分支迁移（lease transfer）
   （P0，无状态）          （P1，见调研报告）
```

三条纪律：

1. **信号必须来自引擎内部**——CPU/内存是通用信号但会滞后且误导
   （缓存热身期 CPU 低但延迟高）；Dendro 的真实压力在
   组提交队列、checkpoint 积压、冲突率上，这些只有引擎知道。
2. **暴露的指标要能直接驱动决策**——每个指标附带"该触发什么动作"（§3）。
3. **反压与伸缩互为闭环**——过载时先摘流量（readiness 失败 + 特定错误码），
   再等扩容生效；否则负载会在扩容完成前把节点打穿，产生"越缩越糟"的振荡。

## 2. 负载信号目录（自感知层）

### 2.1 引擎里**已经存在**的信号（零成本暴露）

| 信号 | 位置 | 说明 |
|------|------|------|
| `pending_bytes` | `Branch::pending_bytes` (AtomicU64) | 未物化写字节 → **checkpoint 积压**的先行指标 |
| `watermark` / `next_seq` | `Branch` 原子量 | 提交吞吐（差分）、写放大 |
| `durable_seq` vs `watermark` | `WalWriter::durable_watermark()` | **持久化滞后**（组提交队列压力）|
| `pending_frames` | WalShared | 当前组提交缓冲的帧数（队列深度）|
| `cur_seg` / `flushed_seg` | WalShared | WAL 段产出速率 |
| `S3Stats` | S3 适配器 | gets/ranges/puts/cond_puts/heads/deletes + 字节数（**网络成本**）|
| `hits` / `misses` | CachedObjStore | 读缓存命中率（跌落 = 冷读风暴）|
| Throttled 统计 | 延迟注入器 | 基准对照 |

### 2.2 需要补的仪表（实施清单）

| 仪表 | 类型 | 位置 | 为什么重要 |
|------|------|------|-----------|
| `commit_latency_ms` | 直方图（每分支）| `commit_tx` 的 ACK 点 | **TP 压力的黄金指标**（p99 驱动扩容）|
| `conflict_total` | 计数器（每分支）| `validate_and_install` 冲突分支 | 冲突率↑ ⇒ 该拆分支（热点 key）而非加节点 |
| `checkpoint_duration_ms` | 直方图 | `checkpoint_locked` | checkpoint 变慢 = 树变大/存储变慢 |
| `checkpoint_lag_s` | 仪表 | 上次 checkpoint 时间戳差分 | 滞后窗口上限告警 |
| `memtx_rows` / `memtx_bytes` | 仪表（估算）| 分片条目计数 | 内存压力 → 触发提前 checkpoint |
| `sessions_active` | 仪表 | Session 计数器（`session_seq` 已有）| 连接压力 |
| `follower_lag_s`（副本）| 仪表 | 副本的 `watermark` vs 主 `watermark` | 读副本新鲜度 SLA |
| `lease_valid` / `lease_epoch` | 仪表 | fence 状态（P1）| 写权丢失 → readiness 立即失败 |

标签纪律：**分支名可以作为 label**（基数 = 分支数，Agent 场景可控）；
**绝不**把表名/用户名/键放进 label（基数爆炸拖垮 Prometheus）。

## 3. 暴露通道

```
GET /metrics     → Prometheus 文本格式（进程内 registry，无重依赖）
GET /healthz     → 200（进程活着）
GET /readyz      → 200 | 503   ← readiness 失败 = k8s 自动摘 Service endpoint
```

`readyz` 的失败条件（自感知的反压出口）：

1. S3 写者失去分支租约（P1 的 fence 过期）且请求是写
2. 组提交队列深度 > 上限（准入控制：拒新写，先保已接受的事务）
3. 底层存储连续 N 次瞬态失败

配套 SQL 层反压：过载时写事务返回 `53300 too_many_connections` 语 义的
专用错误（如 `dendro_overloaded`），驱动客户端/代理侧重试——
**readiness 管 k8s 摘除，SQL 错误管应用退避**，两者必须同时有。

事件（K8s Event / webhook，v2）：`LeaseLost`、`CheckpointBacklogHigh`、
`BranchCreated/Moved`、`MergeConflict`——用于 Operator 的审计与告警，
伸缩决策本身只依赖指标 + readiness（保持决策器无状态、可替换）。

## 4. 三种工作负载 → 三种伸缩执行器

### 4.1 R 读副本 → 无状态 Deployment + HPA/KEDA

```
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: { kind: Deployment, name: dendro-reader }
  metrics:
  - pods:
      metric: { name: dendro_point_select_p99_ms }   # 引擎内部信号
      target:  { type: AverageValue, averageValue: "20" }
```

读副本无状态（数据在 OSS + 追 WAL 段），直接进 Deployment 生态；
KEDA 可用 Prometheus 查询做更复杂的伸缩公式。**注意**：扩读副本不增加
主分支写能力——必须在文档与指标名上明确（`dendro_reader_*`）。

### 4.2 W1 分支写者 → DendroOperator（CRD + 分支再均衡）

**关键认知：分支写者的扩容不是"多起 Pod"，而是"把最热的分支搬到空闲节点"
（租约转移，P1）**。因此伸缩执行器是一个自定义 Operator：

```yaml
apiVersion: dendro.io/v1
kind: DendroCluster
spec:
  nodes: 4                      # 写节点池
  placement:
    strategy: load-aware        # 按 per-branch commit p99 / pending_bytes 再均衡
  rebalance:
    trigger:
      imbalanceRatio: 2.0       # 最热分支负载 / 中位分支负载
    cooldownSeconds: 60         # 租约转移节流（防抖）
status:
  branches:
  - { name: main,    node: dendro-w0, epoch: 12, commitP99ms: 3.1 }
  - { name: agent-7f3a, node: dendro-w2, epoch: 4,  commitP99ms: 41.7 }  # 热点
  - { name: agent-9c02, node: dendro-w3, epoch: 2,  commitP99ms: 5.0 }
```

Operator 决策循环（与引擎自感知解耦，Operator 只读指标）：

```
每 tick:
  1. 收集每分支 { commit_p99, pending_bytes, txn_rate }（/metrics）
  2. 计算 imbalance = max分支负载 / median
  3. 超阈值 → 选源节点(热)/目标节点(冷) → 转移协议：
       目标节点 put_if_absent(fence/{branch}, epoch+1)   ← 抢租约（S3 条件写）
       旧写者下个写请求 epoch 不符 → 停止（05 章段号单调保证安全）
       新写者从 checkpoint + WAL 尾恢复 → 接管
  4. 更新 manifest 放置表（CAS）→ 写 CRD status
```

冲突分支（`conflict_total` 高）**不迁节点**——迁了也没用，正确动作是
告警让 Agent 拆分支（这是 Dendro 语义独有的运维结论）。

### 4.3 scale-to-zero：Agent 沙箱的天然形态

分支数据全部在 OSS（权威）+ 少量 WAL 段，**空闲分支不需要任何常驻算力**：

```
活跃分支（有会话/水位推进）──▶ 占节点
空闲 > idle_ttl（如 10min）──▶ 停止 Pod（仅保留 manifest ref）
再次访问 ──▶ 任意空闲节点拉起 + 恢复（秒级，已在 e2e 验证）
```

参考 Neon 的 serverless compute（autoscaler-ng 开源：按 compute 指标
在 K8s VM 上伸缩，支持 scale-to-zero）——Dendro 的恢复更快（无页缓存，
直接 manifest+WAL），比 Neon 的暖机更有优势。

### 4.4 P2 日志服务 → 有状态、预设副本数

openraft 3/5 副本是**安全参数不是弹性参数**（副本数影响容错域与多数派，
不建议自动增减）；弹性体现在**分支在日志服务上的迁移与合并**。
运维上用 StatefulSet 固定规模 + 告警即可。

## 5. 引擎内的自适应（第二道防线）

自感知除了外暴露，也驱动**内部自适应**（不依赖外部调度器的即时防线）：

| 信号 | 自适应动作 | 现状 |
|------|-----------|------|
| 组提交队列深 | 动态延长/缩短 `flush_interval`（低载降低延迟、高载增批摊薄）| 结构已支持，加自动调参 |
| `pending_bytes` 超阈值 | 已触发 checkpoint（30s/16MB）| ✅ 已实现 |
| checkpoint 时长过长 | 动态提高阈值/延后（避免 checkpoint 风暴拖垮写入）| 需加 |
| 冲突率高 | 返回专用错误提示"拆分支"（而非无脑重试）| 需加 |
| S3 错误率↑ | 暂停后台 checkpoint/物化，保前台提交（**负载卸载次序**）| 需加（P1 有租约后更安全）|

负载卸载次序（过载时牺牲顺序）：后台物化 → checkpoint 频率 → AP 扫描并发
→ 新写入准入 → 已有事务永不半途丢弃。

## 7. 实施路线

| 里程碑 | 内容 | 工程量 |
|--------|------|--------|
| **M1 指标暴露** | 进程内 registry（无重依赖）+ `/metrics`；先接 §2.1 的现成原子量 + `commit_latency`/`conflict_total` 两个新仪表（插入点已定位）| 小 |
| **M2 readiness/反压** | `/readyz` 三条件 + `dendro_overloaded` 错误 + KEDA/HPA 文档样例 | 小 |
| **M3 Operator v0** | DendroCluster CRD + 分支再均衡循环（依赖 P1 租约）| 中（依赖调研报告 P1）|
| **M4 scale-to-zero** | 空闲分支停 Pod + 访问拉起 | 中 |
| **M5 自适应调参** | 组提交间隔/checkpoint 阈值自动调 + 负载卸载次序 | 中 |

依赖关系：M3/M4 依赖多节点调研的 **P1（租约 fencing）**——先有"分支可迁移"，
才有"分支可再均衡"。M1/M2 无依赖，可立即做。

## 8. 一句话结论

> 引擎负责**把压力变成诚实的数字**（组提交队列、checkpoint 积压、冲突率——
> 这些 CPU 指标看不见）和**诚实的态度**（过载时 readiness 失败 + 应用层反压）；
> **调度决策完全交给 k8s 生态**（HPA/KEDA 管无状态读副本，DendroOperator
> 管分支放置与再均衡，scale-to-zero 天然适配 Agent 沙箱）。引擎不自研调度器，
> 只做好的信号源与听话的执行器。
