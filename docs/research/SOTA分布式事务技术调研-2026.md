## 1. SOTA 采纳的三大共识（2024–2026）

### 1.1 提交时集中裁决，执行期零协调（OCC 回归）

Aurora DSQL 是 2024–2026 最重要的信号：**少数派路线**——几乎所有分布式 SQL
（Spanner/TiDB/Yugabyte/CockroachDB）用锁或时间戳不确定区间在执行期协调，
而 DSQL 用**乐观并发控制**：执行期零协调（读不阻塞、无分布式锁），
仅在提交时由 **Adjudicator**（裁决器）检查读写集冲突。

对 Dendro 的意义：我们 memtx 的 OCC 与 DSQL 同族。**P3 的"分布式 OCC"
不是冷门选择，而是当前 SOTA 主流路线之一**，且工业级可行性已被 DSQL 生产验证。

### 1.2 授序与裁决合流：Adjudicator + Journal（取代 2PC）

DSQL 写路径（Brooker 博客 + 论文）：

```
查询处理器（Firecracker 隔离，执行期不碰共享状态）
   │ 提交请求（读写集）
   ▼
Adjudicator 裁决器（多实例分片共担）
   ├─ 冲突裁决：读写集 vs 最近提交（OCC 验证的分布化）
   ├─ 授序：批次序 + 提议者哈希 → 全序键（Warp 启发：投票后仅 leader 写日志，
   │   免去传统 2PC 的协调阻塞——Stanford "Trading Conflict for Consistency" 系）
   ▼
Journal（内部复制日志，多 Region 2+1 持久）
   │ 提交批次顺序落 Journal = 事实源
   ▼
读节点/缓存层从 Journal 回放 → S3 为长期层
```

要点：
- **无 2PC**：单分片事务自然免 2PC；跨分片用"裁决 + Journal 顺序"替代
- **裁决器可水平扩展**（按 key 分片共担），裁决是纯内存操作
- Journal 是唯一强持久组件（快速盘多数派），S3 是长期层

### 1.3 对象存储原生事务的成熟（与 Dendro 同 niche）

- **Slatedb**（Rust，对象原生 LSM）：快照隔离、对象存储为唯一持久层——
  与 Dendro 的 memtx+树+OSS 组合同 niche，其 WAL 持久化/压缩/缓存策略可对照
- **Delta Lake / Iceberg**：JSON/CAS 事务日志 + 乐观并发——与 Dendro 的
  manifest CAS 同构（我们比表格式多了事务性行级写入）
- 结论：**"OSS + 条件写 CAS + 乐观提交"是被两个生态验证过的 SOTA 范式**，
  Dendro 已在此范式内

## 2. 各维度 SOTA 技术清单与 Dendro 现状对照

| 维度 | SOTA 技术（代表系统） | Dendro 现状 | 采纳建议 |
|------|----------------------|-------------|----------|
| 冲突裁决 | 提交时 OCC 裁决（DSQL Adjudicator）；范围缓存冲突检测（FDB Resolver）| 进程内 OCC 已实现 | **P2 核心**：裁决分布化（读写集上送）|
| 授序 | 批次序 + leader journal（DSQL）；TSO（OceanBase）；HLC+不确定性区间（CRDB）| manifest CAS 隐式授序（OSS RTT 限吞吐）| **P2**：Journal 服务承担授序 |
| 提交延迟 | 并行提交（CRDB）；commit-and-serve（DSQL：Journal 记录即提交，读节点接收即服务）| 组提交 1 RTT | P2：Journal 即提交点，节点间流水线 |
| 只读扩展 | 回放日志的只读节点（Aurora/Neon/DSQL）| ✅ 已有（追段）| 维持 |
| HTAP 单存储 | Universal Storage（SingleStore）；Hybrid Tables（Snowflake）；TiFlash 列副本（TiDB）| CBF 列存段 = 列副本（已有）| 维持；补 seekable 更新（v2）|
| 对象原生事务 | manifest/CAS + 乐观（Delta/Iceberg/Dendro 同范式）| ✅ | 维持 |
| 快照隔离引擎 | Slatedb（对象原生 LSM，SI）| ✅（memtx+树）| 对照其 compaction/缓存参数 |
| 弹性 | serverless scale-to-zero（Neon/DSQL）| 分支模型天然支持 | 与负载自感知设计（P1）衔接 |
| 多 Region 强一致 | Journal 多 Region 2+1 持久（DSQL）；TrueTime（Spanner）| 无 | 远期；依赖基础设施 |

## 3. 修订后的 P2/P3 路线（吸收 SOTA 后）

原 P2（通用日志服务）与 P3（分布式 OCC）合并为一个连贯的目标架构——
**即 DSQL 的"Adjudicator + Journal"形态，落到 Dendro 的对象存储原生底座上**：

```
修订后目标架构（P2' = P2+P3 合并）：

  节点1（SQL/KV wire）─┐ ①提交请求（读写集）
  节点2（SQL/KV wire）─┼─▶ Adjudicator 层（无状态，按 key 分片共担）
  节点3（SQL/KV wire）─┘     ├─ OCC 裁决：读写集 vs 最近提交（复用 memtx 验证逻辑）
                             └─ 授序：批内顺序 + 全序 ts（epoch<<32|seq 延续）
                                   │ ②多数派持久（openraft Journal，NVMe）
                                   ▼
                              Journal（提交日志 = 事实源）
                                   │ ③异步物化（ prolly 树增量 + CBF 段 + manifest）
                                   ▼
                              OSS（长期权威层）+ 各节点读缓存
```

### 3.1 与原 P2/P3 的差异及理由

| 原计划 | 修订 | 依据 |
|--------|------|------|
| P2 只做"日志多数派"，P3 再加裁决 | **裁决器与授序合并在 Journal 入口**（同一请求路径）| DSQL/DSQL 论文：裁决-授序-持久一次往返完成，分两次会引入额外 RTT |
| P3 用读写集上送 | 保持，但**读集用范围摘要**（前缀区间而非逐键）| FDB Resolver 的范围冲突检测实践；memtx 读路径需记录读范围（改造点）|
| P2 日志服务用通用 openraft 直接存 WAL 帧 | Journal 记录 = **提交批次**（含读写集+变更），WAL 段退化为 Journal 的物化形式 | DSQL Journal 语义；减少 OSS 段数量（网络成本目标）|
| 跨分支事务 2PC | **维持"跨分支=merge"**，不引入 2PC | 分支模型是 Dendro 的冲突消解协议；DSQL 证明单 key 空间内 OCC 足够 |

### 3.2 P2' 实施清单（下一阶段）

1. **Adjudicator 服务**（可内嵌单进程起步，v2 拆独立分片）：
   - 接口：`adjudicate(read_ranges, write_keys, base_ts) -> ts | conflict`
   - 复用 memtx OCC 验证语义（SPEC 04 §3 的分布化）
2. **Journal（openraft 3 副本）**：
   - 记录 = `{ts, branch, 读写集摘要, 变更批}`；多数派持久 = durable
   - 分支 WAL 段变为 Journal 的按分支投影（物化到 OSS，供无 Journal 的只读节点）
3. **memtx 职责调整**：install 改为"从 Journal 批次重放"；读写集上送替代本地验证
4. **OSS 物化器**：Journal → prolly 树增量 + CBF 段 + manifest（现有 checkpoint 逻辑复用）
5. **网络成本控制**（用户强调）：Journal 批内聚合多事务；OSS 物化批间去重
   （col_segments 增量段已实现）；节点读全部经 LRU 缓存（已实现）

### 3.3 保留不变的 Dendro 差异化（SOTA 之外的定位）

1. **分支即分片**（P1 租约）：Agent 沙箱的冲突局部化——SOTA 系统（DSQL 等）
   均为单键空间模型，分支化是我们的差异化
2. **内容寻址版本存储**：commit/树/列存段全量哈希寻址——合并与审计能力
   是 DSQL/FDB 不具备的
3. **列存投影派生**（CBF 段）——HTAP 一体化，对标 Unistore/TiFlash 但保持
   对象存储原生

## 5. 结论

1. **DSQL 验证了 Dendro 的大方向**（OCC + 提交时裁决 + 对象存储事实源），
   但 DSQL 的 Adjudicator/Journal 是 Dendro 目前缺失的部分——即修订后的 P2'。
2. **P2' 优先级应高于原 P3**：裁决与授序本就同路径，分开实施是浪费。
3. **P1（已实现）不与 SOTA 冲突**：fencing/epoch 是任何 Adjudicator 方案的
   前提（DSQL 同样有世代/租约概念）；分支分片模型则是 Dendro 超越
   单键空间 SOTA 系统的差异化所在。
4. **执行顺序**：P2' Journal（授序+持久）→ Adjudicator 裁决接入 →
   memtx 重放化改造 → 读副本经 Journal 服务。
