# 一致性哈希内存优化调研：Cloudflare PBR 用数学省下 100TB RAM（2026-09-19）

> 调研时间：2026-09-19。来源：Cloudflare 博客 "Saving 100 TB of RAM with
> math"（Kevin Guthrie / Mariia Iurchenko，2026-09-18，
> <https://blog.cloudflare.com/saving-100-tb-of-ram-with-math/>）。
> 触发：用户指定分析记录该文方法。结论先行：
>
> 1. **两刀省 100TB**：①把环上每个点从 8 字节压到 6 字节（省 25%）；
>    ②每服务器哈希点数削减 90%（误差几乎不涨）。两者相乘 ≈ 砍掉
>    ketama 相关内存的 92.5%，全网累计 100TB。
> 2. **核心方法是精确统计公式而非直觉**：作者推导出每服务器 k 个
>    哈希时负载变异系数的闭式解 `CV_k = √((N−1)/(Nk+1))`，渐近为
>    `1/√k`——误差每降一个数量级，哈希数要涨两个数量级。据此算出
>    NGINX/Pingora 默认的 160 点基线 × 权重 625 = 10 万点里，最后
>    9 万个点只买了 0.7 个百分点的误差。
> 3. **军备竞赛的终点是生日悖论**：32 位哈希空间下，点数越多碰撞越
>    多，碰撞会随机丢贡献、引入不可预测误差。模拟显示 2048 服务器的
>    数据中心在 1 万→10 万点/服务器区间，**实际误差反而上升**——
>    加资源到某点之后开始负收益。
> 4. **Rust 对齐陷阱有无争议解法**：`u32 + u16` 结构体因对齐规则仍占
>    8 字节；`struct Point([u8; 6])` + `from_ne_bytes` getter 与
>    `#[repr(packed)]` 编译结果相同但无 UB 争议。
> 5. **迁移模式值得抄**：新旧双环同时在内存 + 按请求哈希稳定选环 +
>    流量百分比 × 地理范围双维度分层放量，100% 后才删旧环。

## 1. 背景与问题

- 场景：Cloudflare 内部负载均衡服务 **PBR（Pingora Backend Router）**，
  用一致性哈希（`pingora-ketama` crate）把可缓存请求按 URL 路由到
  缓存服务器，目标是一个文件在每个数据中心只存一份。
- 一致性哈希环：哈希输出视为环上的点；请求落到环上某点，归该点
  顺时针方向遇到的第一个服务器。每个服务器承担的负载 ∝ 它拥有的
  环段长度。
- 问题：同事 Ivan 报了内存超标工单——ketama 相关结构在某些情况下
  占到 **6GB**。排查发现内存放大有两个独立来源：存储布局浪费
  （§4）与哈希点数过多（§5、§6）。

## 2. 环上负载失衡的精确统计（每服务器 1 个哈希）

设 N 个服务器、每服务器 1 个哈希点，单个服务器拥有的环段占比：

- 期望：`Exp = 1/N`
- 标准差：`SD = (1/N)·√((N−1)/(N+1))`
- 变异系数：`CV = SD/Exp = √((N−1)/(N+1))`

N=100 时 Exp=1%、SD≈0.99%、**CV≈99%**——纯随机布点下，有服务器
承担约 2 倍期望负载，有的几乎为零。这就是必须加虚拟节点的定量
理由。

## 3. 虚拟节点与 Ketama 权重

- **虚拟节点**：每服务器放 k 个哈希点，大数定律把 CV 压到
  `~1/√k`。NGINX 硬编码 **160 点/服务器**，Pingora 沿用同一默认值。
  N=100、k=160 时 CV 从 ~99% 降到 ~8%。
- **权重**：Ketama 规则——若 S₁ 应承担 S₂ 的 w 倍请求，则
  `H₁ = w × H₂`（H 为该服务器的哈希点数）。权重来源：缓存场景用
  磁盘容量，计算密集型用 CPU/GPU 数。
- **基线因子不可省**：固定基线（160）仍然需要——它为**最低权重**
  服务器设定误差上限。即 k = base × weight，例：160 × 625 = 100,000。

## 4. 存储压缩：Rust 对齐规则与 6 字节点（省 25%）

**内存爆炸的结构根源**：不同特性/合规规则限制哪些服务器可服务哪些
请求，因此每种**特性组合各建一个环**——"少量特性的 2^组合 = 几十个
环"，每个环都存海量哈希点。

**布局优化**（Zaidoon 的洞察）：

```rust
// 原始：8 字节（u32 hash + u32 index）
struct Point { hash: u32, index: u32 }

// 想当然的压缩：仍然是 8 字节！
// Rust 要求结构体大小是最大对齐字段（u32，4 字节）的整数倍
struct PointV2 { hash: u32, index: u16 }   // sizeof == 8

// 可行做法：u16 索引足够（PBR 永远不会协调超过 2^16 ≈ 6.5 万台服务器）
// 裸字节数组 + getter，与 #[repr(packed)] 编译结果相同（作者在
// Godbolt 验证），但没有 packed 的 UB 争议
struct Point([u8; 6]);

impl Point {
    fn hash(&self) -> u32 {
        u32::from_ne_bytes(self.0[0..4].try_into().unwrap())
    }
    fn index(&self) -> u16 {
        u16::from_ne_bytes(self.0[4..6].try_into().unwrap())
    }
}
```

仅此一项把一致性哈希内存砍掉 **25%**（8→6 字节）。

## 5. 精确误差公式与边际收益递减（哈希数 -90%）

作者推导出每服务器 k 个哈希时的**精确**（非渐近）统计量：

- `Exp_k = 1/N`（期望不变）
- `SD_k = √((k+1)/(N(kN+1)) − 1/N²)`
- `CV_k = √((N−1)/(Nk+1))`

验算（本文自行核算，与原文数字吻合）：

| N | k | CV_k |
|---|---|--------|
| 100 | 1 | √(99/101) ≈ 99% |
| 100 | 160 | √(99/16001) ≈ 7.9%（原文"约 8%"） |
| 100 | 10,000 | √(99/1000001) ≈ 1.0% |
| 100 | 100,000 | √(99/10000001) ≈ 0.315% |

关键结论：

1. 渐近行为 `CV_k ≈ 1/√k`——**误差降一个数量级，哈希数要涨两个
   数量级**，边际收益急剧递减。
2. 权重 625 的服务器 k=100,000，其中"最后 90,000 个哈希"只把误差
   从 ~1.0% 降到 ~0.315%，**共 0.7 个百分点**。
3. 决策：把每服务器哈希数削减 **90%**，不产生可感知的误差增长。

## 6. 32 位哈希碰撞：生日悖论终结军备竞赛

- 哈希是 32 位，点数增多时碰撞概率按生日悖论快速上升；碰撞会随机
  丢掉点（同 hash 二选一），引入**不可预测的**误差。
- 原文模拟：2048 服务器的数据中心，实际误差在 **10,000→100,000
  点/服务器**区间**不降反升**。
- 验算（本文自行估算，量级佐证）：期望碰撞对 ≈ n²/2³³（n 为总点
  数）。2048×10⁴ ≈ 2.05×10⁷ 点 → ~4.9 万对碰撞；2048×10⁵ ≈
  2.05×10⁸ 点 → ~490 万对——点数 ×10，碰撞 ×100。
- 结构性认识：随机布点误差随 k 下降（~1/√k），碰撞误差随 k² 上升，
  **误差主导项会切换**——参数调到平衡点即停，过了平衡点加资源反而
  变差。90% 削减正落在平衡点附近。

## 7. 迁移策略：双环共存 + 按请求选环

直接全局换环会让几乎所有缓存失效，回源流量尖峰不可接受。PBR 的
做法：

1. **新旧双环同时在内存**（迁移期内存翻倍，可接受）。
2. **每请求选环框架**：按请求哈希稳定决定用哪个环——同一请求始终
   走同一环，单请求视角一致，且可干净回滚。
3. **双维度分层放量**：流量百分比 × 地理范围独立控制，先小验证点，
   再逐级放大到全网，爆炸半径最小。
4. **监控面**：后端选择 trace、环版本计数器、连接错误、进程内存、
   启动时间、缓存行为、回源流量。
5. 放量到 100% 且稳定后，才移除旧环。

## 8. 结果与开源状态

- 两项改动合计把 PBR 内存占用降了 **100TB**（全网累计；此前 DNS
  团队另省过 100TB，两不相干）。
- 已随 `pingora-ketama` crate 发布，藏在一个（暂未宣传的）cargo
  feature 后：**v2 环** = 压缩存储格式 + 更快的排序方法 + 可配置
  基线哈希数。v1 环完全不动，两者可同时运行并按请求选择。

## 9. 对 dendro 的可借鉴点（本文自行引申）

1. **Rust 紧凑内存表示**：对齐导致的 padding 是隐形 33% 浪费
   （u32+u16 → 8B）；`[u8; N]` + `from_ne_bytes` getter 是
   `repr(packed)` 的无争议等价物、编译产物相同。dendro 内存态紧凑
   数组（memtx 结构、页/键缓冲、任何 `{u32, u16}` 形态的定长记录）
   同款手法可用。
2. **参数调优先推闭式解**：CV_k 这类精确公式让"多花 10× 内存换
   多少误差"变成一道算术题，而不是压测玄学。dendro 的采样率、
   bloom/sketch 参数、后台任务批大小等都适用"误差预算 → 反解参数"
   的路径。
3. **警惕误差主导项切换**：一种误差随资源下降、另一种随资源上升
   （碰撞、锁竞争、放大系数……）时，最优点在两者平衡处，无脑加
   资源会负收益。上线前用模拟找拐点，而不是只看单调下降段。
4. **双版本共存迁移模式**：新旧共存 + 按请求键稳定选择 + 双维度
   放量 + 全量后才删旧——与 dendro 未来存储格式/WAL 版本升级的
   诉求同构，可作为迁移框架的设计参照。
5. **若 dendro 未来做分片/缓存路由**：一致性哈希的基线 160 点/
   服务器是 NGINX/Pingora 的工程共识起点；权重乘基线、基线决定
   最低权重者的误差下限；哈希宽度（32 vs 64 位）要在点数预算
   定了之后按生日悖论反推。
