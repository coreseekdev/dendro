## 0. 结论先行

**当前架构的性能天花板不在任何单点热点，而在一个结构性事实：缓存复用的单位是
AST（文本形状的数据），不是编译产物（可执行的程序）。** 每次执行——哪怕是最简
单的 `WHERE pk=?` 点查——都要重新支付"SQL 机器税"：两次 AST 整树深克隆、
build_plan + 7 条重写遍历、全表达式克隆的掩码分析、以 `to_string()` 为键的谓词
重编译。SQLite 对标路径完全没有这笔税：`sqlite3_stmt` 缓存的就是编译完的字节码，
执行 = 绑定参数 + 跑寄存器。

**裁决：留存储、重装中段。** prolly/memtx/WAL/checkpoint 这套不可变底座健康且
已多轮验证，不动；SQL 中段（解析后→执行前）以"编译边界"为轴重装——这与
2026-09-16 审视报告"渐进统一到计划路径"的裁决同向，只是把终点从"统一"推进到
"编译一次、执行多次"。同时勘探揪出一个立即可拿的存储侧大坑：**INSERT 每行的
PK 存在性检查在 memtx miss 时触发全 catalog 树扫描 + 每表 JSON 解码**（新键
插入的常态路径）。

预算主张（诚实口径：以下是预算不是承诺，验收一律 A/B 差分 + perf 归因）：
编译边界落地后 SQL 机器税从火焰图清零，point 路径预期再拿 30-50%——这是
"2.0 验收结构性不可达"结论中指出的两条出路之一（另一条是 10M 负载复验），
且不依赖负载口径。

## 1. VDBE 问题定案（就地证据）

**问：SQLite 支持 VDBE 字节码直接指向（direct threading）吗？**

**答：不支持。** 证据取自 Cargo.lock 锁定的 libsqlite3-sys 0.35.0 捆绑
SQLite 3.50.2（即 sqlite-cmp 基准臂背后的那个 SQLite）：

- 主解释循环是一个 `switch( pOp->opcode )`（sqlite3.c:95321 起），外层
  `for(;;)` 推进 `pc`/`pOp`。**整个 25 万行 amalgamation 中 `goto *`（computed
  goto）出现次数为 0**，也没有任何构建开关能启用 direct threading——SQLite
  核心坚持可移植 C，不依赖 GCC 扩展。
- 控制流全部经整数 `pc`：跳转指令设 `pc = p2` 后 `continue` 外层循环
  （`goto jump_to_p2` 宏族，sqlite3.c:95434 起）。
- SQLite 有的两个"字节码"设施都不是直接指向：①prepared statement 本身就是
  缓存的 VDBE 程序（这是它快的真正原因，见 §2）；②
  `SQLITE_ENABLE_BYTECODE_VTAB`（`.bytecode` 命令）只是**只读检视**程序的
  表值函数，不是另一种执行模式。

**为什么 switch 够快**：opcode 是稠密 u8（0..~185），编译器把巨型 switch 编成
跳转表——每条指令一次间接分支，与 computed goto 在现代分支预测器上的差距在
个位纳秒级。direct threading 的理论优势（每指令独立预测槽）对 SQLite 的指令
混合收益很小。**这给 dendro 的启示不是分发机制，而是固定成本结构**：SQLite 的
胜利来自"每执行零重解析、零重规划、零克隆"，分发方式是次要的。Rust 里稠密
enum + match 同样编译为跳转表；fn 指针表（Rust 式 direct threading）会失去
内联，不推荐。Turso/Limbo 的 Rust VDBE 复刻（已入档）同样是 match 循环。

**对 dendro 的直接结论**：问题"我们的编译产物要不要用直接指向分发"是伪问题；
真问题是"我们要不要有编译产物"。现状是没有——这是 §2 的主题。

## 2. 宏观诊断：三重税

SQL 执行路径的完整管线（勘探全文见附录 A，此处只列税单）：

```
文本 → split → [plan_cache: AST] → 深克隆① → exec_statement
  → Query 臂深克隆② → eval_query
    → 快路径形态门三连（未中白付）
    → 通用路径: build_plan → 7 次重写遍历 → 掩码分析（全表达式克隆）
    → exec_plan 树递归解释（每节点 String label、bindings HashMap 克隆）
    → 表达式: AST 递归解释器（投影/过滤/键）或 ScalarProgram（仅谓词）
  → 输出: colmeta 两遍 + ≤256 行 direct_rows / Arrow 批
```

**税一：AST 克隆税**。plan_cache 命中 = `cached.as_ref().clone()`（sql/mod.rs:172，
Statement 整树）；Query 臂再 `q.as_ref().clone()`（sql/mod.rs:731）。prepared/
形状缓存路径每执行还有 ParamSwap 构造 + Drop 还原等 3 次全树 Visitor 遍访
（shapecache.rs:217/238/267）。缓存的存在反而制造了克隆——因为缓存的是数据
（AST）不是程序。

**税二：重规划税**。每次执行 build_plan 后跑 7 条重写遍历——且
`rewrite_eq_copy` 被连续调用了**两次**（sql/scan/mod.rs:209-210；EXPLAIN 路径
只调一次，疑似复制残留）；plan_scan_masks 再把计划内全部表达式克隆一遍
（plan_exec.rs:416-478）。这些是 prepare 一次就该定型的东西。

**税三：解释税**。表达式求值双轨：AST 递归解释器（expr.rs:eval）服务投影/
UPDATE/DELETE 过滤/ORDER BY 键——`Value` 字面量每行 `clone`、`Identifier` 取
`row[i].clone()`；ScalarProgram 寄存机只覆盖谓词，且缓存键 =
`(e.to_string(), names.join)`（scalar.rs:227）——**每次过滤调用先把 AST 渲染
成 String 作键**，常常比编译本身贵；eval_row 每步操作数 `regs.clone()`、每行
重建寄存器文件（scalar.rs:703-736）。更隐蔽的解释税在聚合：
`exec_aggregate_composite` 的投影匹配**每输出行每投影表达式 `e.to_string()`**
再线性 position 查找（plan_exec.rs:129-134）——O(行×投影×聚合列) 的字符串
渲染。join/group 键同样是字符串化（join.rs:414 `format!("i:{i}")`、
agg.rs:157-165 类型标签 String）。

三重税的金额：第十三/十四轮已把可见热点砍到"SQL 机器热点清空"（火焰图前十
无 SQL 机器帧），剩余成本摊在几十个小项里——这正是结构性税的特征：没有单点
可砍，只有换结构才能整体消失。SQLite 对标臂 2.1µs/点查 里没有以上任何一项。

## 3. 拆开重装裁决

| 层 | 裁决 | 理由 |
|---|---|---|
| prolly/memtx/WAL/CAS | **留** | 不可变底线（owner 定案）；多轮 TLA+/测试/崩溃恢复验证；性能已达标区（insert.disk 1.9×） |
| checkpoint 三段式 | **留，补第二步** | publish 阶段锁内 I/O 是残余最大写路径瓶颈，MO 蓝图已入档（§4-D） |
| 解析层（sqlparser） | **留** | 换解析器无收益；解析已非热点（形状缓存生效） |
| SQL 中段（AST 缓存→重写→解释） | **拆开重装** | 三重税的结构根源；已有目标架构 70% 骨架（Plan IR + ScalarProgram + pipeline），缺的是"编译边界"这根轴 |
| 快路径家族（try_point/range_early） | **并入编译期** | 每执行三道形态门 = 又一笔税；编译期选 access path 后形态门消失，且天然满足"快路径在统一框架内"的 owner 红线 |
| 双表达式引擎 + 双子查询检测 | **收敛为一** | 编译边界的副产品；两套并存本就是维护债（十四轮 review 已记） |

不推翻的理由同 2026-09-16 审视报告：530 workspace 测试 + 34 SLT 是重写带不
走的资产。重装以"渐进换内芯"方式进行：每一阶段现路径与新路径共存于差分轴后
面，测试永不红。

## 4. 重装蓝图（四条线，A 为轴）

### A. 编译边界：CompiledPlan（dendro 的 VDBE 时刻）

**目标形态**：以 `(SQL 形状, catalog root, dialect)` 为键缓存 `CompiledPlan`——
内含扁平化的程序（Plan 树或步骤数组）、编译期解析好的列偏移、已编译的全部
ScalarProgram（谓词+投影+键）、access path 描述符（table_id、键编码器、投影
偏移）、输出 schema。执行 = 取计划 → 参数入槽 → 跑。**AST 在 prepare 后不再
被触碰。**

**失效协议**：catalog root 变化（DDL/分支切换/checkpoint 推进视语义而定）即
失效——dendro 的 versioned catalog 天然给了等价于 SQLite schema cookie 的
失效信号，这是现架构送的重装便利。

分三步，每步独立可验收：

- **A1 去克隆**（小改动，先行）：plan_cache 存 `Arc<Statement>` 命中改借用
  执行（exec_statement 借用化），Query 臂第二次克隆消掉。形状缓存 ParamSwap
  三遍访改为执行期参数槽（ScalarProgram 已有 `Param` 步，scalar.rs:36-40，
  只差把代入从 AST 挪到执行器）。预算：point 探针 +10-15%，火焰图上克隆帧
  消失。
- **A2 编译缓存**（主体工程）：CompiledPlan 落地，重写链/掩码/谓词编译全部
  移到 compile 时跑一次。顺带修掉：rewrite_eq_copy 双调用、谓词缓存
  to_string 键（键=计划内指针身份，或干脆挂在计划上不查缓存）、
  exec_aggregate_composite 的每行 to_string（编译期把投影解析为槽位）。
  预算：SQL 机器税清零——point.mem/disk 各 +20-40%；update/insert 同享
  （它们每行/每条也付重规划税）。
- **A3 快路径并入**：try_point_early/try_range_early 的形态判定移到编译期，
  编译产物直接是"点取程序"/"范围程序"。每执行三道形态门消失；DELETE 的
  早退缺失（§4-C3）在同一框架内补齐而不是加第三条快路径。

**风险与对策**：参数语义（NULL 三值逻辑、类型强转）必须在编译期定形——
以现有 SLT 语料 + 差分轴（optimize=off / DENDRO_NO_GATE 先例）双保险；
计划缓存内存上界——沿用 NodeStore 字节预算 LRU 的先例。

### B. 执行模型：从"每行解释"到"每批执行"

- **B1 类型化键**：join/group/投影匹配键从 String 化（join.rs:414、
  agg.rs:157-165、plan_exec.rs:129-134）改为 order_domain 键编码
  （point.rs:20 已有域实现）。聚合/join 路径预期数量级（字符串渲染 +
  哈希整串 vs 定宽比较）。预算：无负载回归；agg/join 基准翻倍以上。
- **B2 ScalarProgram 全覆盖**：投影/过滤/键统一走寄存机；寄存器文件跨批复用
  （scalar.rs:703 注释自认"留给 B2 接线"）；op 编译期特化（现在每步从侧表
  取 op 再 clone，scalar.rs:731-736）。AST 解释器降级为编译失败的兜底。
- **B3 算子流式化**：算子间 `TableView{Vec<Vec<SqlValue>>}` 全物化改拉取式
  批迭代（ROW_BATCH=1024 的 pipeline.rs 已有批式骨架，缺的是算子接口）。
  这主要兑现在 range100（当前 0.3×，最大落后场景）和大结果集内存。

B 线依赖 A2（没有编译边界，B2 的特化每次执行重做等于白干）。

### C. 存储访问缝：点路径的散乱收拢

- **C1（立即，与重装无关）INSERT 的 PK 检查走 RESOLVE_CACHE**：`entry_root`
  （ddl.rs:1182-1193）在 memtx miss（新键插入常态）时被每行调用，内部
  `catalog_entries` = catalog 树**全量 range_scan + 每表 TableEntry JSON 解码**
  （含 col_segments 路径）。RESOLVE_CACHE（scan_table.rs:758-827）里已有同
  root 的 TableEntry（含 table_root）。一行改动级别的修复，insert 多表场景
  是 O(表数×段元数据)→O(1)，单表基准也白省一次树遍历+JSON 解码/行。
- **C2 UPDATE 旧值读对齐 SELECT**：`build_point_view` 整行 `row_from_bytes`
  （point.rs:503-504）而 SELECT 已用 `decode_row_proj`；`fetch_row_bytes`
  miss 后 `get`+`latest_ts` 两次独立走 shard 双锁（point.rs:432-436）可合一；
  新行可字节拼接复用旧行 payload 未变列，免整行 SqlValue 物化。对应已知
  ~17% 树 lookup 瓶颈的可削减部分。
- **C3 DELETE 早退**：exec_delete 一律全表扫 + 逐行 AST eval（ddl.rs:1215，
  注释自认"v1"）；`resolve_table(...).as_ref().clone()` 深克隆 Schema/Entry
  又把 Arc 化收益丢了。在 A3 框架内补点删/范围删。
- **C4 投影解码真跳过未选列**：decode_row_proj 对未选中的字符串/字节列也
  构造 SqlValue（format/row.rs:241-258, 302-309）——tag+len 已知可只前移
  游标。宽表选单列点查白付全部字符串分配。
- **C5 TableAccess 编译产物**：A2 的 access path 描述符落地形态——持
  `Arc<Branch>`、table_id、键编码器、投影偏移；一次点查里 `db.branch()`
  被调 3+ 次（implicit_snapshot/resolve_table/fetch_row_bytes 各一，
  engine.rs:910）收敛为一。Session 缓存 `Arc<Branch>`（失效点单一：
  remove_branch_runtime，engine.rs:1106-1108）。

### D. 写路径残余（非阻塞 checkpoint 第二步 + 攒批）

- **D1 publish 出锁**：三段式只把物化挪出了 commit_mu，publish 仍锁内做
  WAL Checkpoint 帧 `Durability::Always`（= flush_now 真落盘，
  engine.rs:1697-1702）+ manifest LIST+GET+CAS PUT 重试至 64 次
  （engine.rs:1741-1760）+ 旧 epoch 墓碑 LIST。方向：head CAS 成功即逻辑
  发布，WAL ck 帧与 manifest 异步收敛（MO TAE 蓝图已入档，engine.rs:1252-1256
  的 in-doubt 先例可援引）。
- **D2 CAS put_batch 每节点税**：每新 chunk 一次 `has()` 探测（cas.rs:80）
  + PAR=8 每组 spawn OS 线程（cas.rs:87-113）——万级节点 checkpoint =
  万次线程创建。常驻写线程池（或 io_uring，Turso 档案）。
- **D3 checkpoint prepare 去冗余**：muts 全量 clone（engine.rs:1596）→
  chunker 再 to_vec+sort+dedup（chunker.rs:182-187，pending BTreeMap 本已
  有序，排序纯冗余）；每表循环重跑 catalog_entries；count_rows 树根重数可
  增量维护（+puts −deletes）。
- **D4 WAL 帧编码去双拷**：TxnRecord 构造 `v.to_vec()`（engine.rs:2122）+
  encode_txn 再序列化——值在 Txn/memtx/pending 三处已是 `Arc<[u8]>` 共享，
  唯 WAL 路径断链。对应待办"update 0.6× WAL 攒批"。
- **D5 write_full 流式化**（已入档的 18.8GB RSS 根因，integrate.rs:147-153
  整树 decode 进 BTreeMap）→ k 路归并直写新段。
- **D6 树读路径去锁化**（长期）：叶层分片 Mutex+LRU 哈希、上层
  RwLock<HashMap>（store.rs:181-217）——不可变内容寻址天然适配 ArcSwap
  快照读/无锁结构；十六轮已证 LRU 哈希 <3%，此项优先级低于 A/B，列此存档。

**回退观察纪律**（沿用每轮战役惯例）：每阶段 A/B 差分（optimize=off /

A2 是主战场，若其验收不达标则 B 线重评（无编译边界的特化是每次重做的特化）。
