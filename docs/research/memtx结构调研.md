# memtx 分片结构调研：高性能有序映射选型 + 持久化必要性分析

> 2026-09-10 · 起因：P2-6g 将 memtx 分片从 HashMap 换为 BTreeMap（范围扫描
> 的地基），需要回答两个问题——有无更高性能的实现？memtx 是否需要（临时）
> 持久化？

## 1. 访问模式（选型的依据）

memtx = 分支的未物化写入 overlay（checkpoint 之后的增量），`64 分片 ×
有序映射<编码行键, 版本链>`。真实访问画像：

| 操作 | 调用方 | 频度 | 关键需求 |
|------|--------|------|---------|
| 点查 `get(key, snapshot)` | PK 下推直查、UPDATE/DELETE 定位 | 极高（TP 主路径） | 单键延迟 |
| 安装 `install(key, ts, val)` | commit Pass2（每事务每写键一次） | 高（写路径） | 短临界区、版本链有序追加 |
| OCC 校验 `latest_ts(key)` | commit Pass1（每写键一次） | 高 | 同点查 |
| 范围可见性 `snapshot_rows_in_range` | PK 范围下推扫描（P2-6g） | 中（分析/分页） | **键序迭代** |
| 全量快照 `snapshot_rows` | 非下推扫描 | 中 | 迭代 |
| 截断 `truncate_to` | checkpoint（释放 ≤ covered 的版本） | 低 | 顺序遍历 |

overlay 规模上界 = checkpoint 间隔内的写入量（默认 30s 或 16MB pending），
通常远小于表规模——这是与"主索引"选型的本质区别：**memtx 是热增量缓存，
不是全量结构**。

## 2. 结构对比（实测，1M 键 × 64B，单线程口径；并发由 64 分片提供）

复现：`/tmp/mapbench`（`docs/research/memtx结构调研.md` 同款负载，可随时重跑）。
单位：万 ops/s。点查探针 = 80% 热键 + 20% 键空间外（模拟 miss）。

| 结构 | 点查 | 安装 | 范围迭代 | 全量迭代 | 内存 | 备注 |
|------|-----:|-----:|---------:|---------:|-----:|------|
| **std BTreeMap（现状）** | 131 | 893 | **11.6 亿** | 1.03 亿 | 104MB | 全能；点查最弱档 |
| std HashMap（参照） | **312** | 257 | ✗ 无序（过滤式 29） | **7.15 亿** | 104MB | 点查 2.4×，无范围 |
| crossbeam SkipMap | 71 | 693 | 4844 万 | 3111 万 | 144MB | 点查指针追逐最慢 |
| scc TreeIndex | 118 | 547 | 404 万 | 9461 万 | 144MB | 免锁读；range 慢 |
| im OrdMap（结构共享） | 64 | 418 | **1.73 亿** | 6640 万 | 160MB | O(1) 快照；点查/安装最慢 |

**解读**：

1. **点查**：HashMap 2.4× 于 BTreeMap（哈希 vs 树下行 + 缓存局部性）——
   这就是 P2-6g 之前的状态；当时为范围能力支付的点查税 ≈ 250-470ns/次
   （64B 键、100 万键规模）。
2. **范围迭代**：只有有序结构可行；BTreeMap 全量/范围迭代都是最快档
   （B = 11 叉紧凑节点，顺序访问缓存友好）。
3. **SkipMap**：无锁读是卖点，但我们的并发已由分片 RwLock 解决（分片内
   单线程口径），其点查指针追逐反而最慢——**不选**。
4. **scc TreeIndex**：EBR 免锁读，但 range API 带 guard 开销后比
   BTreeMap 慢 25×；点查也不占优——**不选**。
5. **im OrdMap**：结构共享让"快照"变 O(1)（对 MVCC 理论上优雅），但
   点查/安装慢 2-4× 且内存 +54%——与"热增量缓存"定位不符——**不选**。

## 3. 结论与建议

**保持 std BTreeMap（64 分片）**：五项操作没有单项垫底，范围能力是 P2-6g
的既得收益；点查税（~4%/点查，仅当 overlay 巨大时可见）是可接受成本。

**记录为未来选项**：若出现"overlay 巨大 + 点查极重 + 范围扫描少"的真实
负载画像，**双结构**（HashMap 承担点查 + BTreeMap 承担有序迭代，同分片锁
内双写，键内存 ×2）可将点查拉回 2.4×——实现 ~50 行，收益/风险数据齐备
（本表），按负载触发再做。

**明确不选**：SkipMap / scc TreeIndex / im OrdMap（证据同上）。

## 4. memtx 是否需要（临时）持久化？——不需要，且不该做

**现状的持久化语义**（已足够）：

- memtx 本身是易失缓存，**持久化由 WAL + checkpoint 双层承担**：提交 =
  WAL append（掉电安全由 fsync 策略决定）→ 安装 memtx；checkpoint 把
  memtx 增量物化进 prolly 树（内容寻址、真持久），`covered_seq` 推进后
  WAL 前缀可回收。
- **恢复 = 重放**：`wal_first_seg` 起顺序回放，实测 **2.5M 事务/s**
  （20k 事务 8ms，`benches/results/recovery.json`）。恢复时间上界 =
  checkpoint 间隔内的未物化事务量 ÷ 2.5M/s——是**可配置的滑杆**
  （`checkpoint_interval_s` / `checkpoint_threshold_bytes`），不是一个
  需要新机制的问题。

**候选方案评估**：

| 方案 | 收益 | 代价/风险 | 判定 |
|------|------|----------|------|
| (a) 优雅关闭时快照 memtx 到文件 | 快速 reopen | 崩溃场景无效（正是最需要恢复的场景）；文件一致性需再设计 | ✗ 收益只覆盖优雅路径 |
| (b) mmap 影像文件（临时持久化） | 进程重启免回放 | 影像与 WAL 双事实源（一致性协议复杂化）；写放大 ×2；mmap 页回写时机不可控破坏持久化语义 | ✗ 双事实源违反"Journal 即事实源"架构原则 |
| (c) 更频繁 checkpoint（现有旋钮） | 直接缩短回放 | 写放大按需付出 | ✓ 已有能力，按负载调参 |
| (d) status quo | — | — | ✓ |

**结论**：memtx 持久化 = 与 checkpoint 语义重复的第二持久化通道，违反
"单一事实源"（SOTA 调研的核心结论：Journal 即事实源）。回放速度
（2.5M txn/s）已使恢复不是瓶颈；若极端负载需要，调 checkpoint 旋钮即可。

## 5. 遗留观察

- `partition_point` 依赖版本链 ts 有序——install 的有序插入（P2-6 修复）
  是正确性前提，任何未来结构替换必须保持或重建该不变量。
- 分片数 64 为写并发与范围分片数的折中；分片内 BTreeMap 无并发竞争
  （RwLock 单写者口径）。
- 键内存大头是 `Box<[u8]>`（每键一次分配）——若 overlay 内存成为问题，
  值得评估"键内联进版本链节点"的arena 化改造（预期省 ~30%），但属于
  内存优化而非延迟优化。

# 附：资源守卫生产化差距清单（2026-09-10，R7 评估）

对照 PostgreSQL/MySQL 生产标准的逐项评估与处置：

| 项 | 生产标准 | Dendro 现状 | 处置 |
|----|---------|------------|------|
| 连接守卫原子性 | CAS 无竞态 | fetch_update 循环 ✓ | ✅ |
| 连接守卫 panic 泄漏 | panic 展开必回收 | **曾泄漏**（handle_connection panic → 计数滞留 → 永久拒服） | ✅ ConnSession Drop（R7-1） |
| 连接守卫竞态上限 | 检查与写入原子 | — | ✅ |
| 分支上限竞态 | CAS 重试以最新状态重评 | **曾越限 +1**（预检在 CAS 外） | ✅ 权威检查入闭包（R7-2） |
| 单事务字节 | Pass1 拒绝无副作用 | 入队前拒绝 ✓ | ✅ |
| 拒绝可观测 | /metrics 拒绝率 | dendro_connections_{active,max,rejected_total} | ✅（R7-3） |
| 语句超时 | statement_timeout 标配 | ✗ 缺失——失控查询占线程到永远 | ⬜ 需查询取消基础设施（PG CancelRequest + 执行器检查点） |
| 每会话内存 | prepared/cursors 有界 | prepared ≤1000、游标 ≤255 且单游标 ≤64MB（54000 拒绝保留）；旋钮可调 | ✅ 会话配额（R8） |
| 结果集留存 | 大结果可限 | max_result_bytes（默认不限）超限丢输出回 54000 | ✅ 守卫（R8）；真流式 = 执行器惰性化仍 ⬜ |
| 多节点全局配额 | 集群级连接数 | 每进程独立（N 节点 = N×上限） | ⚠️ 文档化；全局配额需分布式协调 |
| 磁盘空间上界 | WAL/对象占用可观测可限 | checkpoint 回收 ✓；无空间水位拒绝 | ⬜ 可观测先行 |

**判定**：连接/分支/事务三类守卫的**正确性**已达生产水平（竞态/泄漏/副作用
闭合 + 回归防线）；**完备性**未达——语句超时、会话内存配额、结果集流式是
下一批，其中语句超时优先级最高（可用性风险）。
