# 选型：Raft 共识实现对比与 Dendro Journal 底座决策

> 问题：Journal（提交日志）需要一个多副本持久化层——用哪个 Raft 库？
> 本文对比 Rust/Go/Java 生态的工业级实现，给出推荐与备选。
> 2026-09 · 决策文档。

---

## 1. 先想清楚：Dendro 的 Journal 到底需要什么

Journal 不是通用状态机复制——它是**单写者追加日志**（每分支一个写者，epoch fencing 已保证）：

```
需要：                                不需要：
├─ 追加（append-only）                ├─ 通用状态机快照安装
├─ 多数派持久 = ACK                   ├─ 自动 leader 选举（租约/fencing 已有）
├─ 顺序 = ts 全序（epoch<<32|seq）    ├─ 成员变更（v2）
├─ 读取 = 顺序重放                    ├─ 分片/多 Raft 组（单分支=单组够用）
└─ 恢复 = 顺序重放                    └─ 事务语义（上层已有）
```

关键洞察（Aurora 论文的教训）：**如果你已经有外部单写者保证（我们的
epoch fencing），Raft 的 leader 选举和状态机安装层是多余的**——你只需要
"多数派持久化的追加日志"，即 PacificA/Socrates 式的**复制日志**，而非
完整 Raft。这决定了选型方向。

## 2. 候选对比

### 2.1 Rust 生态

| 库 | 形态 | 生产验证 | 集成成本 | 评估 |
|----|------|----------|----------|------|
| **tikv/raft-rs** | 仅共识核心（FSM 驱动） | ✅ TiKV/TiDB（最大 Rust TP 生产部署） | 高：需自建传输/存储/tick 驱动 | ⭐ 最成熟，但胶水代码 ~500 行 |
| **openraft** | 较高层框架（含存储 trait、网络抽象接口） | ⚠️ Databend 生产，但版本 API 频繁破坏性变更 | 中 | Databend 系，与 openraft 生态一致 |
| **raftify** | raft-rs 的高层封装 | ⚠️ 较新 | 低 | 不确定长期维护 |
| **async-raft** | ❌ 已废弃（openraft 前身） | — | — | 排除 |

## 3. 推荐：三层演进

### M1（当前，P2 第一步）：嵌入式单节点 Journal

**不做 Raft。** WAL 的组提交缓冲 + 段上传就是 Journal 的单节点形态——
它已经具备：追加语义、段持久（PUT 原子）、ts 全序。把它形式化为
`Journal` trait 即可，无需任何新组件。

```
Journal（单节点）= 当前 WalWriter 的形式化包装
  append(batch) → 段缓冲 → flush_now → PUT wal/{branch}/e{epoch}/{seg}.wal
  durable_watermark() → 已持久 ts
  replay(from, sink) → 段读取 + 帧迭代
```

这一步的价值：**提交管线从"直接操作 WalWriter"改为"面向 Journal trait"**，
后续替换实现时协议代码零改动。

### M2（多节点，P2 主体）：静态三副本 Quorum Append

**不用 Raft 的 leader 选举**（epoch fencing 已取代），做一个轻量复制协议：

```
Leader（租约持有者节点）
  ├─ 接受提交批次 → 序号（全局 ts）
  ├─ 并行发往 F1, F2：AppendBatch{ts, records}
  ├─ 收到 ≥1 确认（+自己 = 多数派 2/3）→ ACK 客户端
  └─ F1/F2 追加到本地段文件（与 Leader 相同格式）

Follower 落后 → Leader 发 range（已有 HEAD 探测逻辑复用）
Leader 崩溃 → 存活 Follower 仍在多数派内，数据不丢
新 Leader 选举 → manifest CAS（epoch fencing 已有）+ F2 的日志重放
```

这是一个 ~300 行的协议（对比 openraft 的 ~5000 行），正确性由：
- 单写者租约（epoch fencing）→ 无分叉
- 多数派 ACK → 持久性
- ts 全序 → 恢复确定性

三个保证与 Raft 等价（在使用场景内），但省去了 leader 选举、
成员变更、快照安装三大复杂度。**代价**：Leader 崩溃后有
`TTL + 恢复重放时间` 的不可用窗口（秒级），Raft 则是
`选举超时 + 日志追平`（也是秒级，但自动化）。

### M3（v2，按需）：替换为 tikv/raft-rs 或 openraft

触发条件：需要**自动化 leader 选举**（无人值守故障转移）、
**成员变更**（在线加减节点）、或**多 Raft 组**（分支数 > 单组承载）。
从 M2 的协议升级到 Raft 的代价：Journal 的段文件已经是 Raft log 的物理
形态（追加+编号），只需把"租约决定 leader"换成"Raft 选举决定 leader"。

| 如果选 | 理由 |
|--------|------|
| **tikv/raft-rs** | TiKV 级生产验证；BatchSystem 吞吐好；但胶水代码多 |
| **openraft** | Databend 系、Rust 原生、API 较完整；版本不稳定是风险 |

## 4. 决策总结

| 阶段 | 共识方案 | 理由 |
|------|----------|------|
| **M1（当前）** | 单节点 Journal（WAL 即 Journal） | 零新组件，正式化接口 |
| **M2（P2 主体）** | 静态三副本 Quorum Append（自研 ~300 行，epoch fencing 选主） | Aurora/Socrates 证明：有外部单写者时 Raft 的 leader 选举是多余的 |
| **M3（v2 按需）** | tikv/raft-rs 或 openraft | 仅当需要自动化选主/成员变更时 |

**一句话**：不从 Raft 库开始——先用已有的 epoch fencing + WAL 段实现
"多数派追加日志"（Aurora 的核心洞察），Raft 库（raft-rs/openraft）作为
自动化选主的升级路径而非起点。
