# SQL 机器热点剖析与剖析设施（pprof-rs 火焰图，2026-09-21）

> 背景：P0 战役收官后 point 0.4× 的主战场 = SQL 机器（4-6µs）。
> 本机 `perf_event_paranoid=4` 禁用 perf——引入 **pprof-rs**（SIGPROF
> 信号采样 + backtrace-rs，进程内嵌，无权限要求）。本文 = 剖析设施
> 使用说明 + 火焰图热点定位 + SOTA/同族参考 + 下一役路线图。

## 一、剖析设施（新增）

| 设施 | 入口 | 用途 |
|------|------|------|
| **火焰图探针** | `cargo run --release --example flame -- [rows] [secs] [point\|tree\|insert]` | pprof-rs 信号采样 → SVG（`/home/nzinfo/bench-p0/flame-*.svg`）；SVG 内 `<title>` 含函数名+样本数，可脚本聚合 |
| perf 八阶段 | `cambium.perf_stages` / `perf::report()` | 阶段级分解（无栈） |
| memprof 三层 | `cambium.memory_usage` | 驻留计量 |
| memres 三臂 | `example memres [rows]` | 驻留/LRU 命中率/perf 分解 |
| pointearly | `example pointearly` | 未物化早退/冷 get/range100/差分 |
| pointbreak | `example pointbreak [rows] [full] [diff]` | 点查分层 + optimize on/off + 表达式投影对照 |

pprof 依赖：`dendro-core [dev-dependencies] pprof = { version = "0.15", features=["flamegraph"] }`
（tikv/pprof-rs：SIGPROF 定时 + backtrace-rs 采样，inferno 渲染——
perf_event_paranoid 环境的 CPU 剖析替代）。

## 二、火焰图热点全景（1M 行，flame 探针，5s 采样）

**point 模式**（未物化全驻 memtx，108k ops/s）：
| 热点 | 占比 | 判定 |
|------|------|------|
| `TableMem::get` → sorted `partition_point` 二分 | ~15% | 存储本质工作（1M 键冷 key 0.73µs） |
| `to_result` → `String::push/realloc` | ~5% | **可修**：QueryResult 行物化无预留扩容 |
| `Query::clone`（AST 深克隆） | ~5% | **可修**：eval_query 每查询无条件 `q.clone()`（scan/mod.rs lower_subqueries 输入） |
| memtx 冷 get | 460ns | 已优化到位 |

**tree 模式**（物化后，143-147k ops/s）：
| 热点 | 占比 | 判定 |
|------|------|------|
| `lower_subqueries` | ~16% | **下一役大头**：含 q.clone + reject_multi_from + rewrite_rowid_refs 串联 |
| `rewrite_rowid_refs` | ~15% | **下一役大头**：rowid 别名扫描 + 每因子 resolve |
| `resolve_table`（缓存命中路径） | ~9% | ✅ 已修（见下）；残值为锁+哈希+Arc clone |
| NodeStore LRU `get_node`（foldhash 哈希） | ~8% | 树点查 3 层 × LRU 哈希查找——可再省（见 SOTA） |
| `Node::lower_bound` | ~11% | 树节点内二分（本质工作） |

## 三、本轮已修：resolve 缓存命中深克隆

`resolve_table/resolve_table_at` 命中即返回 `Arc<(Schema, Entry)>` clone
（两次原子递增）——此前命中即**深克隆** Schema（columns Vec×String）
+ Entry（十余字段），~600ns × 2 次/查询（try_pk_pushdown +
rewrite_rowid_refs），火焰图 `to_vec/to_string` 6.6% 消失。
pointearly：未物化 +6%、物化 +5%（162k/200k）。40 调用点：热路径借用
`&rc.0/&rc.1`，DDL/管理面 `.as_ref().clone()` 等价 owned。633 测试全绿。

## 四、下一役路线图（SQL 机器砍半，point 0.4× → 0.6×+）

按火焰图 ROI 排序（合计 ~36% 可削减）：
1. **q.clone 门控**（~5%）：`expr_has_subquery` 全树预检（现成单Expr 版），
   无子查询/无 WITH 免整树克隆。难点：lower_subqueries 同时承担
   reject_multi_from + rewrite_rowid_refs（需 mut）——拆分：只读检查
   前置 + rowid 改写仅"含 rowid 别名标识符"时进行。
2. **rewrite_rowid_refs 重构**（~15%）：rowid 别名→PK 列名映射缓存
   （catalog 根键控，表结构 checkpoint 间不变）；别名标识符快扫
   （无 rowid 引用直接返回）。
3. **to_result 预留**（~5%）：行物化 String/Vec with_capacity
   （按列宽估计或 schema 统计）。
4. **树点查免 LRU 哈希**（~8% 潜力）：点查 3 层 × foldhash——
   可缓存"热路径节点指针"或根两层常驻（树高 3，根+中层仅数十节点，
   专用小缓存可装满）。SOTA 对照见下。

## 五、SOTA / 同族参考

**剖析**：[tikv/pprof-rs](https://github.com/tikv/pprof-rs)（本设施）；
[hotpath.rs 教训文](https://hotpath.rs)（进程内采样器构建）；[inferno]。

**有序结构**（memtx 对照）：[rart](https://crates.io)（ART，含 versioned
形态）、[arctic](https://docs.rs)（无锁并发 ART）、[bench-maps](
https://github.com/Rufflewind/bench-maps)（BTreeMap/HashMap/sorted-vec
对比）、["Smolderingly fast B-trees"](https://www.scattered-thoughts.net)
（B-tree 节点大小调优——**std 11-key 非最优点**，cache line 对齐节点
更优——sorted 主区未来若分层可参考）、ART 原论文（Leis，TUM——
读重负载标杆，矮高度 O(k)）。**dendro 现状判定**：sorted 数组+delta
已对齐 SOTA 主流形态；ART 是键形态多样时的候选（rowid 定长键下
数组二分已够）。

**Rust 复刻 SQLite 族**：
- **Turso（原 Limbo，tursodatabase/turso）**：SQLite 全重写（SQL 方言
  3.50.4/文件格式/C API 三兼容），**VDBE 字节码 VM**（"数据库的 LLVM"）
  + **io_uring 原生异步 I/O**（与 SQLite 同步 I/O 的核心差异）+
  `BEGIN CONCURRENT` MVCC + 多进程 WAL 协调（.tshm sidecar）。参考点：
  ① VM/字节码路线 vs dendro 计划执行器的对照（dendro IR 计划 +
  形状缓存 ≈ 其 VM 程序缓存——Turso 佐证"编译一次多次执行"路线）；
  ② 异步 I/O 是服务形态差异（dendro 云原生 ObjStore 天然异步面）；
  ③ 确定性仿真测试（dendro 已有 TLA+/差分，同族方法论）。
  Enberg et al. EdgeSys'24 / CoNEXT-SW'23（serverless + async I/O
  协同设计）。来源：[turso.tech](https://turso.tech)、
  [GitHub](https://github.com/tursodatabase/turso)、
  [The Register 报道](https://www.theregister.com)。
- std `BTreeMap`：~1k 以下与 HashMap 竞争（bench-maps）——**碎片小表
  场景 std 足够**，dendro memtx 分片后单分片规模大，数组正确。
