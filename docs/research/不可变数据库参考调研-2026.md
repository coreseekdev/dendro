## 一、dendro 基线（对照前提）

dendro 的不可变核心栈（spec 01–03）：

| 层 | 机制 |
|---|---|
| 对象层 | 一切持久化状态 = 不可变对象；`ObjStore` trait；20 位零填充编号；无 LIST 恢复（指数+二分 HEAD 探测）；manifest 单调版本 + `put_if_absent` CAS；put-id 不确定写消解 |
| WAL | 段 = 一个不可变对象；24B 帧头 + CRC；组提交（事件驱动刷盘，两段式提交解耦）；毒化语义（40003）；每分支独立 seq/段序列；fence epoch |
| 版本层 | SHA-512 截 20B 内容寻址；prolly tree（weibull keySplitter，min 512/target 4096/max 16384，逐层 salt）；refs/catalog 本身是 prolly map；分支 O(1)；merge = 双 patch 流 + 行级冲突，**冲突即 abort**；节点编码含 `addr_slots`（GC 免解析扫描） |
| GC | 墓碑随 manifest 原子发布 + 保留窗口；manifest 保留 16 版；**CAS chunk v1 不回收** |
| 时间旅行 | `FOR SYSTEM_TIME AS OF <commit|timestamp>`，精度 = 提交粒度 |

参考系中 dendro 已明确借鉴的：dolt 的 hash/splitter/address_map/patch 合并、slatedb 的 WAL 段+HEAD 探测+manifest CAS+put-id。**本文只列尚未借鉴的部分。**

## 二、与各参考的核心差异

### dolt / doltgresql —— 同道中走得最远的

dolt 的存储栈是 NBS（noms block store）：memtable(128MB) → **table file**（不可变大文件：snappy chunk 数据 + prefix(8B)二分/suffix 比对索引 + footer）→ manifest(文件锁乐观并发) → conjoiner（>256 表文件时合并最小 N 个）。世代分代（oldGen/newGen NBS）支撑分代 GC。doltgresql 不是 fork，是把 dolt 当库 + 换 PG 协议/类型/系统表前端（`server/tables/dtables/init.go:26-57` 用 hook 把 dolt_* 系统表按方言改名）。

**关键差异（dendro 视角）**：
1. **冲突处理哲学**：dolt 冲突不阻塞合并——冲突/约束违反写入每表的 Artifacts prolly map（`go/store/prolly/artifact_map.go:30-60`），可 SQL 查询、可程序化 resolve、可 `--abort`（working set 里存 MergeState 记 pre-merge root，`doltdb/workingset.go:129-250`）。dendro 是冲突即 abort + `last_merge_conflicts` 视图。
2. **chunk 物理布局**：dolt 把大量 chunk 打包进 table file，dendro 逐 chunk 一个对象（`objects/{xx}/{hash}.chunk`）。对象存储上这直接决定请求数与成本。
3. **GC**：dolt 有完整的在线分代 GC（写记账 + safepoint + 在途读排空）；dendro v1 不回收 CAS chunk。

### immudb —— 带密码学证明的不可变 KV

三日志分离（vLog 值日志 / txLog 事务日志 / cLog 提交日志）+ 不可变 COW B-tree（tbtree）+ 主 Merkle 树（AHtree）。核心是 **Alh 链式累积哈希**：`Alh_n = H(TxID, Alh_{n-1}, innerHash)`，配合树+链双轨证明（inclusion / consistency / last-inclusion / linear advance，`docs/security/PROOFS.md:182-481`）与 ECDSA 状态签名。**dendro 没有任何防篡改/可验证性机制**——这是定位差异（immudb 卖点是审计抗抵赖），但链式哈希本身成本极低。

### endb —— 数据库即值（accumulate-only）

全库状态 = 一个持久化 map（md）+ 不可变 Arrow 文件堆；WAL = **一个 tar 文件**，每事务的 entry = 新 Arrow buffer + 最后一条 `_log/<txid>.json`（**md 的 JSON merge patch diff**）；提交冲突检测 = 锁内比较持久化结构指针 `eq`（结构共享 ⇒ 指针相等 ⇒ 零成本，`src/http.lisp:152-179`）；删除 = 元数据 deletion vector（行不动，记 `system_time_end`），时间旅行 = 双时间戳行过滤（SQL:2011 语法）。与 dendro 的"manifest JSON + 内存 OCC"架构最同构，工程细节参考价值最高。

### noblit —— append-only 的设计文档最佳（代码停滞）

datom 五元组 32B 定长、三个覆盖索引（EAVT/AEVT/AVET）、heap 追加堆、全库唯一可变部分 = 40B head（原子写即提交点，无 WAL）。hitchhiker tree 用 pending datoms（高层节点暂存脏数据、批量下刷）解决持久化树的写放大。文档把两条推论讲透：(a) append-only 永不复用名字 ⇒ **任何层缓存永不需要失效协议**；(b) GC 的代价清单（重写放大、旧文件可删时机、GC 后名字不再全局唯一）。

### immdb 参考集（备份）—— 修正既有报告的三个事实

- 该克隆是 **xtdb 2.x**（不是既有报告描述的 1.x EAV/B+ 树）：实际是 IID 哈希 trie + Apache Arrow 块 + 对象存储分层压实；
- datascript 没有真正的 as-of 查询（靠持久化结构持有旧值），datahike 才有双时态索引；
- PumpkinDB 的"内容寻址"是脚本层约定（LMDB `NOOVERWRITE` + HASH 指令），不是存储引擎特性。

有价值的新机制：xtdb 2.x 的 **bitemporal 区间下推 + 块级 temporal 剪枝**、nebari 的 **三段式提交与 by-sequence 双根**、terminusdb 的 **squash/pack 克隆**、PumpkinDB 的 **HLC 持久化发号**。

### layerfs / slatedb —— 对象存储工程细节

- layerfs：CDC"冻结 profile"（分块参数哈希进 GEAR 表，跨版本边界确定）、哈希**域分离**（对象/内容/inode 各自域）、"ID 命中 ≠ 复用成立，必须字节比对"、对象身份与物理 pack 容器解耦（256KiB pack）、stage 表两阶段发布（昂贵准入与廉价发布分离）。反面：`journal_mode=MEMORY + synchronous=OFF`，明确不提供崩溃持久性——dendro 不应学。
- slatedb（dendro 已借鉴基础三件后仍剩的）：**RFC 0026 GC 边界协议**（防"停顿写者复活"：GC 删旧元数据前必须先推进持久边界，写者提交成功后要复查边界）、重放去重以 seq 为准、代价模型重排（S3 瞬时空间放大免费 / 读放大按 GET 计价 / 写放大按出口带宽计价）、调用打标（Extensions 携带 `{调用来源, 对象类型, 重试原因}` 决定缓存策略）、fizzbee 形式化规格验证恢复协议。

## 三、值得 dendro 学习的关键设计（按主题，标注优先级）

### A. 不可变核心（本次重点）

**A1. 链式累积哈希：给 WAL/manifest 加防篡改链（P1，成本低收益大）**
immudb 的 `alh_n = H(n, alh_{n-1}, tx_digest)` 只需在每 commit 记录一个 32B 链头，任何人保存一个 (seq, alh) 对即可独立验证任意历史前缀未被篡改/重排/删除。dendro 的 manifest 已是单调版本+CAS，天然适合在 manifest 里携带每分支链头。进阶：immudb 的 **AHtree** 把 Merkle 树塞进 append-only 日志的方案（dLog = 按层扁平排列的 32B digest 流，节点位置纯算术计算 `nodesUntil/levelsAt`，`embedded/ahtree/ahtree.go:485-523`），Append 只追加根路径 digest，O(log n)——digest 流可按 chunk 上传对象存储，与 dendro 的 WAL 段天然契合。
（`embedded/store/immustore.go:1891-2003`、`docs/security/PROOFS.md`）

**A2. 冲突落库而非 abort：Artifacts + MergeState（P0，Agent 沙箱核心体验）**
dolt 把行冲突/FK/唯一/CHECK 违反统一写入 per-table Artifacts prolly map（参与版本化、可 `dolt_conflicts` 查询、可 `dolt_conflicts_resolve()` 程序化解决、`--abort` 回 pre-merge root）。对 dendro 的 Agent 场景（合并→程序检视→解决），"合并带着冲突完成、冲突本身是数据"远优于 abort+重放。dendro 已有 prolly map 基建，实现是"第二种 artifact 值类型 + merge 不 abort"。
（`go/store/prolly/artifact_map.go:30-60`、`merge/merge.go:169-386`）

**A3. 删除的时间语义：deletion vector + 双时间戳（P1）**
dendro 的 append-only 意味着删除也只能是新版本，但当前墓碑只服务 GC。endb 的做法：删除 = 记 `{row_id, system_time_end}` 到元数据 deletion vector，读取时按 `AS OF t` 过滤即得时间旅行（`src/sql/db.lisp:124-129`），压缩时 row_id 重映射保持历史连续；xtdb 2.x 更彻底——删除 = 插入一条带 valid 区间的墓碑行（`indexer.clj:100-232`），erase 是单独的 GDPR 硬删路径。**"逻辑删除=区间墓碑，物理抹除=独立路径"的分层语义**对 dendro 的墓碑设计是直接升级。

**A4. 时间约束编译成区间下推 + 块级剪枝（P2）**
xtdb 把 `FOR VALID/SYSTEM_TIME` 编译成两个整数区间（`operator/scan.clj:61-113`），每个 trie 块携带 min/max temporal 元数据，扫描先整块裁剪（`trie.clj:94-131`）。dendro 的 time travel 目前走"解析提交→换根重查"；若把 `AS OF` 下推为对 prolly 节点/chunk 的 temporal 元数据过滤，历史查询可免提交链解析。

**A5. 历史查询与压实解耦的不变式（P2）**
immudb tbtree 明确注释 `history(t) = history(compact(t))`——key 历史链放独立 hLog，主索引压实/GC 不影响历史查询（`embedded/tbtree/tbtree.go:80`）。dendro v2 做 CAS chunk GC 时必然面对"压实后墓碑历史还在不在"，这条不变式应提前写进 GC 设计。

**A6. 内容寻址缓存免失效的论证（认知资产，无需实现）**
noblit `docs/architecture.md:44-67`：永不复用名字 ⇒ 曾经取回的数据永远有效 ⇒ 任意层缓存（内存→本地盘→远端）无需失效协议、无需租约。dendro 已具备此性质，但把推论写进 spec 能指导未来读副本/CDN 层设计。反面对照：noblit 的 GC 代价清单指出 copying GC 会破坏"名字全局唯一"，dendro 用内容哈希天然免疫——这是对 dendro 路线正确性的独立印证。

**A7. 不可变树的写放大解法（P2，v2 prolly 升级时对照）**
dendro v1 用"路径复制 + 中点重分裂"的 CoW 简化（边界不重对齐，diff 多下一层）。参考系里有三种解法：noblit hitchhiker 的 pending 暂存（高层攒批下刷）、xtdb live index 的 log→page 两级紧凑化（`MemoryHashTrie.kt:11-71`）、datahike hitchhiker-tree 的节点内 op-log（b=17/node 300/log 283）。共同思想：**不可变语义 + 可变写缓冲**，攒批后一次确定性重建——与 dendro 的 memtx→checkpoint 分层其实同构，可用于 v2"前缀复用+重切+实时对齐"算法的节点内策略。

### B. 对象存储工程

**B1. chunk 打包成不可变大文件 + 合并器（P1）**
dendro 逐 chunk 一个对象：万级 chunk = 万级 PUT/GET/LRU 项。dolt 的 table file（chunk 数据 + prefix 二分索引 + footer + snappy + mmap，`go/store/nbs/table_index.go:42-110`）+ conjoiner（>256 文件时合并最小 N 个，`conjoiner.go:35-60`）是现成方案；layerfs 的 pack（GROUP 64KiB/PACK 256KiB/≤8191 record，`objects/pack.rs:6-11`）证明"对象身份与物理容器解耦、读时重组验证"可行。dendro 的 checkpoint 已知 dirty chunk 集合，按此打包顺理成章。

**B2. GC 边界协议（P0，dendro CAS+GC 最可能缺失的一环）**
slatedb RFC 0026：写者算好 version N+1 后停顿，GC（min_age 后）删掉别人写的 N+1，停顿者再写 N+1 → `put_if_absent` 假成功 → 写穿 CAS。防护：**GC 删旧元数据前必须先推进持久边界文件；写者提交成功后复查边界，落后于边界按冲突处理**（`slatedb-txn-obj/src/lib.rs:688-713`）。dendro 用"LIST 为权威 + 保留 16 版"缓解了读侧，但写侧"停顿写者复活"窗口值得专项审计。slatedb 还有 fizzbee 形式化规格（`specs/fizzbee/*.fizz`）验证此类协议——dendro 的恢复/fencing 协议可仿照。

**B3. 代价模型重排（认知）**
slatedb RFC 0002：对象存储上瞬时空间放大免费（compaction 全量重写可接受）、读放大按 GET 计价（最痛）、写放大按出口带宽计价（~1.5-2x 本盘写）。dendro 的 GC/compaction 策略不应从磁盘 LSM 直觉搬。另：分段尺寸上限应由"元数据块能否全驻内存"反推（Sorted Run 存在的理由）。

**B4. 空闲成本与调用打标（P2）**
RFC 0032 起因是空闲库 5 分钟 560 次 LIST ≈ $24/月——dendro 应有"空闲库月账单"指标。调用打标（Extensions 携带调用来源/对象类型/重试原因，按标签定缓存策略，RFC 0027）比到处传布尔参数干净。

### C. GC 完整方案（v2 CAS chunk 回收的路线图）

dolt 的分代 GC 三状态机（`go/store/types/value_store.go:568-710`）：OldGen→NewGen→Finalizing；**GC 开始后所有新写入 chunk 地址记账**（防并发写丢失）；Finalizing 等 `gcOut` 计数排空在途读后 swap manifest。SQL 层 safepoint：GC 等所有 session 到命令边界并枚举其内存中活跃 chunk 地址作为额外 GC 根（`doltdb/gcctx/gc_safepoint_controller.go:22-100`）。配合：slatedb 的"删除谓词 = 不在任何活跃引用区间 + min_age"；xtdb 的不可变对象生命周期状态机（LIVE/NASCENT/GARBAGE + garbage-as-of）。dendro v2 做引用计数入 manifest 快照时，这三家合成完整答案。

### D. 事务与并发

- **endb 指针等价 OCC**（`src/http.lisp:152-179`）：持久化结构未变则指针同一，`eq` 比较即冲突检测。dendro 的 catalog 若也用持久化结构（或 generation 计数），提交冲突检测可降到零成本。
- **immudb 两阶段流水线**：precommit（内存+日志追加，单锁串行）与异步 fsync 分离，三档 watcher（预提交/落盘/索引可见）让读者自选等待点；MVCC 读集校验（expectedGets 指纹，`ongoing_tx.go:38-73`）。对照 dendro 的组提交 latch 已有等价物，读集指纹可增强 OCC 验证凭证。
- **xtdb live index**：StampedLock 乐观读 + 写锁只护根交换，旧快照引用计数关闭（`indexer/live_index.clj:52-121`）——OCC 提交+快照发布的现成范式。

### E. 版本语义完整性（产品层）

1. **CommitClosure**（dolt，`prolly/commit_closure.go:29-60`）：每 ref 一棵 (height, hash) 排序的 prolly map，使 `commit_log`/祖先查找/`AS OF timestamp` 不递归链。dendro 的 `cambium.commit_log` 目前走父链回溯。
2. **merge 语义三档 + squash**（dolt `--ff/--no-ff/--ff-only`；terminusdb `api_squash.pl` 压层链减树深）。
3. **pack 克隆**（terminusdb：层链打包单文件传输）——dendro 的 `backup` 可演进为"按引用闭包打包"的 clone 语义。
4. **reflog**（dolt journal 内存 ring buffer 5000 条 + `dolt_reflog`）：误删分支的产品化出口，dendro 的 manifest 版本史可直接承载。
5. **feature version 写进根对象**（dolt `root_val.go:52-56`）：格式演进护栏，dendro manifest 已有 `format_version`，注意保持与 refs 同版本化。
6. **working/staged/head 三根**：git 语义完整化（staging area），dendro 目前 commit 即全部——可按需评估。
7. **doltgresql 方言适配层**：单仓两方言（系统表 hook 改名、过程注册为函数）——dendro 的 pgwire/mywire 双协议 + 系统视图（`cambium.*`）可直接套用此模式统一维护。

### F. 元数据与验证细节

- **endb：manifest 的 JSON merge patch diff 即 WAL 记录**——恢复 = 快照+重放 patch，审计 = 逐 tx 可读 diff，人类可调试；md diff 极小使事务元数据开销与数据量解耦。
- **layerfs：哈希域分离**（对象/内容/inode 独立域，`digest.rs:5-7`）防跨类型哈希混淆、v1→v2 换域作废旧身份；**CDC 冻结 profile**（分块参数哈希进 GEAR 表）防升级后边界漂移导致去重失效——dendro 的 splitter salt 已按层分离，可再加"版本域"。
- **layerfs：stage 表两阶段发布**——昂贵准入（数据对象写入）与廉价发布（head CAS）拆成两个故障域，中间状态可恢复。dendro 的"WAL 段已传、manifest 未推进"窗口等价。
- **endb：本地盘只是对象存储缓存层 + sha1 读校验 + 近似 LRU buffer pool**——dendro 的 CachedObjStore + put-id 可对照补强"读校验"。
- **nebari：by-id / by-sequence 双根**（`tree/versioned.rs:44-61`）——seq 游标天然支持增量同步/复制，dendro 的分支 WAL seq 已有等价物，只差"按 seq 拉取增量"的对外接口。

## 五、优先级建议

| 级别 | 事项 | 参考实现 |
|---|---|---|
| P0 | 冲突落库（Artifacts + MergeState + resolve/abort） | dolt |
| P0 | GC 边界协议审计（停顿写者复活窗口）+ fizzbee 式协议形式化 | slatedb RFC 0026 / specs/fizzbee |
