## 0. 总体结论（TL;DR）

**架构方向正确、工程纪律良好、v1 原型质量高于平均；但存在 3 个 P0 级正确性缺陷、系统性的"fencing 安全语义夸大"、测试面与代码雄心严重不匹配（执行器深水区零覆盖）、无任何 CI。** 现状定位：**单机（单写者）数据库原型 + 多节点方向的纸面路线图**，不是云原生多节点系统。README 的 M0–M7 声明基本可对上证据，但基准数字与仓库 JSON 互相矛盾，需要整改证据链。

**按严重度排序的三大问题**：

1. **[P0·数据丢失+挂死] WAL flush 失败即永久丢帧，且等待者死循环**（详见 §5.1）
2. **[P0·损坏即崩溃] 恢复路径对坏数据直接 panic**，CRC 校验形同虚设（§5.2）
3. **[P0·安全语义虚标] P1 fencing 的"运行时拒写/TTL 门控/续期"不存在**，三处文档/注释声称已实现（§4.1）

## 1. 架构设计评审

### 1.1 总体判断：分层架构合理，选型有据

"PG 优先双协议薄适配 → 内存 OCC → group-commit WAL 直写 OSS → prolly tree 版本化 → CBF 列存 AP"这条主线，每一段都有明确的工业先例并如实引用（dolt / slatedb / HANA / Aurora），且与"Agent 沙箱"目标自洽（分支 O(1) + 行级冲突 merge 正是 Agent 工作流需要的原语）。**这个总体架构没有原则性问题。**

做得好的具体点：

- **依赖倒置方向正确**：dendro-columnar 依赖 dendro-core 并实现 core 定义的 `ColumnarStore`/`ApScan` trait（`engine.rs:195-236`），core 不依赖 columnar，无环。
- **OSS 语义认真对待了**：条件写（S3 `PutMode::Create` + `S3ConditionalPut::ETagMatch`，`objstore/s3.rs:57,175-178`）、`ObjError::Uncertain` 的 manifest 消解（`manifest.rs:156-182`，payload 内嵌 putid + GET 反查，实现正确）、epoch 化 WAL 段路径——这三件是多数"把存储搬上 S3"的项目会漏的，这里都做了。
- **格式设计有冗余校验**：WAL 24B 帧头 crc32c + 段尾 32B trailer、CBF footer CRC、prolly 节点 CRC。
- **代码注释诚实度高**：chunker 自述 v1 是"路径复制+溢出重分裂"而非严格 prolly（`chunker.rs:1-7`）、fence 的"诚实边界"段落（`fence.rs:15-17`）——这种注释纪律值得保持。

### 1.2 架构层面的问题

**A1. "向量化列式执行器"名不副实。** SPEC 00 §2 架构图写"向量化列式执行器 (Arrow RecordBatch) scan→filter→project→agg"，实际 `sql/scan.rs`（1436 行）是**行式解释器**：全程物化 `Vec<Vec<SqlValue>>`，AP 路径读 CBF 得到 Arrow batch 后又立即行化（`scan.rs:616-648` `rows_from_batches`），向量化只发生在最终输出边界。这是 SPEC 与实现的最大单点偏差，直接削弱 G4（GPU 路径）与 AP 性能声明的根基。**要么修 SPEC 措辞（v1=行式解释器），要么把 AP 执行器列入明确的 v2 任务，不能维持现状的表述。**

**A2. 提交路径实际是"每分支一把大锁串行 + 锁内等 S3"。** memtx 64-shard 细粒度锁只覆盖读写路径；`commit_tx`（`engine.rs:864-893`）在 `Branch.commit_mu` 内完成验证+安装+WAL append，`Durability::Group/Always` 时**锁内等待 flush durable**。S3 后端下单分支提交吞吐 ≈ 1/(flush 延迟)，这是全引擎最粗的串行点。对"单写者/分支"的设计语义这是可接受的 v1 取舍，但与 SPEC 00 §6"锁粒度：memtx 分 shard"给人的印象不符，且 bench 的 157k txn/s 是 `NoWait`+内存库数字，掩盖了这一点。

**A3. 读路径并非"零锁"。** SPEC 00 §6 红线写"读路径零锁(原子快照指针)"，实际 memtx 点查每次取 shard 读锁（`memtx.rs:56`，注释自己也承认 `memtx.rs:9`）；`NodeStore` 节点缓存是单把 Mutex 包整个 HashMap（`prolly/store.rs:13`），每次 `get_node` 过锁、淘汰策略"超容量清一半"（`store.rs:62-67`）。热扫描路径上这是真实争用点。

**A4. SPEC 00 §6 性能红线有已违反项**：`Node.key(i)` 每次调用分配新 `Vec<u8>`（`node.rs:156-160`），`lower_bound` 二分中 O(log n) 次堆分配——同时违反"序列化零拷贝优先"与"禁止热路径每行 alloc"两条红线。这与号称为零拷贝布局的 `node.rs:11` 注释矛盾。

**A5. 分层是名义纪律而非强制**：`wal.rs:217,284,302-307` 使用 `engine::Durability`（下层依赖上层类型）、sql↔engine 互相引用、recovery 实为 engine 层逻辑。单 crate 内可接受，但 lib.rs 顶部"单向分层"的声明建议改为"单向分层（类型例外：wal 引用 Durability）"之类，避免误导。

**A6. append-only 的两大必然产物未处理**：
- **无任何 GC**：旧 commit chunk、旧树节点、旧 manifest 版本永久保留，WAL 段从不删除；`ManifestStore::retained()`（`manifest.rs:185-188`）是死代码，从未被调用。SPEC 00 术语表里有"GC 水位"概念，实现为零。存储无限增长。
- **time travel 没有查询面**：无 `AS OF` / `FOR SYSTEM_TIME`（`TableFactor::Table` 的 version 字段被硬编码忽略，`scan.rs:377`）。数据层（不可变 chunk+父链）保留了可能性，但"全历史可查"（README 特性第 3 条）目前只有 `commit_log` 伪表。
- 恢复成本随库龄线性增长：`replay_branch` 对 epoch 1..=max_epoch 全历史段从 seg 1 探测回放（`recovery.rs:50-53`）。

**A7. 只读打开模式缺失**：`engine.rs:branch()` 对**任何**打开（含纯读）都领取新 epoch 并启动 WAL writer 线程。所谓"读副本"每次打开都制造新写者世代与空 epoch 目录，污染 epoch 序列。设计文档 §7 差距清单 #4（只读打开）确实该做——它同时是 P0 读副本路线的前置。

## 3. 测试机制评审

### 3.1 现状清点

169 个测试函数（80 内联单测 + 89 集成），分布：pgwire 71、mywire 39、core 41、columnar 13、server 5。slt 7 文件共 **303 行 / 76 条语句**。两个"名义通过"：`s3_cloud.rs` 2 个云原生测试未设 `DENDRO_S3=1` 时直接 return 跳过；SLT 不归 `cargo test` 管。**无任何 CI**（无 .github/、无 workflows、无 pre-commit、无 rust-toolchain/clippy/rustfmt 配置——AGENTS.md 自述属实）。

### 3.2 结构性失衡："宽协议、窄引擎"

wire 协议测试占 65% 且质量高（真客户端对拍、错误码、边界包）；而风险最高的引擎深水区覆盖极薄：

1. **JOIN 实现了但零测试**：`hash_join`/`hash_join_left`（`scan.rs:887` 起）全仓库 tests/ 与 .slt 中 grep "JOIN" 为 **0 条**。执行器里最复杂的路径无任何红线保护——**这是测试体系最刺眼的单洞**。
2. **slt 基线是冒烟级**：303 行自写语料 vs 参考库 `sqllogictest-corpus` 624 文件 4490 万行、PG 回归 224 个 .sql。"7/7 全绿"的含金量极低，每文件十余条 happy-path 语句。BASELINE.md 诚实写了"corpus 接入 v2"，但对外表述（README 状态表）未反映这个差距。
3. **无并发测试**：OCC 唯一冲突用例是同线程顺序交替（`kv.rs:114`）；无多线程 SQL 压力、无多进程并发写。memtx/wal/manifest 的并发正确性基本裸奔。
4. **崩溃一致性全靠 `drop(db)` 模拟**：无真 SIGKILL/子进程杀、无 WAL torn-frame/坏 CRC 构造测试（错误路径代码存在但从未被触发过）、无 manifest 半写、无 S3 5xx/Uncertain 注入。**且坏数据路径目前是 panic 而非报错（§5.2），一构造就会暴露。**
5. **fencing 安全性质未按声明验证**：`multi_node.rs:3` 文件头声称"旧实例的写被拒绝（fencing 生效）"，两个测试体内**均无此断言**（A 总在 B open 前 drop；测试 2 只断言 `e_b > e_a`，且因 `acquire` 不等待 TTL（`fence.rs:76-93`），注释"B 需等租约过期"也不成立）。测试还残留 `[dbg]` println 调试输出（`multi_node.rs:29-33`）。
6. GRAMMAR.md 15✅/29⬜，引用的 `tests/differential/` **不存在**；`WITH` 勾选与代码不符（静默丢弃）；`CHECKPOINT` 标 ⬜ 但实际支持（勾选过期反向）。
7. 无升级/格式版本兼容测试、无长时/内存增长测试、无随机/模糊 SQL 测试。

## 4. 文档诚信问题（需要修正表述，不是补代码）

这是本轮评审的**核心发现之一**：P1 fencing 的安全语义被三处协同夸大，读者会以为已有运行时互斥，实际只有"epoch 路径隔离 + 恢复期重放抑制"（被动 fencing）：

| 位置 | 声称 | 事实 |
|------|------|------|
| `docs/design/多节点memtx一致性.md` §3.1④/§3.3 | "X 的写被 fence 校验拒绝/事务返回 40001"、"TTL 过期是接管的前提" | `commit_tx`（`engine.rs:864-889`）无任何租约/epoch 校验；`acquire()` 从不等待旧租约过期，接管即时，脑裂下双活跃写者可并存 |
| `objstore/fence.rs:9-13` 模块注释 | "持有者周期性续期；commit 前的本地过期检查 + 后台续期线程" | `renew()` 全仓库零调用、`expired()` 只有测试调用、无续期线程 |
| `tests/multi_node.rs:3` 文件头 | "旧实例的写被拒绝（fencing 生效）" | 测试体内无此断言 |

同样的模式还有：`engine.rs:657-661` 注释说旧段"保守起见延后"删除、代码却**立即** `obj.delete(&p)`——此刻崩溃，**已发布的旧 manifest 引用的段已被删**，AP 扫描将 NotFound（TP 不受影响）；benches 自述含"OSS 延迟注入"实际没有。**建议把"fence 运行时校验 + 续期线程 + 接管等待 TTL"列为 P1 收尾硬项，在此之前先改文档措辞。** 项目大量注释是诚实的（chunker、fence 诚实边界），这几处夸大更显得刺眼，应统一清理。

## 5. 遗漏任务清单（按优先级）

### P0 — 正确性（建议立即修，均已复核）

1. **WAL flush 失败处理**（`wal.rs:329-353, 311-326, 366-378`）：`flush_now` `mem::take` 缓冲后 put 失败 → **帧永久丢失**（`flush_loop` 仅 log error，`wal.rs:374-376`）；随后 `await_durable` 超时重试 `flush_now` 时缓冲已空返回 Ok → `durable_seq` 永不推进 → **已 ack 的 Group/Always 提交线程永久挂起**。一次 S3 瞬时故障 = 丢数据 + 挂死。修法：put 失败时帧回退缓冲（或上传前保留副本 + 重试/退避），durable 语义与缓冲解耦。
2. **恢复路径损坏安全**：`wal.rs:201` 先 `&d[HEADER_LEN..HEADER_LEN+len]` 切片后校验 CRC——坏 len/截断段直接 panic，CRC 形同虚设；`format/row.rs:230-259` `decode_row` 定宽字段（BOOL/I32/I64/F64/DATE/TS）无长度守卫，截断行 panic，而 decode_row 被 WAL 回放/树扫描/CBF overlay 多处调用。修法：所有解析对不可信输入返回 Err 而非 panic，并补对应坏数据测试。
3. **列存全量重建的删除时序**（`engine.rs:651-662`）：旧段删除必须在新 manifest 发布**之后**（且最好由 GC 延迟执行），否则崩溃窗口内旧 manifest 指向已删段。

### P1 — 设计完整性 / 半成品收尾

4. fencing 收尾：`renew`/`expired` 接入（续期线程 + commit 前过期检查），或明确降级为纯被动 fencing 并修订全部文档（§4）。
5. 只读打开模式（不领 epoch、不起 WAL writer）——读副本路线前置。
6. GC：`ManifestStore::retained()` 接入 + 对象/WAL 段/manifest 版本回收；否则"只写库会很大"（立项硬性要求 6）没有闭环。
7. time travel SQL 入口（`AS OF`），兑现"全历史可查"。
8. journal/consensus 决策落地：修订选型文档的自相矛盾，或实现 entries 持久化再谈接入；当前骨架建议挂 `#[cfg(any())]` 或标注 experimental，避免读者误以为可用。
9. `/metrics` `/readyz`（负载自感知文档 M1/M2 自评"可立即做"却零代码）——k8s 探针也依赖它；顺带修 Dockerfile（EXPOSE 漏 6380、无 HEALTHCHECK、无非 root USER、部署 yaml 不在仓库）。

### P2 — 质量 / 证据链

## 6. 设计预期能否达成（SPEC 00 G1–G7 逐项）

| 目标 | 判定 | 依据 |
|------|------|------|
| G1 协议分离、PG 优先 | ✅ **达成** | 双 wire 共用 AST/执行器；pgwire 71 测试最扎实；真客户端对拍 |
| G2 只写+版本化、O(1) 分支、行级 merge | ✅ **基本达成** | O(1) 建分支与 merge 冲突检测实测在；保留 criss-cross 假冲突与 time travel 无查询面两个尾巴 |
| G3 云原生 WAL+列存落 OSS | 🟡 **单机达成** | RustFS 端到端验证可信（条件写/恢复/增量段/读缓存），但"计算节点无状态、多节点共享"只有 P1 半套（无续期、无运行时拒写、无只读模式），多写者安全问题未闭环 |
| G4 列存为 GPU 保留机制 | 🟡 **格式达成、路径未达成** | CBF 格式（64B 对齐、codec 分层、zone map）在且有测试；但 AP 执行器是行式解释器（§1.2 A1），GPU 解码零实现零验证——"保留机制"目前只是承诺 |
| G5 SQL 一等公民+基线 | 🟡 **弱达成** | slt 7 文件 303 行是冒烟级；GRAMMAR 29/44 首关键词未支持；JOIN 零测试；WITH 静默丢弃 |
| G6 压缩必须+量化衰退 | 🟡 **部分** | 原型+bench_cbf（RUNS=3 取中位，方法学反而是全仓库最好的）有；但 SPEC 08 承诺的 benches/compression/ 目录、Q 曲线、"持续测量"的重复入口不存在 |
| G7 性能绝对优先 | 🟡 **部分** | 热路径确无 Rc/RefCell（红线 3 落实）、unsafe 零；但 §6 自定红线有违反（A3/A4），行式物化执行器与"内存池"未落地 |

**结论：G1/G2 达成，G3-G7 均为"机制在、深度不足"或"SPEC 写了、实现没跟上"。** 这对 v1 原型是正常状态，问题不在差距本身，而在文档多处把"设计意图"表述成"已有能力"（§4）。
