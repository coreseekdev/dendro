### 2.2 委托点 b：冻结根的边界——冻结为真，但事务面三个洞（R8-1/R8-2/R8-3）

**R8-1（P1）显式事务不读自己的写——探针实锤：**

```
BEGIN; INSERT INTO t VALUES (2,'b'); SELECT id FROM t ORDER BY id
→ 实得 ["1"]（PG 期望 ["1","2"]）
BEGIN; DELETE FROM t WHERE id=1   → DELETE 1（报告成功）
UPDATE t SET v='z' WHERE id=1     → UPDATE 1（PG 应为 UPDATE 0）
COMMIT                            → 表内残留 (1,'z')——被删行复活
```

- 根因：SQL 读路径（`table_scan`/`build_point_view`/JOIN/UPDATE/DELETE 的目标行扫描）全部只读 memtx+树，从不合并 `sess.txn.writes`。`Txn::local_get`（`memtx.rs:191`，带注释"读取时写集优先"）**仅被 KV 层调用（kv.rs:113）**——同一仓库里 KV 语义读自己的写、SQL 语义不读，接口存在而未接线。
- 隐式语句不受影响（语句末即 install，下一条语句新快照可见）；**显式事务内**（产品叙事的核心用户 AI Agent 长事务编排）一切"写后读"失真，且 DELETE+UPDATE 组合产生**静默行复活**（两条语句都报成功，数据结局与两者都不符）。
- 修法方向：读路径在 overlay 归并前并入 `txn.local_get`（写集按 table_id 索引后键级覆盖，BTreeMap 已按 `(table_id, key)` 有序）；或显式事务写语句即时安装为对本人可见的未提交版本（需要 abort 时回滚安装，复杂度高不推荐）。回归：`BEGIN; INSERT; SELECT`、`BEGIN; DELETE; UPDATE; SELECT`、`BEGIN; INSERT; UPDATE 同键` 三组合。

**R8-2（P2）显式事务内 DDL 立即生效、ROLLBACK 不撤销，且行为随"BEGIN 时库是否已有 commit"漂移——探针实锤：**

- `BEGIN; CREATE TABLE c1` → head 立即推进 + WAL Checkpoint 帧 + manifest CAS（`ddl.rs:63-93` 完全绕过事务缓冲）；`ROLLBACK` 后 `SELECT * FROM c1` 正常（表存活）——非事务性 DDL，PG 不符。
- 同事务内后续 SELECT 的可见性取决于 `head_root` 是否为 Some：fresh 库（BEGIN 时无任何 commit，`head_root=None`）冻结静默失效（`scan.rs:816-819` 的 `None => resolve_table(当前 head)`），看得见新表；已有 commit 的库冻结生效，同一语句序列报 `42P01`。**同一 API、两种结果**。
- TRUNCATE 同病（`ddl.rs:273-302`）：数据 tombstone 留在事务缓冲，`catalog_commit`（head 前移 + row_count=0 发布）立即生效，ROLLBACK 撤不掉目录变更。
- 修法方向（一行级）：显式事务内 CREATE/DROP/ALTER/TRUNCATE/CHECKPOINT/MERGE/CREATE BRANCH 一律 `25001`（PG 对事务内部分 DDL 的兼容口径之外，宁可拒绝不可半生效）；或按 PG 真语义把 DDL 进 catalog 写集——后者是大工程，v1 拒绝即可，SPEC 04 注明"DDL 为隐式提交"。

**R8-3（P2）BEGIN 后 USE BRANCH 不设防——"读冻结在 A、写提交到 B"：**

- `USE BRANCH`（`sql/mod.rs:245-251`）只改 `sess.branch`，无事务检查。探针：BEGIN@main（冻结 main 根 + main watermark）→ USE b2 → `SELECT` 读到的是 **main 的树**（b2 树里 checkpoint 过的行不可见）+ **b2 的 memtx overlay**（按 main 的 watermark 过滤）；写语句解析当前 head（b2），COMMIT 走 `commit_tx(db, &sess.branch)` 落 **b2**，validate_only 用 **b2 的 memtx latest_ts 对比 main 的 watermark**——跨分支比较，冲突检测失去意义。
- 修法一行：`sess.txn.is_some() && explicit` → 拒绝 USE BRANCH（25001）；DROP/CREATE/MERGE BRANCH 同理（R8-2 的拒绝清单内）。

冻结机制本身的评价：R7-3 把"同事务内可见性随 checkpoint 翻转"这个**最锋利**的角修掉了，回归为真；剩余三个洞都是"事务"这个概念在引擎里只覆盖了数据写集、不覆盖 DDL/会话状态的系统性残留——建议以"显式事务 = 数据写集 + 冻结读"为 v1 明确边界写进 SPEC 04，并在此边界内把 R8-1 修掉、R8-2/R8-3 拒绝掉。

### 2.3 委托点 c：update_manifest 守卫覆盖面——✅ 无绕过路径

- **全部 8 个调用点**过咽喉（清单见 §1 表）；数据写路径不经 update_manifest，由 `fence_gate` 首查 `read_only`（`engine.rs:214-216`，先于毒化检查与租约续期）拦截。
- **fence renew**：RO 分支是占位租约（expires_at_ms=0），fence_gate 在 renew 之前已返回；RO writer `stop=true` 且无 flush 线程（`wal.rs:315-348`），无保活路径——RO 进程对存储**零写**（除读缓存目录）。
- **gc_sweep 只读空操作**：`engine.rs:1066-1068` 显式早退 `Ok(0)`，探针 P8-4 实锤（RO 实例 `gc_sweep() == Ok(0)`）——R7-2 修复不会把 RO 副本的 gc 变成报错源。
- **backup 不经此路径**（纯文件拷贝，第五轮已定案）；`Database::open` 打库 gc_sweep 对 RO 同样早退。
- 结论：25006 单一咽喉 + fence_gate 双层覆盖**完备**。P1-1（RO 不领 epoch/不起 writer）+ R7-2（咽喉守卫）+ 本轮复核，只读副本的"零写承诺"如今可以画成完整闭环。

### 2.4 委托点 d：009 语料在 runner 下的实际执行路径——✅，一个时序巧合

- runner（`crates/slt/src/main.rs`）每文件独立内存库 + 单 Session，`run()` 直接 `sess.exec(sql)` → `exec_batch` → `branch_sql_kind("CHECKPOINT")` → `db.checkpoint_branch(sess.branch)`——**CHECKPOINT 语句真实走完整 checkpoint 管线**（commit_mu + fence_gate + pending 物化 + 树提交 + manifest 发布），不是 stub、不是被 runner 吞掉。三次变异全红即最硬的执行证据（若 CHECKPOINT 未真实执行，归并缺陷不会被 009 暴露）。
- **观察（P3）**：回应所说"runner 关闭自动 checkpoint 的口子由显式 CHECKPOINT 堵上"，实现上是**时序巧合而非配置保证**——`DbOptions::memory()` 保留默认 `checkpoint_interval_s=30`/`threshold=16MB`，runner 并未置 0；语料不中途 auto-checkpoint 只因"跑得快 + 数据小"。极慢 CI 上单文件超 30 秒且 pending 超阈值时理论上可出现文件中途自动 checkpoint。建议 runner 显式 `checkpoint_interval_s: 0`，把巧合变成配置（一行）。

### 2.5 委托点 e：墓碑感知 dup check × OCC validate_only——✅ 一致；顺藤摸出 R8-4

- **P8-3a（委托核心问题）**：键在 BEGIN 前已被删（可见墓碑），显式事务内重插 → 语句期 dup check 放行（`ddl.rs:417`）→ **COMMIT Ok**：validate_only 的 `latest_ts(=墓碑 ts) <= snapshot`（`memtx.rs:215-223`）不误判 40001。三态矩阵（删后同事务重插 / 删后他人重插 / 删并 checkpoint 后重插）均正确。
- **P8-3b**：无 checkpoint 介入时，同键并发写正确 40001（first-committer-wins 生效）。
- **R8-4（P2）OCC 冲突检测窗口止于 checkpoint——探针实锤**：

```
s2: BEGIN（snapshot=S）; UPDATE id=1（写集缓冲）
s1: UPDATE id=1 → 提交 ts=T（T>S，安装进 memtx）
    CHECKPOINT（覆盖 T → truncate_to 把 id=1 从 memtx 整键释放；树无版本时间戳）
s2: COMMIT → validate_only 读 latest_ts=None → 无冲突 → Ok
    终值 = 'from-s2'，s1 的已提交更新静默丢失（无 40001）
```

  根因：OCC 冲突检测的唯一依据是 memtx `latest_ts`，而 checkpoint 的 `truncate_to`（`memtx.rs:96-118`）会把"最新版本 ≤ ckpt_seq"的键整体移除，prolly 树不存版本时间戳——**任何与快照的偏离只要被一次 checkpoint 物化，就退出冲突检测视野**。checkpoint 每 30s/16MB 必然发生，长事务（>checkpoint 间隔）的写写冲突从"报错"退化为"静默 last-writer-wins"。这与读侧 R7-3 修复共享同一事实：**引擎的 MVCC 只在 memtx 窗口内存在**。
  修法方向：truncate 不释放"仍被活跃事务快照引用"的版本（按全部活跃 txn 的最老 snapshot 截断，而非按 ckpt_seq）——窗口从"上次 checkpoint"放宽到"最老活跃事务"；或 SPEC 04 诚实修订："first-committer-wins 保证限于 checkpoint 窗口内的写写冲突"。前者是正确修法，后者是诚实降级，二选一必须做其一。
- **P8-3c（P3）**：同一显式事务内两次 INSERT 同键不报 23505（dup check 不查事务写集，`Txn::put` BTreeMap 后写覆盖前写，最终单行）——PG 报错；修法是在 insert_row 的存在性检查里加 `txn.local_get`（与 R8-1 同一处接线，可顺带修复）。

## 4. 新增缺陷与工程问题清单（本轮发现）

### P1（事务语义 / 可观测性）

1. **R8-1 显式事务不读自己的写（§2.2，探针实锤）**：读路径不合并 `sess.txn.writes`；DELETE+UPDATE 同事务复合成"行复活且两条语句都报成功"。`Txn::local_get` 死接线（仅 kv.rs:113 使用）。修法 = 把 local_get 接进 table_scan/点查/dup check 三处 + 三组合回归。
2. **R8-5 服务端日志静默丢弃（§6.1）**：17 处 `tracing::` 调用遍布 9 个文件（WAL flush 失败、毒化、续期失败、auto-checkpoint 失败 "pending retained"、gc sweep 失败、accept 失败……），全库无任何 subscriber 初始化——生产环境零服务端日志。40003/58030 到达客户端时服务端无痕迹可查。修法 = main.rs 装 fmt subscriber + `RUST_LOG`（一行依赖 + 三行初始化）。

### P2（语义边界 / 运维）

3. **R8-2 显式事务内 DDL 立即生效且 ROLLBACK 不撤销；可见性行为随 BEGIN 时库状态漂移（§2.2）**：拒绝清单（25001）一行级修复。
4. **R8-3 BEGIN 后 USE BRANCH 不设防（§2.2）**：读冻结在旧分支/写提交到新分支/OCC 跨分支比较。一行守卫。
5. **R8-4 OCC 冲突检测窗口止于 checkpoint（§2.5，探针实锤）**：checkpoint 介入后写写冲突静默 last-writer-wins。按最老活跃快照截断（正确）或 SPEC 04 边界修订（诚实），二选一。
6. **R8-6 serve 无优雅关闭 + 监听器失败暴露顺序错误（§6.2）**：无 SIGTERM/SIGINT 处理、无 drain/checkpoint-then-close；main join 顺序 metrics→pg→my→kv 使 **pg bind 失败（端口占用）时进程照常打印 "dendro ready"、/readyz 正常、PG 无人监听且永不退出**（main.rs:220-231）。修法：bind 全部前置到 spawn 之前、任一失败即退出非零；优雅关闭入册（SIGTERM → 停 accept → drain → checkpoint → close）。

## 6. 全新扫描：运行与运维面（本轮委托扩权项，首次覆盖）

### 6.1 日志与可观测：有骨架、无血液（P1，见 R8-5）

- **全部服务端日志为零输出**：`tracing::warn!/error!/info!` 共 17 处（engine.rs 5、wal.rs 4、metrics.rs 2、pgwire 3、mywire 2、kv_resp 2、columnar 2+），无任何 subscriber。第七轮自豪的 `dendro_branch_poisoned` gauge 与 /metrics 面板是"事后告警"通道；**事件发生当下的服务端叙述（哪次 PUT 失败、哪个分支为何毒化、checkpoint 为何 retained）完全丢失**。对一个以"fencing/毒化/reopen"为卖点的系统，毒化事件无日志等于故障排查靠猜。
- M-5（metrics 直方图 + 慢查询日志）连续七轮未动——弹性调度故事（"据 /metrics 扩缩容"）缺日志半边、缺延迟分布另一半。
- 既有可观测资产复核为真：/readyz（过期写者 → 503）、/metrics 六指标族（HELP/TYPE 单次、RO 分支 TTL 巨负数已防护）、`active_branches()` 零懒加载承诺——骨架是对的，差的只是 subscriber 与直方图。

### 6.2 进程生命周期：无关闭语义（P2，见 R8-6）

- 无 SIGTERM/SIGINT 处理（无 signal 相关代码；tokio "signal" feature 开了没用）；无 `Database::close()`——`stop_cp` 死字段（Q-7）就是当年没做完的 close 收口。k8s 滚动更新 = 硬杀：Group/Always 的已 ack 提交持久（无数据丢失，WAL 重放恢复），NoWait 尾部丢失是已文档化契约；**缺的是 drain 与租约/写者的即时让位**（重启实例要等旧进程的 30s lease TTL 过期或走 fence epoch 接管——后者已实现，可接受但粗）。
- **监听器失败暴露顺序 bug**：四个监听器 spawn 后按 metrics→pg→my→kv join；metrics 永不返回 ⇒ 后续 join 永远轮不到。pg bind 失败（端口占用/权限）时：panic 发生在子线程（被 `expect` 触发），主线程照常打印 "dendro ready"、/readyz 200、PG 端口无人听——**编排层看到一个永远健康但永不提供 PG 服务的实例**。修法：全部 bind 在 spawn 前完成（顺序声明依赖），任一失败立即退出非零。
- Dockerfile 有 HEALTHCHECK（/readyz）✅、无 STOPSIGNAL（默认 SIGTERM，配合 R8-6 无 handler 即硬杀）。

### 6.3 备份恢复演练：本地形态完整，云上形态缺席（P2/P3，见 R8-8）

- 已有资产复核为真：backup 原子写 + 截断修复 + 非 dendro 目录拒绝 + roundtrip/截断/拒绝三测试（`dendro-server/tests/backup.rs`）；"先拷数据后拷 manifest"的一致性论证成立（append-only + manifest 最后拷）。
- 缺口：**备份工具只认 std::fs 本地路径**——主部署形态（S3/OSS）没有 `dendro backup`；无 `restore`/`verify` 子命令（恢复=手工拷回+打开，验证=人肉）；M-1 的"不停机备份"手册语义仅对 local 后端成立。云原生数据库的备份故事按当前状态只能打"本地开发形态"分。

### 6.4 升级场景：manifest 半边有守卫，其余靠自律（P3，见 R8-8）

- manifest `format_version > 1` 显式拒绝（M-2，含测试）✅；WAL 帧有 magic+version 检查（`wal.rs:189-196`）✅——**读侧守卫齐全**。
- 缺：新读旧/旧读新的**回归矩阵**（M-2 的尾巴：升版字段后的兼容测试）；数据根目录无 layout/engine 版本戳（降级打开无守卫）；`--cache-dir` 静默无效（main.rs:115）是升级/部署文档最容易踩的"设了没用"陷阱。
- 其余核查项（无缺陷记录）：pgwire CancelRequest 直接关连接（`startup.rs:60`，无查询取消——配合 Q-1 全物化，失控查询只能等/杀连接，S-3 同族）；kv_resp 硬编码 main 分支（main.rs:178，文档未提）；thread-per-connection 无上界（S-3 既有）；连接线程 panic 无 catch_unwind（default hook 打 stderr，可接受）。
