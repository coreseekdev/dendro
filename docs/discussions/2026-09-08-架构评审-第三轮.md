## 2. 新代码逐行审查——两个新 P0

### P0-A【并发丢帧，已实证】并发的 flush_now 用同一段号互相覆盖，`Always` 已 ack 的帧被静默丢失

- 位置：`wal.rs:377-415`（`flush_now`）、`:324-349`（`append` 的 Always/Group-超时路径都会调 `flush_now`）、`:428-441`（flush_loop 也调）
- 机制：`flush_now` 在锁内 take 缓冲并读取 `g.cur_seg`（`:383`），但 `cur_seg` 要等 **PUT 成功后**才推进（`:412`，这是第二轮段号修复的正确取舍）。于是存在窗口：flush_loop 取走段 N 的缓冲正在慢速 PUT（100ms RTT 的 S3 上很常见），期间新 append 使缓冲非空，另一个 `flush_now`（Always 直发或 Group 的 `await_durable` 超时重试，`wal.rs:344-345, 359-362`）会以**同一段号 N** 再次 PUT——两个不同内容的对象写同一路径，最后写者胜，先落盘的帧全部丢失。`await_durable` 的 `durable_seq = max(...)`（`:423`）还会给被覆盖的帧**错误地 ack**。
- **实证**（评审人临时探针，已删除）：`MemoryObjStore` 包一层"第一次 put 该段路径阻塞 400ms"，帧 1 NoWait 入缓冲由 flush_loop 上传（慢），60ms 后帧 2 以 `Always` append——最终段对象里**只剩帧 1，帧 2（已 ack）丢失**（期望 `[1,2]`，实际 `[1]`，测试确定性失败）。
- 修法建议：给 `WalShared` 加 `uploading: bool`（或 in-flight 段号），第二个 `flush_now` 在上传期间直接返回 `Ok(flushed_seg)`（其帧留在缓冲，由下一次 flush 带走）；PUT 期间禁止并发上传是最小修复，代价仅是 Always 提交偶尔多等一个 flush 周期。**必须补并发回归测试**（注入慢 PUT + 并发 Always append）——这正是 TASK P1-7（多线程测试 ⬜）缺位的直接代价。
- 备注：注释 `:373` 自述的"Uncertain 语义：同路径重试 PUT 覆盖写，内容为超集"这一前提，被并发路径破坏（两个 PUT 互不为超集）。

### P0-B【checkpoint 失败丢已提交数据】pending 被 take 后不可回滚，失败越过 covered_seq 后永久丢失

- 位置：`engine.rs:777` `std::mem::take(&mut *b.pending.lock())`；`:796-831` 树物化循环（`apply_table_mutations`/`apply_catalog` 内部含 `cas.put_batch` 的**远端写**）、`:844` commit chunk 上传——任何一步 S3 失败都会在 `head.store`（`:845`）之前 `return Err`，**已取走的 pending 直接被 drop**。
- 后果链：这些行已通过 `commit_tx` ack（Group durable、WAL 已落）。① 进程内：下次成功 checkpoint 的树根不含它们，而 `truncate_all(covered)`（`:897`）把 memtx 历史清掉 → 读不到；② 重启后：`recovery.rs:66` 只回放 `ts > covered_seq` 的帧，而下次成功 checkpoint 已把 `covered_seq` 推过这些 ts → **ack 过的事务永久丢失**。列存路径同样依赖 pending/memtx，不豁免。
- 触发条件：checkpoint 树物化期间的 OSS 错误——在"存储主体在 OSS"的定位下这是**常规运维事件**而非罕见故障，与首轮 P0-1（flush 失败丢帧）同类。第二轮修好 flush_now 让它返回 Err 之后，这条路径从"挂死"变成了"可到达的失败"。
- 修法建议：失败路径把 take 走的 pending **合并回** `b.pending`（BTreeMap 按 key 覆盖合并即可，提交序由 commit_mu 保证）；或把 take 推迟到所有 fallible 远端写成功之后。配套：失败注入测试（对 `cas.put_batch` 注入一次错误，断言失败 checkpoint 后数据仍完整、再成功 checkpoint 后仍完整）。另注意 checkpoint 线程吞错误（`:969` `let _ = db.checkpoint_branch(&n)`），失败至少要 `tracing::error!` 并可被 /metrics 观测。

## 3. 其余新代码审查（🟡/✅）

### 3.1 fence_gate（`engine.rs:161-188`）——🟡 逻辑正确，产品语义有硬伤

- ✅ 正确性：读锁内先查本地过期（`:167`）再惰性续期（`:173-186`）；续期失败不更新本地 `lease`/`next_renew_ms` → 本地视角与远端一致，过期即拒，无"本地以为活着"的窗口；三个写入口（`commit_tx:1036`、`write_branch_commit:640`、`checkpoint_branch:709`）全覆盖。
- 🟡 **空闲写者自毒化**：续期只在 commit 路径，默认 TTL=30s（`engine.rs:89`）。任何分支 **30 秒没有提交，下一次提交即 40001，且会话内无自愈**（错误信息要求 "re-open"，server 层对此无任何处理——grep pgwire/server 无 40001 特判）。对"AI Agent 沙箱"这种间歇写入的目标负载，这是默认配置下的必然踩坑。建议：`ttl/3` 一次 PUT 的后台续期线程（成本可忽略），或 fence_gate 检测到过期时在锁内重走 `acquire(epoch+1)`+重建 WalWriter 的进程内接管路径。
- 🟡 `fence.renew`（`fence.rs:104-108`）是无条件覆盖写——当前唯一调用点在 gate 校验之后所以安全，但建议注释标明"调用者必须已验证持有该 epoch"，防止未来误用。

### 3.2 gc_sweep + 墓碑（`engine.rs:909-938`、`manifest.rs:77-81`）——🟡 方向正确，三处瑕疵

1. **删除失败仍移出墓碑清单**（`:924-931`）：`obj.delete(p).is_ok()` 失败的对象照样被 `retain` 从清单剔除 → 永久孤儿。应只移除删除成功的，失败的留在清单下轮重试（Memory/Local 语义下概率低，S3 上是真实路径）。
2. **在 commit_mu 内做最多 256 次远端 DELETE**（checkpoint_locked `:899` 调用 `gc_sweep`，持锁范围 `:708-710`）：100ms RTT 下最坏 ~25s 阻塞该分支全部提交。GC定案 §3.4"不阻塞提交路径"与实现不符。建议移出锁（checkpoint 发布后 spawn）或加时间预算。
3. 墓碑登记与"停止引用"的原子性（`:881-894`）**正确**——登记与取消引用是同一 manifest JSON 的一次 CAS PUT，P0-3 的崩溃窗口从机制上关闭（详见 §4）。

### 3.3 recovery.rs 的 wal_first_seg（`:42-56`）——✅ 正确

- `epoch == head.epoch` 时从 `head.wal_first_seg.max(1)` 探测，旧 epoch 从 1 探测、目录整体被回收时 `probe_tail` 返回 lo-1 → 零帧回放（`wal.rs:479-481`）。前缀-only 删除保证"段号空间只有前缀空洞"，与探测语义自洽。`set_first_seg` 在 manifest 发布**之后**（`engine.rs:895`），崩溃窗口内向保守方向回退，安全。
- 一个诚实的遗留：**僵尸旧 epoch 段**——失约写者在被接管后仍可向旧 epoch 目录追加新段（其 gate 过期前），这些段不在接管者 LIST 快照里 → 不被墓碑覆盖，之后也再无回收时机（`prev_epoch != cur_epoch` 只在新 epoch 首个 checkpoint 触发一次）。泄漏非正确性问题，建议 GC 定案补一条"回收所有 epoch < 当前 epoch 的全部现存段"（每次首 checkpoint 重新 LIST，而非依赖首次快照）。

### 3.4 metrics.rs（`crates/dendro-server/src/metrics.rs`）——🟡 达标但有名不副实项

- ✅ `/metrics` 每驻留分支 5 个指标、HELP/TYPE 去重、`active_branches()` 不懒加载（`engine.rs:425-427`，注释明确"绝不懒加载"）；`metrics_endpoint.rs:57-66` 断言 pending>0、TTL>0 真实。
- 🟡 **`/readyz` 恒 200**（`:60`）：无任何健康判定（WAL durable 落后、lease 过期、manifest 可达性均未检查），对 k8s 它是 liveness 而非 readiness——一个 lease 已过期、只能拒写的实例依然"ready"接流量。至少应纳入 `lease 剩余 TTL > 0` 与 `durable_watermark 落后 watermark` 两个信号（数据都现成）。
- 🟡 只读分支的 `dendro_branch_lease_ttl_ms` 输出 `0 - now`（巨大负数，`engine.rs:479-486` 的占位 lease expires_at_ms=0），监控面板会被污染，应跳过或标记。

### 3.5 JOIN 修复（`357860a`）——✅ 且是本轮最佳工程实践

### P1-C【新】manifest 版本回收破坏乐观 CAS 的单调性前提

- 机制：`load_latest` 的探测路径在 `cached+1` NotFound 时**直接返回 cached 为最新，不回落 LIST**（`manifest.rs:139-146`；LIST 兜底只服务 `cached==0`）。而 `gc_sweep` 每次**删除 `latest-16` 以下的版本对象**（`engine.rs:935` + `manifest.rs:207-215`）。
- 后果推演：一个停滞写者（GC 停顿/网络分区，落后 ≥48 个 manifest 版本——多分支共享一个 manifest 序列时这并不夸张）醒来后：探测 `cached+1` 命中空洞 → 拿着陈旧快照去 `commit(cur=k)` → `put_if_absent(manifest/k+1)` **在空洞上成功创建** → 该写者进入一条版本号更低的**影子谱系**，其后续 `load_latest` 永远探测不到主谱系 → 它 ack 给客户端的分支头推进全部写进一个注定被 GC 删除的孤儿 manifest。CAS 靠"版本号单调 + Create 条件写"防串台，版本删除把这条地基拆了。
- 修法建议（任选其一或组合）：① `cached+1` NotFound 时以 LIST 校验一次（GC 节奏下 LIST 频率可忽略）；② `update_manifest` 提交成功后校验新版本号 > 本次读取的版本号 + 本地水位，异常即报错重开；③ 版本删除水位取"全部活跃 Database 实例 reported cached 的最小值"（进 manifest 的 GC 水位字段——`gc_last_sweep_ver` 字段已存在但**零使用**，正好用上）。配套：构造"删除中间版本 + 停滞写者醒来"的回归测试。

## 5. P2' 设计评审（`629d155`/`e3b0557`，commit pipeline 分离）

**总评：🟡 方向与 SOTA 对齐、接口切面选得对；但"seam 已留"言过其实，且有抽象层堆积风险。**

1. **`e3b0557` 名不副实**：提交信息"commit pipeline separation (adjudicate/persist/install/watermark phases)"，实际 diff 是**把评审首轮报告文件加入 git**（181 行，零设计内容）。真正的设计文档在 `629d155` 的 `docs/design/提交管线重构.md`。提交信息与内容不符属于新的失真形态（虽无害，但违反自己的 DoD 精神）。同理 `92dcb35` 信息中的 "SPEC revision" 无对应内容。
2. **代码 seam 是注释级的**：`629d155` 对 `commit_tx` 的全部代码变更 = 阶段注释标签 + 返回值 `Ok(seq)`→`Ok(ts)`。Adjudicator/Journal trait 只存在于设计文档。TASK P3-1 说"seam 已留（629d155/e3b0557）"——**现状是概念 seam，非编译期 seam**，建议表述降级或在代码里真正落 trait。
3. **SOTA 引用基本正确**：Adjudicator/Journal 术语与 Aurora DSQL 论文（SIGMOD'25）的裁决器+Quorum Log 架构对应，FoundationDB Resolver 类比成立；"Journal 物理载体 = WAL 段，消除双写"与 DSQL 的设计同构，是这份设计里最有价值的一句话。
4. **设计缺的三块（落地前必须补）**：① **读路径/快照时间戳**——裁决只解决写，多节点下读者从哪里拿 read ts、如何保证不读落后的 Journal 水位，只字未提（DSQL 用快照命中 + Quorum 租约读）；② **Adjudicator 自身的 HA 与 fencing**——独立裁决服务是新的单点，failover 时新旧裁决器的授序冲突需要 fencing/epoch（现有 fence/复合时间戳体系正好是地基，应显式接入设计）；③ **抽象收敛**——仓库现在有三套重叠抽象：`consensus/` 的 ConsensusNode/ConsensusLogStore + raft-rs 适配器（`87c9a87`，零持久化、未接线）、`journal.rs` 的 RaftJournal 骨架（`aa3a2e8`）、本设计的 Adjudicator/Journal。落地前必须宣布唯一权威接口，其余标记 experimental 或删除，否则后来者无所适从（首轮 §2 对 raft 骨架空转的意见继续有效）。
5. 顺带指出：现实现是 **install（validate_and_install）先于 WAL append**（`engine.rs:1041-1057`），WAL 失败时 memtx 已带数据、客户端却收到错误（in-doubt：`wal_corruption.rs::flush_put_failure...` 甚至把"报错行重启后出现"当作期望行为断言 `:240`）。设计文档的管线（adjudicate → journal → install）**恰好修正了这个顺序**——实施该重构时应把"install 必须在 durable 之后"作为显式验收项，并修订上述测试的语义期望。
