### reopen_branch 并发边界
三处加固：
- **每-名字打开互斥**：`branch()` 的创建段全程持有 per-name 锁（双检）——

- **只允许驱逐毒化写者**：健康写者 reopen 幂等返回（`poisoned()` 访问器
  获得第二个读者）；
- **驱逐前持旧 commit_mu** 清空在途提交。
"驱逐窗口内并发会话"的残余语义：等锁窗口内的会话拿到旧/新 writer 均按
各自 writer 语义执行（旧的按毒化失败）——这是 reopen 语义的一部分，已
在 SPEC 02 §3.5 口径内。

## 4.5 修复过程中的新发现（链式根因，均以回归固化）

实施 S-1/S-2 时，`lazy_open_and_drop_branch_gc` 暴露了一条**三层叠加的
Arc 自环链**——遗弃分支的租约保活"永生"，甚至会在 GC 删除已删分支的
fence 对象后将其**复活**（manifest 墓碑在、文件被重建，mtime 晚于 sweep
250-350ms；用 renew 回溯 + 文件 mtime 定位）：

1. **checkpoint 线程持 `Arc<Database>` 且在 upgrade 持有期内 sleep**
   （30s/轮）→ Database 在整轮 sleep 期间存活；
2. **WAL flush 线程持 `Arc<WalWriter>` 自环** → Drop 永不触发，
   遗弃分支的 writer/线程永生；
3. keepalive 经 `cfg`→closure→`LeaseKeeper` 持续续租已死分支的租约。

修复：checkpoint 线程**先 sleep 再 upgrade**（不持 Arc 睡觉）+ Weak；
flush 线程改持 `Weak<WalWriter>`（外部 Arc 全释放 ⇒ upgrade 失败退出）
+ `impl Drop for WalWriter` 置 stop 双保险。附带清理：`load_open_branches`
死方法删除；`open_rejects_corrupted_wal_segment` 因惰性打开改为"触达即
恢复"语义。这条链同时解释了 M-6（fence 对象累积）在长驻进程中的真实
严重度——它不只是"文件多"，而是伴随永生的续租 PUT 流量。
