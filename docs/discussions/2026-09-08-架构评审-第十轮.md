## 0. 总体判定（TL;DR）

第九轮的四项修复中，R9-2（事务内守卫）与 R9-5（KV 双洞）机制验真为真；但 **R9-1 与 R9-4 各自引入了一个新的 P0**，且两个 P0 都是"修复的自我伤害"：

1. **R10-1（P0，资源/性能）：`active_snaps` 只在 `Session::drop`（且事务未决时）注销——COMMIT 与 ROLLBACK 根本不注销**（`sql/mod.rs:440-459` 无任何注销调用；全库 `unregister_snapshot` 唯一调用点是 `engine.rs:1197` 的 Drop）。而 COMMIT 已经 `take()` 了事务，Drop 里 `if let Some(t)` 落空——**一个分支上只要发生过一次成功的显式事务，其快照就永久留在注册表里，checkpoint 的截断从此对该分支永久跳过**（`engine.rs:1068-1075` 的跳过条件是 `!is_empty()`）。commit 信息声称"BEGIN registers, COMMIT/ROLLBACK/Session-drop unregisters"——**前半句真、后半句假**。后果：tutorial 06 §4 与 SPEC 04 的"memtx 常驻 ≈ 两次 checkpoint 之间的写入量"（内存有界）在一切用过显式事务的分支上永久失效，memtx 无界增长。连接池里长连接跑一次 `BEGIN..COMMIT` 即触发。r9_1 回归测不到它，因为测试在 checkpoint 时事务还开着、COMMIT 后测试即结束——**又是"镜像方向零覆盖"**。
2. **R10-2（P0，装配）：R9-4 的前置 bind 把监听器装错了端口**。bind 循环按 `[metrics, pg, mysql, kv]` 顺序压入 `listeners`（`main.rs:172`），装配却按 metrics(187)→**kv(200)**→mysql(213)→**pg(235)** 的顺序 `remove(0)`——FIFO 队列与消费顺序错位。进程级实验实锤：**默认配置（kv 关闭）下 PG 与 MySQL 端口互换**——banner 声称 `pg=15442`，实际 15442 发出的是 MySQL 握手（`8.0.36-dendro`），pgwire 自己的 INFO 行承认在 23316 监听；四端口全开时 pg↔kv 再互换。**README 快速开始的 `psql ... port=5432` 在默认配置下连到的是 MySQL 协议监听器，开箱即坏**。commit 信息声称"verified end-to-end: second instance on an occupied port exits 1"——该验证只覆盖了 bind 失败路径（本轮复验确实 exit=1），没验证成功路径上"哪个端口讲哪个协议"。`main()` 装配层零测试覆盖，是这个 P0 漏网的结构性原因。

第三组发现是注册表的**数据结构选型**：`BTreeSet<u64>` 天然去重，两个会话在同一 watermark 上 BEGIN 只占一个槽位；先结束的那个（Drop 未决事务）会把它连同别人的保护一起摘除——探针端到端复现了 R9-1 的击穿（count 1→0）。加上 KV 层显式事务从未接入注册表、R9-2 守卫误伤只读的 SHOW BRANCHES、BEGIN 注册与 checkpoint 截断之间存在竞态窗口——R9-1 的机制方向正确，但交付质量不达标。

收尾扫描的结论：文档体系与实现的偏差在积累（Q-15 未动、KV 接口零 SPEC、README 状态段陈旧）；性能声明与证据的裂缝从"没补基准"升级为"内存有界承诺被 P10-1 打破"；G1–G7 中 G1 因装配 P0 回弹为 🟡。修复流程层面，"**修复引入新 P0**"的模式近五轮出现三次（R5→R6 keepalive、R8-6 假修复、本轮两处）——交付验证止于单测绿的问题没有随着轮次收敛，反而在装配层、生命周期层这两个没有测试的层反复发作。

## 2. 专项审查（委托点 a–e）

### 2.1 委托点 a：active_snaps 注册/注销的完备性——注册单点、注销缺口、去重缺陷（R10-1/R10-3）

**注册面**：唯一注册点是 SQL `BEGIN`（`sql/mod.rs:436`）。
- **KV 层 `Kv::begin` 不注册**（`kv.rs:300-309`，探针 P10-3：KV 事务活跃时 `active_snaps==0`）——委托点 a 预警的"kv 层 begin 走 Kv::begin 而非 SQL BEGIN"属实。更糟的是 KV 事务连**冻结根**都没有（`Kv::get`/`scan` 每次经 `resolve_table` 取**当前** catalog entry，`kv.rs:105-110/148-150`）——R7-3 的"overlay 按 BEGIN 快照、树按当前 head"翻转型缺陷在 KV 层原样存活：事务内他人提交的键，物化前不可见、经一次 checkpoint 后**变得可见**（探针 P10-3：`get(k2)=Some("v2")`）。而提交侧 Q-9 的 40001 却照拦（`commit_tx` 共享，`engine.rs:1253`）——**KV 显式事务：读不冻结、写照拒**，两端都不对。
- prepared `BEGIN` 经 `exec_statement(StartTransaction)` 同一注册点 ✅。

**注销面**：见 §0 第 1 条。三个缺口按危害排序：
1. COMMIT 不注销 → 永久跳过截断（P10-1，内存无界）；
2. ROLLBACK 不注销 → 同上；
3. `BTreeSet<u64>` 去重 → 同 watermark 双事务共占一槽，先结束者把后者的保护一并摘除（P10-2 端到端：s1/s2 同快照 BEGIN → drop(s1) → checkpoint → **s2 冻结读 1→0**）。需要的是 `HashMap<u64, usize>` 引用计数。

**边界细节**：
- Drop 里 `unregister_snapshot` 经 `db.branch()` 查分支——`branch()` 是**惰性打开**入口（S-1），在 Drop 路径上调用一个可能重建运行态的函数是隐患（当前仅 DROP 后分支会失败→被忽略，故未发作）；建议 Session 持有 `Arc<Branch>` 弱引用或注销走只读查找。
- **注册与截断的竞态**：BEGIN 先读 watermark、后插注册表（`sql/mod.rs:429-436`），两步之间不持 commit_mu；checkpoint 在 commit_mu 内评估 `is_empty()`（`engine.rs:1068`）。并发交错"读快照 → checkpoint 判空并截断 → 插入注册表"会复现 R9-1 本体。窗口微秒级，但 auto-checkpoint 让它成为时间彩票。修法：BEGIN 在读快照**之前**持 commit_mu（或插入占位后再取快照）。

**无界增长**：委托问"BTreeSet 无界增长（长会话泄漏）"——实际比预想严重：不是长会话才泄漏，是**每一笔已结束的显式事务都泄漏一项**（P10-1），且第一项就足以关闭全分支截断。条目本身（u64）内存可忽略，危害全在截断跳过。

### 2.2 委托点 b：三层归并 × 截断跳过 × 冻结读/读己写/并发 checkpoint 的行为矩阵

| 场景 | 判定 | 依据 |
|------|:----:|------|
| 冻结读 × 手工 checkpoint（单事务、注册无冲突） | ✅ | r9_1 回归 + 本轮复核；截断跳过后 `树@冻结根 ∪ overlay(≤快照) ∪ 自身写` 不变式恢复 |
| 读自己写 × 并发 checkpoint | ✅ | 自身写在层③（`txn.writes`），不依赖 memtx/树版本，截断与否无关 |
| 冻结读 × 同 watermark 双会话 | ❌ | P10-2：去重 + 提前摘除 → count 1→0（R9-1 借注册表自身复发） |
| 会话在 COMMIT 之后继续存活 | ❌ | P10-1：快照残留 → 该分支截断永久关闭（方向相反的破坏：不是丢数据，是丢内存上界） |
| 显式**写**事务 × 并发 checkpoint（活跃） | 🟡 | 读侧全程正确（P10-5：自身写可见、他人 BEGIN 后提交不可见）；**COMMIT 必 40001**，且错误消息失实——见 §2.3 |
| AP 列存路径（≥1 万行）× 事务 × checkpoint | ❌ | Q-14 未动（第九轮已登记）：`try_ap_scan`（`scan.rs:412-514`，`col_rows<10_000` 即旁路）仍不读写集、不认冻结根 |
| KV 事务 × checkpoint | ❌ | P10-3：未注册 + 无冻结根 → 翻型可见性 + 40001 不对称 |
| 事务内 SHOW BRANCHES（只读） | ❌ | P10-4：被 R9-2 守卫 25001 误伤 |
| auto-checkpoint 线程 × 活跃事务 | 🟡 | 与手工 checkpoint 同一 `checkpoint_locked` 路径（`engine.rs:1157-1161` 阈值触发），机制覆盖；但**并发回归仍为零**（P1-7 连续九轮 ⬜），r9_1 只有单线程手工编排版 |

### 2.3 委托点 c：R9-2 守卫的误伤面——SHOW 被误伤；USE 双路径一致；covered_min 的口径裂缝

- **SHOW BRANCHES**：守卫（`sql/mod.rs:257-264`）对 `branch_sql_kind` 的全部返回值一刀切，`Show` 也在内 → 事务内 25001（P10-4 实锤）。SHOW 只读 manifest、无副作用，应放行——一行修复：`matches!(kind, Show) => 放行`。
- **USE**：新守卫先拦（消息 "cannot execute USE BRANCH inside a transaction"），原 Q-11 分支（`sql/mod.rs:269-271`，"cannot switch branch inside a transaction"）成为**死代码**。双路径同判 25001、无冲突；prepared 路径经 `exec_prepared → exec_branch_statement` 同拦 ✅。建议顺手删除死分支。
- **CHECKPOINT 自伤链已闭合** ✅：事务内手工 CHECKPOINT/CREATE/DROP/MERGE/REOPEN 全部语句期 25001（r9_2 + 代码复核），第九轮 P9-3 的自伤 40001 不再可达。
- **但 auto-checkpoint 仍能造成同样的自伤**：`covered_min` 在**截断被跳过时照样推进**（`engine.rs:1077` 无条件 store）。P10-5：活跃写事务期间他人触发 checkpoint（截断跳过、版本全保留），事务提交仍 40001 "transaction spans a checkpoint; **conflict detection unavailable**"——而此刻版本链完整在 memtx 里，`validate_only` 完全可以精确裁决，**冲突检测是可用的**，消息与事实相反。研发注释"写冲突检测的盲区与读保留是两回事"在跳过截断的路径上不再成立：保留本身就关闭了盲区。修法（随 Q-13 一并）：`covered_min` 推进为 `min(covered, 最老活跃快照)`，保留窗口内的跨 checkpoint 事务回归普通 OCC 裁决，Q-9 的"必拒"退役为兜底。这也是第九轮评审建议的"三合一"路线中被放弃的那三分之一——本轮证据表明放弃它让机制自相矛盾。

### 2.4 委托点 d：前置 bind 的装配顺序与错误消息——消息合格，装配交换（R10-2）

- **错误消息质量 ✅**：bind 失败输出 `dendro: {name} listen {host}:{port} failed: {e}`——名字、地址、OS 原因齐备，同名/同端口冲突可定位（进程级实验亲见）。

  - 四端口全开：kv 弹到 pg 的、pg 弹到 kv 的——pg/kv 互换；
  - 仅当只开一个 SQL 协议时凑巧不换。
- 进程级实验（两实例，产物已清理）：
  | 端口 | banner 声称 | 实测协议 |
  |------|------|------|
  | 15442（默认组合） | pg | **MySQL 握手**（`8.0.36-dendro`） |
  | 23316（默认组合） | mysql | **PG**（等待 startup 包；pgwire INFO 行自认监听 23316） |

  | 16379（四端口） | kv | RESP PING 连接被关（PG 层行为） |
- ready banner（`main.rs:248-252`）按 CLI 参数拼地址，与实际监听不符——**打印的是谎话**。README 快速开始（`README.md:112`，psql→5432）在默认配置下不可用。

### 2.5 委托点 e：R9-5 KV 修复复核——扫描三层顺序与 R8-1 一致 ✅；get 与 SQL 语义一致 ✅

- **scan 三层顺序**（树 → overlay → txn 写集，`kv.rs:152-238`）与 R8-1 table_scan 的三层语义同构：每层按键唯一、后层覆盖前层；写集最后覆盖使"树/overlay 复活事务内已删键"结构性不可能（commit 信息记录测试当场抓到该序错误——正是这个抽象的正确用法）。

## 3. 新增缺陷与工程问题清单（本轮发现）

### P0

1. **R10-1 active_snaps 注销缺失 → 截断永久关闭 → memtx 无界（§2.1，探针 P10-1）**：COMMIT/ROLLBACK 不注销；一次显式事务即令分支永久跳过截断。修法 = `HashMap<u64,usize>` 引用计数 + COMMIT/ROLLBACK（含 failed_txn COMMIT 丢弃路径）注销 + Drop 兜底；回归 = "COMMIT 后再 checkpoint，memtx 截断必须发生"（白盒断言 active_snaps 空 + 行为断言）。

### P1

## 5. 架构 / 选型 / 测试 / 文档诚信

### 5.1 架构（增量）

- active_snaps 注册表**方向正确、实现三处漏**（注销、去重、竞态）——与 R8-1 的三层归并（一次做对）相比，这次交付缺了第八、九轮反复要求的"镜像方向用例"。
- 装配层 FIFO 队列是典型的"顺手抽象"错误：四个监听器是**具名资源**，用位置容器承载具名资源必然错位。结构体字段或 HashMap 才是对的选择——这与 R8-6 的"保留宾语丢主语"同型：**对机制没想清楚就动了刀**。
- 修复流程观察（连续第三轮）：R5→R6 keepalive 回归、R8-6 假修复、本轮双 P0——**"修复引入新缺陷"已发生 3/5 轮**。共性：改动所触达的层没有测试（空闲路径、默认配置装配、事务提交后生命周期）。建议把"修复必须自带其触达层的测试"写成 DoD 第 4 条。

### 5.2 技术选型（增量）

- `BTreeSet<u64>` 承载"每会话一份"的计数语义是选型错误（set 去重 vs multiset 语义）；`HashMap<u64, usize>` 或 `Vec<u64>`（线性扫描，活跃事务数很小）皆可。
- 无新外部依赖风险。std::thread + 前置 bind 的装配模式本身正确，R9-4 的方向没有错，错在数据结构。

### 5.3 测试机制

- 208 单测 + 9 slt 的防线对"已修复缺陷"依旧密实，但本轮再次证明：**它对装配层、生命周期层、默认配置完全失明**。三条具体欠账：① main::serve 装配冒烟（R10-9）；② 显式事务全生命周期（COMMIT/ROLLBACK 后的引擎状态断言）；③ 双会话同 watermark 的并发编排（可单线程模拟：先 BEGIN 再 BEGIN，不动 watermark 即同快照）。
