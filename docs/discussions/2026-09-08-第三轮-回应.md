## 1. P0 修复

### P0-A flush 并发同段号覆盖 → ✅ 已修（方案 = 评审建议的单飞互斥）

`WalWriter` 增加 `flush_mu: Mutex<()>`，`flush_now` 全程持锁（`wal.rs`）：
同一时刻至多一个上传在途；段号推进（成功后 +1）在下一个 flush 开始前完成，
同段号并发从机制上不可能。Always 提交在 `flush_mu` 上等待在途上传完成后
以新段号落盘。

**回归**：`tests/wal_corruption.rs::concurrent_flush_same_seg_never_overwrites`
——评审探针的场景原样固化（慢 PUT 400ms + 60ms 后 Always append），断言
两帧分属两段、Always 等待 ≥300ms。修复前该测试确定性红。

### P0-B checkpoint 失败丢已提交数据 → ✅ 已修 + **新发现 P0 级缺陷一处**

**修复 1（评审指出的）**：`checkpoint_locked` 拆为 take + inner，任何错误
把 pending **键覆盖合并归还**并重建 pending_bytes（commit_mu 保证无并发
写者）。若错误发生在 head.store 之后（WAL ck 帧失败），head 已前进而
manifest 未动，归还的 pending 会在下次 checkpoint 以新 head 为父重新
发布——收敛。自动 checkpoint 线程不再吞错误（`tracing::error!`，分支名
+ 错误可检索）。

**修复 2（本轮注入测试捕获的新缺陷，比评审描述更深）**：`CasStore::
put_batch` 的"每组后尽早失败"检查与 worker 实际执行存在竞态——spawn 是
异步的，检查时 worker 往往尚未运行，循环结束 scope join 后错误才写入
mutex，但返回值已定为 `Ok`。**即 put_batch 基本必然吞掉所有上传错误**：
S3 上任何 chunk 上传失败，checkpoint/merge/DDL catalog 提交都会照常发布
引用缺失 chunk 的 manifest（后续读 404 = 静默损坏）。这意味着修复 1 单独
存在时甚至无法生效——checkpoint 根本不会"失败"。修复：权威错误检查移到
scope join 之后（`cas.rs`，附注释指向回归测试）。此缺陷由
`checkpoint_failure_preserves_committed_data` 注入测试首次暴露——**先有
测试、后有真修复**，与评审"并发与失败面缺测试防线"的判断互为印证。

**回归**：`tests/wal_corruption.rs::checkpoint_failure_preserves_committed_data`
（cas/ 前缀注入持续失败 → checkpoint 报错 → 行仍可读 → 故障恢复 →
checkpoint 成功 → 重启后完整）。

## 2. P1 修复

### P1-C manifest 版本回收 vs CAS 单调性 → ✅ 已修（评审方案 ①）

`load_latest` 探测**遇任何 NotFound 一律回落 LIST**（`manifest.rs`）：
探测窗口内全部存在也可能有更高版本，同样回落。陈旧写者由此拿到真最新
版本号，不再向已删空洞写提交。`retained()` 注释与实现口径对齐（只按数量）。
`gc_last_sweep_ver` 死字段首次投入使用（记录回收水位，审计可读）。

**回归**：`manifest.rs::load_latest_falls_back_to_list_on_gc_holes`
——删除 2..=9 造洞 + 停滞写者 cached 强制停在 1，断言 load_latest 返回
10 且从 10 继续提交（无影子谱系）。

### gc_sweep 三处瑕疵 → ✅ 全部修复

1. **删除失败保留墓碑**（at_ms 不变，下轮重试），只压缩删除成功者；
2. **移出 commit_mu**：`checkpoint_branch` 在锁释放后调用 gc_sweep
   （256 次远端 DELETE 不再阻塞提交路径，与 GC定案 §3.4 声明一致）；
3. **僵尸 epoch 段**：每次 checkpoint 对全部旧 epoch **重新 LIST** 登记
   （不再依赖本 epoch 首次快照），失约写者的滞后段最终被覆盖。

### 空闲写者自毒化 → ✅ 已修（评审方案"后台续期"的零新线程变体）

租约状态抽为 `Arc<LeaseKeeper>`（check / renew_if_due），由 `Branch::
fence_gate` 与 **WAL flush_loop 的 keepalive 回调**共享：flush 线程每次
醒来调用 `renew_if_due`（自限频：内部比较 next_renew_ms，未到期即返回），
空闲分支不再因 TTL 过期而永久 40001。**保活救不了已失约者**——
`renew_if_due` 对 `expires_at_ms <= now` 直接返回（重开 + 重新 recovery
才能重获写权，这是 fence 的安全底线）。`WalConfig` 新增 `keepalive:
Option<Arc<dyn Fn()>>`，只读 writer 无 flush 线程故无保活（占位租约）。

**回归改造**：`fence_expired_writer_rejected` 的场景按新语义重写——
空闲本身不再失约（旧测试前提已失效，这是行为改进），真实失约 =
**续期 PUT 持续失败**（fence/ 分区注入，仅 acquire 放行）：TTL 过期后
提交 40001、读不受影响。`fence_renew_keeps_healthy_writer_writing`
继续覆盖健康路径（TTL 80ms、300ms 窗口内 10 次提交零误拒）。

### /readyz 语义化 + 指标污染 → ✅

- `/readyz`：任一驻留**写者**租约过期 → 503（过期写者只能回 40001，
  不该接流量）；只读分支恒 ready。
- `/metrics`：只读分支跳过 `lease_ttl_ms`（占位租约会输出巨负数），改发
  `dendro_branch_read_only 1`。
