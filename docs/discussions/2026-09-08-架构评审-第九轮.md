## 0. 总体判定（TL;DR）

**委托点 a–e 的机制层全部验真：三层 map 归并是正确的抽象收敛（键序错误结构性无处可写，本轮探针证实 put→delete 序、同键双改、墓碑序全部正确）；Q-9 的 40001 盲区拒绝实现正确（commit_mu 串行化、隐式/只读双豁免、开库 covered_min=0 保守正确、重试路径成立）；Q-11 拦截覆盖 SQL 文本与 prepared 双路径。但本轮把同一组探针沿"显式事务 × checkpoint"这条轴再推进一步后，挖出了九轮以来最锋利的缺陷（R9-1，P0）：显式事务的冻结读被 checkpoint 截断击穿——事务打开时有数据的表，一次并发 CHECKPOINT 之后 count 从 1 变 0，且只读事务照常 COMMIT Ok、无任何错误信号。** 根因是 R7-3（冻结 catalog 根）与 checkpoint 截断（truncate_all 按 covered 而非按最老活跃快照）的复合：`tree@冻结根 ∪ overlay(≤快照)` 这个并集在截断后不再等于快照状态。Q-9 的 40001 只保护写侧提交，**不保护事务内的读**——同一个架构缺口的另一半。

第二组发现指向**修复的覆盖面**而非机制：R8-1 的"读自己的写"只接了 table_scan 与点查两条路，**AP 列存路径（≥1 万行）没接**（探针：显式事务内 count 12000 vs 应 12001），KV 层的 scan 没接、get 返回未解码整行；R8-6 的 join+exit(1) 修复**在默认配置下无效**——进程级实验实锤：pg 端口冲突时（metrics 默认开启）进程照常存活、"dendro ready" 照打，与修复提交信息声称的行为相悖（❌，第九轮首次出现声称失实）。Q-9 与未实施的"分支族语句拒绝清单"（R8-2 建议）复合出新形态：事务内 CHECKPOINT/CREATE BRANCH 不再半提交，但变成了**提交时刻的自伤 40001**（探针实锤）。

盲区普查的结论偏正面：pgwire/mywire codec 的健壮性（边界守卫、畸形包测试、大包限流）是全库质量最好的模块之一；slt runner 的 R8-9 一行项仍未做；benches 方法学粗糙但已登记（P2-3）；SPEC/tutorial 与 Q-9/Q-11 新语义的文档同步缺失（DoD #3）。

## 2. 专项审查（委托点 a–e）

### 2.1 委托点 a：三层 map 的完备性与性能面——归并本身完备；冻结根 × 截断的复合缺陷（R9-1，P0）

**归并结构（不含冻结根因素）验真为完备**：

- 覆盖顺序 树→overlay→txn 的正确性由数据结构保证：三层各自按键唯一、后层覆盖前层；`snapshot_rows` 对同键多版本取 ≤snapshot 最新（含墓碑 None），"先 put 后 delete"在 memtx 侧收敛为单墓碑、在 txn 侧收敛为单 Delete——探针 P9-6（BEGIN;INSERT id=5;DELETE id=5;SELECT→0;COMMIT→0）绿。
- "先 put 后 delete"的语句级序列、ORDER BY/LIMIT 组合、二次 checkpoint 重物化：第八轮已验 + 本轮结构复核无新洞。

**但委托点 c 的探针把"checkpoint 语义下的正确性"问倒了（R9-1，P0——本轮最重要发现）**：

```
s1: CREATE t; INSERT (1)                    → 提交，watermark=W1，表尚未 checkpoint
s2: BEGIN（snapshot=W1，冻结 catalog 根 F1：t.table_root=None）
    SELECT count(*) → 1                     ✅（overlay 可见）
s3: CHECKPOINT                              → 物化行进树（新根 R2）；truncate_all(W1)
    把 latest_ts ≤ W1 的键**整键移出 memtx**
s2: SELECT count(*) → 0                     ❌ 已提交行在事务内消失
    COMMIT → Ok                             ❌ 只读事务无任何错误信号
```

- 机制：显式事务的可见集 = `tree@冻结根(F1) ∪ overlay(≤W1) ∪ 自身写`。行 (1) 在 F1 的 catalog 里 `table_root=None`（F1 早于物化），树侧为空；truncate 之后 overlay 侧也为空——**并集不变式被打穿**。一般化表述：**凡在 BEGIN 之前提交、但首次物化发生在 BEGIN 之后的行，对冻结读事务不可见**（表从未 checkpoint 过时退化为全表不可见）。
- 与 Q-9 的关系：同一架构缺口（memtx 窗口 = MVCC 窗口）的**读侧**表现。Q-9 的 40001 只在 commit_tx 拦截**带写集**的事务——只读显式事务拿到的是**静默错误答案 + COMMIT Ok**（探针 P9-4 实锤，无 40001 可重试）。写事务也一样先经历错误读、再在提交时 40001：Agent 在事务内基于"消失的数据"做出的决策不会被提交失败挽回。
- 波及面：auto-checkpoint 线程默认 30s 一查、pending ≥16MB 即触发（`engine.rs:1140-1147`）；任意会话手工 `CHECKPOINT`/`CREATE BRANCH`/`MERGE` **无条件**触发 checkpoint_branch。长显式事务（产品叙事里 AI Agent 编排的核心场景）撞上其中任一个是常态而非边角。
- 考古：缺陷随 R7-3（`77009dd`）引入，非本轮修复所致；`r7_3` 回归只测了"BEGIN 时无数据 → count 恒 0"的单向（`sql_semantics.rs:134-165`），镜像方向（BEGIN 时有数据 → 必须恒见）零覆盖——第八轮"归并九边界探针"也未含此序。
- 修法：**truncate 按 min(covered, 全部活跃显式事务的最老快照) 截断**（第八轮 R8-4 的"正确路线"）。该修法同时消除 Q-9 盲区、R9-1 读侧丢行，并为 P1-10 time travel 打地基；届时 Q-9 的"跨 checkpoint 必拒"可退役为普通 OCC。替代方案（拒绝只读显式事务跨越 checkpoint）不可取——把正确读变成报错是倒退。

**性能面（委托点 a 后半）**：每次 table_scan 物化 `BTreeMap<Vec<u8>, Arc<Vec<u8>>>`（`scan.rs:846-853`）——树全量键值先入 map、再解码进 rows，两者同时存活：**扫描峰值内存 ≈ 修复前 ×2**（此前树侧流式、仅 rows + overlay 存活）；CPU 侧 O(N log N) 插入替代 O(N) 归并。渐近上界未变（rows 本就全物化，Q-1 未解前两种写法都是 O(表)），是**常数换结构安全**的交易。鉴于"性能最优先"定位，要求：(1) 注释里写明这笔交易（现注释只写了正确性动机）；(2) `dendro bench` 补一条大表全扫描对照（修复前/后），G7 的证据链别让这次收敛裸奔；(3) Q-1（读内存上界）在限界扫描落地时顺带拆除 map 物化（流式三层归并可在迭代器层面做）。

### 2.2 委托点 b：读自己的写——SQL 主路径 ✅；AP 路径与 KV 层两处未接（R9-3/R9-5）

- **UPDATE/DELETE 目标行扫描**：`update_impl`/`exec_delete` 经 `table_scan_by_name → table_scan`（`ddl.rs:504/464`、`scan.rs:381-394` 直连合并版 table_scan，不经 AP/pushdown 快路径）——同事务先 INSERT 再 UPDATE 同键、DELETE 后 UPDATE 空转均正确（r8_1 + 本轮复核）。
- **隐式事务**：层③ explicit 守卫 + 隐式路径语句末 install，回归与代码复核一致，无波及。
- **R9-3（P1）AP 列存路径不读自己的写 + 绕过冻结根**：`try_ap_scan`（`scan.rs:412-514`，`col_segments 非空 && col_rows ≥ 10_000` 即路由）只合并 memtx overlay，**从不看 `sess.txn.writes`**——探针 P9-1（1.2 万行列存表物化后，BEGIN;INSERT;SELECT count → 12000，应 12001）。同函数 `resolve_table(db, &sess.branch, …)`（`scan.rs:431`）取**当前 head** 而非 `txn.head_root`——R7-3 的冻结读在 AP 路径整体失效（事务内他人 checkpoint 推进 col_segments 会被看见）。生产 `serve` 默认装配 columnar（`main.rs:163`），这是主路径不是边角。修法：AP 路径并入层③（键级覆盖与 table_scan 同法）+ 冻结根解析 entry。
- **R9-5（P2）KV 层事务读两洞**：① `Kv::scan` 只做 树+overlay，不合并 `self.txn` 写集（`kv.rs:135-199`）——BEGIN;put(k1);scan 看不到 k1（探针红）；② `Kv::get` 的 `local_get` 接线返回**未解码整行编码**（`kv.rs:112-115` 直接 `v.to_vec()`，而 put 存的是 `enc_row` 两列行）——显式事务内 get 返回 16 字节行字节而非 `v1`（探针 P9-2b 实锤，**返回值损坏**，比不可见更糟）。`local_get` 这个"读自己写"接口在 SQL 层、KV get、KV scan 三个接点上如今一个解码缺失、一个没接。
- **P8-3c（P3，第八轮遗留）**：insert_row 的 dup check 仍未查事务写集（`ddl.rs:398-433` 只查 memtx/树）——BEGIN 内同键双 INSERT 依旧静默覆盖（探针 P9-5 红）。第八轮评审预期"随 R8-1 顺修"未发生；R8-1 修复只动了读路径，没动写路径存在性检查。

### 2.3 委托点 c：Q-9 的边界——机制全部验真；复合面两处新缺口

- **covered_min 的恢复/reopen 重建（委托核心问题）**：`Branch` 构造一律 `covered_min=0`（`engine.rs:602`），**不**从 manifest `covered_seq` 恢复——经推演这是**保守且正确**的：recovery 把 watermark 恢复为 `max(covered_seq, 回放最大 ts)`（`recovery.rs:44-45,100`）≥ 真实截断点，此后新建事务的快照 ≥ covered_seq，"快照早于截断点"的事务在进程重启后不可能存在；Q-9 只需拦"同进程内先 BEGIN 后 checkpoint"的跨距，而每次 in-process checkpoint 都在 commit_mu 内更新 covered_min。REOPEN BRANCH 重建 Branch 同理成立。✅
- **并发正确性**：checkpoint_branch 与 commit_tx 同持 commit_mu（`engine.rs:841` / `1220`），check 与 truncate 全串行。✅
- **只读显式事务不误伤**：COMMIT 时写集空则不进 commit_tx（`sql/mod.rs:424-426`）——BEGIN;SELECT;CHECKPOINT;COMMIT 正常 Ok（探针 P9-4 前半）。但注意这是"不误伤提交"而非"读正确"——见 R9-1。
- **R9-2（P1）Q-9 × 分支族语句的复合**：第八轮 R8-2 建议的"事务内 DDL/分支族一律 25001 拒绝清单"未实施（Q-10 只登记了 v2 事务化），Q-9 落地后其代价显形——**事务内 CHECKPOINT 使自己的提交必然 40001**（checkpoint 推进 covered_min ≥ 快照；探针 P9-3 红）；`CREATE BRANCH b FROM 当前分支` 内部先 `checkpoint_branch(from)`（`engine.rs:622`）同样自伤；MERGE 更是在事务中途 publish 另一支的 head。用户视角：工作全部作废，错误信息"transaction spans a checkpoint"指向了一个用户没做过的操作。修法：把第八轮建议的一行级拒绝清单补上（USE 已拦，CHECKPOINT/CREATE/DROP/MERGE/REOPEN BRANCH + CREATE/DROP/ALTER/TRUNCATE TABLE 在 `sess.txn.is_some()` 时 → 25001），并让错误在语句期而非提交期出现。
- **长事务产品语义**：Q-9 定案 = "显式写事务必须在一个 checkpoint 间隔内提交，否则 40001"。这是合理的 v1 边界，但必须写进 SPEC 04（见 R9-8）——它直接限定"AI Agent 长事务编排"的产品承诺。

### 2.4 委托点 d：Q-11 替代路径——SQL 双路径已拦；R8-6 经进程级实验判 ❌

- **prepared statement 路径**：`prepare()` 把分支语句包装透传、`exec_prepared` 按原文路由回 `exec_branch_statement`（`sql/mod.rs:558-563, 776-778`）——USE BRANCH 经 Parse/Bind/Execute 同样 25001。✅（代码路径唯一，pgwire extended 与 mywire COM_STMT_PREPARE[整体拒绝] 均无旁路。）
- **kv 层**：`Kv::use_branch` 不拦但 `self.txn = None` 静默丢弃未提交事务（`kv.rs:66-72`，注释声明"未提交事务会被丢弃"）——与 SQL 的 25001 口径不一致，且**缓冲写集无提示丢失**比报错更危险（R9-6，P3：至少 SPEC 11 写明，最好同样 25001）。
- **R9-4（P1，R8-6 判 ❌ 的证据）**：进程级实验（真实二进制 + 占用端口的监听 socket）：

| 场景 | 结果 |
|------|------|
| A：pg 端口冲突，`--metrics-port 0` | 退出码 1，输出 `dendro: listener 'pg' failed — exiting` ✅ |
| B：pg 端口冲突，metrics 默认开启（9469） | **5 秒后进程仍存活，"dendro ready" 已打印** ❌ |

  根因：bind 仍发生在各 spawn 线程内部（`main.rs:174/186/200/216` 的 `.expect("… listener")`），join 顺序 metrics→pg→my→kv（`main.rs:230-240`）——metrics 的 accept 循环永不返回，第一个 join 永不返回，exit(1) 不可达。第八轮建议的"bind 全部前置到 spawn 之前"正是为避免这一点，未被执行。修法（半天）：main 线程先 bind 四个 TcpListener（任一失败立即 exit 非零），把 listener 传入各 serve（wire 层加 `serve_on(listener)` 变体，现有 `serve` 签名不变）。

## 3. 新增缺陷与工程问题清单（本轮发现）

### P0（SQL 正确性）

1. **R9-1 显式事务冻结读 × checkpoint 截断 = 事务内静默丢行（§2.1，探针 P9-4）**：BEGIN 前提交、BEGIN 后首次物化的行对事务不可见；只读事务无任何信号地拿到错误结果并 COMMIT Ok。修法 = truncate 按 min(covered, 最老活跃显式事务快照)（与 Q-9 退役、P1-10 地基三合一）；回归 = r7_3 的镜像方向（BEGIN 时可见 → 并发 checkpoint → 恒可见）+ auto-checkpoint 版本。

### P1（覆盖面 / 运维）

2. **R9-2 分支族/DDL 语句事务内不拒 → 自伤 40001 或跨分支半提交（§2.3，探针 P9-3）**：CHECKPOINT/CREATE/DROP/MERGE/REOPEN BRANCH + 表 DDL 在事务内 → 语句期 25001。一行级清单，第八轮已建议。
3. **R9-3 AP 列存路径（≥1 万行）不读自己的写 + 绕过冻结根（§2.2，探针 P9-1）**：生产 serve 默认装配 columnar，属主路径。层③接入 + 冻结根解析。
4. **R9-4 R8-6 修复在默认配置下无效（§2.4，进程级实验）**：bind 未前置 + join 首位永不返回。修法 = main 先 bind 后 spawn（serve_on 变体）。

### P2（KV 接口 / 资源）

5. **R9-5 KV 层事务读两洞（§2.2，探针 P9-2a/b）**：scan 不合并事务写集；get 的 local_get 返回未解码整行（**值损坏**）。
6. **R9-6 kv use_branch 静默丢弃未提交事务（§2.4）**：与 SQL 25001 口径不一，写集无提示丢失；至少 SPEC 11 声明，最好同口径拒绝。

### P3（一致性 / 文档 / 测试基建）

7. **R9-7 P8-3c 未顺修（§2.2，探针 P9-5）**：事务内同键双 INSERT 无 23505；与 R9-5 同修（insert_row dup check 加 txn 写集查询）。

## 4. 盲区扫描（本轮委托扩权项，首次覆盖）

### 4.1 pgwire/mywire 协议健壮性——全库质量最好的模块，结论正面

- **pgwire codec**：BodyReader 全程带边界检查；startup 长度 8..=10000、消息长度 4..=1GB 双守卫；未知 tag / 保留主版本 / 半途 EOF / 畸形 CancelRequest 全部显式拒绝；**13 个 codec 单测覆盖畸形包**（截断、超长、未知 tag、奇数参数）。extended 协议的 in_error 跳过态、26000/08P01/PROTOCOL_VIOLATION 语义、Close 未知名静默，与 SPEC 10 §2 对得上。
- **mywire codec**：帧拼接的 seq 连续性自动管理；读侧 max_allowed_packet（16MB 默认）超限 → ERR 1153 后断开；写侧 >0xFFFFFF 自动拆帧；Truncated 安全的 Reader；lenenc 全域 roundtrip 测试。错误映射表（map_state）含 40003 透传（第五轮修复保持）。
- 认证：cleartext（PG）/ native_password（MySQL）+ AuthSwitchRequest；BackendKeyData secret 用 splitmix64（无 rand 依赖，可接受）；CancelRequest 收到即关连接（无查询取消——Q-1/S-3 族既有）。
- 遗留即 R9-11 小项：批量中途失败的响应丢弃、无 read/write 超时（慢客户端占死线程——S-3 已登记，建议随连接上界一起做）。

### 4.2 slt runner（`crates/slt/src/main.rs`）

- 结构：每文件独立内存库 + 单 Session，sqllogictest 官方 crate 驱动——框架选型正确。
- **R8-9 未做**：`DbOptions::memory()` 默认 `checkpoint_interval_s=30` 未置 0（`main.rs:62`），009 的"不中途 auto-checkpoint"仍是时序巧合。而 benches 的 AP 套件**置了**（`bench/mod.rs:211`）——同一仓库两种口径，说明这不是不知道而是遗漏。
- 次要：一次 `run()` 返回多语句输出时合并成一个比对块（`main.rs:29-50`），失败定位粗化；列类型恒 Text（v1 可接受）。

### 4.3 benches 方法学（`crates/dendro-server/src/bench/mod.rs` + `benches/results/`）

- 正面：点查基准有 `assert_eq!(hits, n_select)` 正确性锚；分支基准隔离了 load/checkpoint/create/merge 四段计时，能真正回答"CREATE BRANCH O(1)"；结果 JSON + results/README 入库。

- tutorial 06（内存事务引擎 OCC）：§3 的 40001 语义描述未含 Q-9 边界（与 SPEC 04 同步缺口）；§4"内存有界的机关"未提活跃事务钉住版本的问题——R9-1 修复落地时这两章要一起改。
