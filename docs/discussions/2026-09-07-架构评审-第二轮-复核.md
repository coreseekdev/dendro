## 1. 逐项复核 verdict

判定词：✅ 已验证修复 · 🟡 部分修复（含新问题）· ❌ 声称修复但未修复

### P0-1 WAL flush 失败丢帧 + 挂死 → 🟡 主病已治，引入两个新问题

**已验证（好的一面）**：`flush_now` PUT 失败时帧放回缓冲头部（正确处理了"上传期间有新 append"的排序问题——旧帧在前）、`await_durable` 超时路径 `?` 传播错误——**丢帧和永久挂死两条路径都关闭了**。这是本轮最有价值的修复。

**新问题 1（回归）——计数器不再清零**：原代码 take 后有 `g.frames = 0; g.min_seq = 0; g.max_seq = 0; g.pending_frames = 0;`，修复时被整段删除（见 `68de926` diff）。后果：
- `g.frames` 跨段累积 → **第一段之后每个段的 trailer 帧数都是错的**（累计值而非段内值）。今天 trailer 没有读者（我已核实 `FrameIter::new` 按 data 长度截尾、recovery 不读 trailer），所以是潜伏 bug 而非现行 bug——但磁盘格式的元数据从此就是错的，等 recovery 将来用 trailer 做交叉校验时会爆。
- `g.pending_frames` 永不归零 → flush_loop 的 `pending > 0` 唤醒条件在首帧之后**永久为真**，每 interval 空转一次 flush_now（空缓冲早退，便宜但设计意图已破坏）。
- 正确做法：**成功路径清零计数器，失败路径（restore 分支）保留**——恢复的帧还在缓冲里，计数器理应保留；两个路径不该共用"都不清零"。

**新问题 2（性能）**：`Bytes::from(segment_data.clone())` 在**每次成功 flush** 上都整段克隆（段上限 32MB）——组提交热路径新增一次全量 memcpy。改为先 `Bytes::from(data)` 持有句柄、`Bytes::clone` 只是引用计数，失败路径再从 Bytes 拷回，可两全。另：`&segment_data[..segment_data.len() - 32]` 的 32 是魔数，应引用 `TRAILER_LEN`。

### P0-2 恢复路径对坏数据 panic → ❌ row.rs 修了，wal.rs 的 FrameIter 没修

**已验证**：`decode_row` 全部定宽字段（BOOL/I32/I64/F64/DATE/TS）长度守卫已加，`take_bytes` 也有守卫。✓
（小瑕疵：V_I32/V_I64/V_F64 三个分支里守卫行**复制粘贴重复了两遍**，无害但请清理——这恰好是"没跑一遍自检"的信号。）

**未修复（评审指出的原bug另一半，仍在）**：`wal.rs` `FrameIter::next_frame` 中

```rust
let len = u32::from_le_bytes(d[16..20].try_into().unwrap()) as usize;
let payload = &d[HEADER_LEN..HEADER_LEN + len];   // ← 仍然先切片
if crc32c::crc32c(payload) != crc { ... }          // ← 后校验 CRC
```

`len` 来自帧头（不可信输入），`HEADER_LEN + len > d.len()` 时直接越界 panic——**这正是首轮报告 §5.2 指出的原始 bug，未修**。回应里写的"FrameIter 在 off + HEADER_LEN > data.len() 时返回 None"描述的是**修复前就存在的检查**，它只保护帧头不保护 len 字段。另有一处连带问题：上一帧的坏 len 把 `self.off` 推过 `data.len()` 后，`self.data.len() - self.off` 在 debug 构建下**下溢 panic**（测试全部跑 debug！），release 下回绕后被下一检查兜住。修法：切片前 `if HEADER_LEN + len > d.len() { return Some(Err(...)) }`，off 推进前重算。

**TASK.md 该项 ✅ 不成立，请重开。**

### P0-3 列存旧段删除时序 → 🟡 修成了"永不删除"

修复把 `for p in old_paths { obj.delete(&p) }` 改成 `let _ = old_paths;`（注释"GC 回收，v2"）。崩溃窗口的数据丢失确实关闭了 ✓。但：
- TASK.md 备注"延迟到 manifest 发布后"**不准确**——实际是无限期滞留。每次全量重建（段数≥8 或删除超阈值触发）留下 8+ 个孤儿段，**只写库的存储增长进一步加速**。
- 可接受的止血，但正确修复是"发布新 manifest 成功后删除本次替换的旧段"（发布点就在同一函数调用链上，把 old_paths 存到 manifest commit 之后处理即可），或至少把孤儿段登记进 GC 墓碑清单（P1-4 GC 的输入）。请把"真删除时序"并入 P1-4 一起做，勿留两处口径。

## 3. 对沟通机制的建议（已落实为 README.md）
