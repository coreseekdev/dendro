## 2. 专项审查（委托点 a–f）

### 2.1 毒化闭环（a）——✅ 四处检查一致 / ❌ 恢复半边缺失（R5-1、R5-3）

- **四处检查的一致性**：`append` 入口（`wal.rs:342`）→ 缓冲 → `Always` 走 flush_now（`:408` 毒化早退）+ await_durable（`:379` 毒化即返）；`Group` 走 await_durable；`NoWait` 直返。flush_loop（`:475-482`）与 flush_now 双入口都被毒化拦截。竞态核查：append 入口检查与缓冲非原子——毒化并发置位时，`Group/Always` 提交者经 await_durable 得到 40003（正确）；失败路径把整段字节归还原缓冲头部（`:435-444`），`cur_seg`/`durable_seq`/`flushed_seg` 均不动，语义自洽。
- **write_branch_commit / checkpoint 路径的 WAL append 在毒化后**：两路径的 ck 帧追加（`engine.rs:713`、`:943-944`）都以 40003 失败。checkpoint 失败 → `checkpoint_locked` 归还 pending（`:852-869`）+ pending_bytes 重建，下轮重试同样 40003——毒化分支的 checkpoint 与提交一致地停摆，pending 不丢（回归 `checkpoint_failure_preserves_committed_data` 覆盖同族 cas/ 失败）。`head.store` 先于 append 的 in-doubt 低配窗口已有诚实注释（`:689-693`、`:826-829`），重启后以 manifest + 回放收敛——可接受。
- **keepalive 在毒化分支上继续工作**：按委托预期"应该继续——租约保活与 WAL 毒化独立"，代码也确实如此（`wal.rs:472-474` 的 `ka()` 在毒化检查 `:480` 之前）。**但本轮探针 B 把这个"正确"的答案变成了一个设计问题**：毒化写者持续续租 ⇒ 租约被一个永远不能写的写者永久占住 ⇒ fencing 的接管机制（依赖 TTL 过期）永远不会触发。叠加下述"reopen 无入口"，一次瞬时故障升级为无限期写冻结——见 R5-1。
- **reopen 后新 writer 状态干净**：新 `WalWriter::open` 的 `poisoned: false`（`wal.rs:281`）；新 epoch 目录为空、段路径按 epoch 隔离；恢复回放按 ts > covered 裁决 Uncertain 帧（`recovery.rs:63-88`）。测试 `wal_failure_poisons_writer_until_reopen` 全链覆盖（拒叠加 → 无痕 → 重启无幽灵 → 可写）。
- **R5-1（本轮最重要发现）毒化没有可到达的恢复路径**：`Database::branch()` 对已在 `branches` map 的分支永不驱逐（`engine.rs:458-464` 直接返回缓存）；全部 SQL 面（CHECKPOINT / CREATE-DROP BRANCH / USE）没有任何 reopen 入口；`DROP BRANCH` 的 `remove_branch_runtime`（`sql/mod.rs:289`）丢弃该分支 ref，不是恢复。错误消息三处都说"reopen the branch to recover"（`wal.rs:345/381/445`），但客户端能做的只有重试（继续 40003）或由运维重启整个 server 进程。**修法（择一，建议 ①）：**
  1. **毒化时停止续租**：keepalive 回调与 commit 路径 `fence_gate` 的 `renew_if_due` 都检查 poisoned（Writer 状态需要暴露给 LeaseKeeper，一处 Arc 传递）——TTL 后租约自然过期，任何新打开者以 epoch+1 接管并回放裁决。安全性论证：毒化已使本写者停止一切上传（flush 停），过期后 `fence_gate.check` 拒绝其一切写——脑裂面不变，可用性恢复。注意只停 keepalive 不够：重试风暴的客户端会经 commit 路径继续续租，两处都要跳过。
  2. 提供显式管理入口（SQL `REOPEN BRANCH` 或 /readyz 附带的管理端点）：驱逐 Branch 运行态 + 重建。
  3. 最低限度：文档明示"唯一恢复 = 重启进程"，错误消息改为可执行的动作。
- **R5-3 NoWait × 毒化 = ack 后静默丢失（探针 A 实证）**：NoWait 提交在毒化置位前后拿到 Ok → 进程内可见 → 帧永不上传 → 重启后消失，全程无任何错误。默认 durability=group 故线上默认面安全，但"错误语义定案"必须写明这条边界：**40003 保护不到已 ack 的 NoWait 事务**（它们的效果等价于"缓冲即丢失"的 NoWait 契约，但触发条件不是崩溃而是毒化）。这正是回应 §5 自己采纳的检查项①（"每个返回错误的路径必须回答客户端如何理解"）该被应用的地方——NoWait 的 Ok 也是一个需要回答的返回值。
- 顺带（P3）：毒化置位不 `cv.notify_all()`（`wal.rs:436-445` 失败路径），await_durable 等待者最迟一个 flush_interval 后才感知（默认 50ms）——无害，加一行更干净。

### 2.2 40003 的 wire 层映射（b）——✅ PG 正确 / ❌ MySQL 退化为通用错误（R5-4）

- **PG**：`SqlError.state`（`error.rs:9-11`）→ `pgwire/error.rs:11-13` `ErrorResponse { severity: "ERROR", code: e.state }` 原样透传；连接保持（`simple_query.rs:121-122`）。40003 是合法 SQLSTATE（SQL 标准 statement_completion_unknown，PostgreSQL errcodes.h `ERRCODE_T_R_STATEMENT_COMPLETION_UNKNOWN` 亦定义 40003），**不会退化成 XX000**。severity=ERROR（非 FATAL）+ 连接保持，客户端可继续在别的分支工作或等待运维介入——映射正确。
- **MySQL**：`mywire/query.rs:255-272` 的 `map_state` **没有 "40003" 条目**，落入兜底 `_ => (1105, "HY000")`（ER_UNKNOWN_ERROR）。即同一毒化错误，PG 客户端拿到语义化的 40003，MySQL 客户端拿到通用 HY000——"结果未知"的语义在 MySQL 协议上只剩 message 文本承担。修法一行：`"40003" => (1105, "40003")`（与 40001→(1213,"40001") 同款的原样透传风格；errno 无对应值，1105 可接受，关键是 SQLSTATE）。
- **测试缺口**：两个 wire 层都没有任何 40003 端到端断言（grep 证实：40003 只出现在 core 与 `wal_corruption.rs`）。毒化语义选了 SQLSTATE 作为载体，却没在任一协议上验证它真的到达了客户端。

### 2.3 put_batch 逐组 join（c）——✅ 语义正确

- **并发上界恢复**：`chunks(8)` 逐组 spawn→join（`cas.rs:82-105`），峰值并发 = 8，`cas.rs:76-78` 注释重新为真。
- **首错早停不漏报**：组内全部 join 后才检查（`:97-104`），组内首错保留（`:90-93`）、其余错误被首错代表（单错误返回是设计而非漏报）；后续组未发（`:100-103` break）——其 chunk 未上传也未进 session_cache，错误上抛后由调用方兜住（checkpoint 归还 pending / 幂等重传），不存在"部分成功被当成全成功"的路径。

### 2.4 load_latest / update_manifest（d）——✅ 正确与安全 / ❌ cached 死状态 + 注释反向（R5-6）

- **真实请求数**：`load_latest` = 1 LIST + 1 GET（`manifest.rs:158-174`），与 SPEC 01 §5 "恰 1 个 LIST"一致；`update_manifest` 一次成功发布 = 1 LIST + 1 GET（load_latest）+ 1 PUT（commit）+ 0 LIST（自采纳）——较第四轮状态（2 LIST + 1 PUT + 1 GET）**实省 1 LIST/发布**，声称成立。CAS 冲突重试每轮多付 1 LIST + 1 GET，上界 64 次不变。
- **无变更路径自采纳的安全性（委托确认点）**：`f(&mut m)` 返回 false 时，m 是**当次 `load_latest` 刚读回的**（`:739`），采纳其版本号不可能引入陈旧快照；`state.store` 发布的也是这份刚读快照——**确认安全**。冲突路径 `continue` 重读，同样新鲜。`commit` 成功路径自发布的 m 就是刚构造的 `version = cur+1` 那份，无需回读——正确。
- **R5-6（新，实测 grep）`cached` 是全库零读者的死状态**：6 处写（`manifest.rs:137/154/172/188/195` + 测试 `:294`）、**0 处读**。P1-F 删除探测循环后，这个字段唯一的读者就没了；`adopt()`（`:152-155`）成了纯仪式。连锁失实两处：`engine.rs:743` "仍把读到的版本采纳为缓存（**下一次 load_latest 省一次 LIST**）"——为假，下一次 load_latest 恒 LIST；回应 §2 "cached 不再只写"——为假，它从未被读。修法二选一：删掉 `cached`/`adopt`（诚实、更短）；或给 `load_latest` 加"cached == LIST 结果即免 GET"之类的真实读者（不推荐，省的是一次小 GET，复杂度不值）。

### 2.5 backup 一致性点（e）——✅ 论证成立 / ❌ 实现两处叠加缺陷（R5-2、R5-5）

**先说论证里对的部分（值得肯定）**：
- append-only 前提真实（对象路径不可变、同路径同内容）；数据前缀先拷 + manifest 最后拷 ⇒ 快照内最高 manifest 版本引用的全部对象必然先于该 manifest 落盘、因而必然已拷入——"至少到最高已捕获版本"的一致点成立。
- **fence 对象必须拷**：研发自己想对的——恢复打开时 `FenceStore::max_epoch`（`fence.rs:67-80`）靠 fence/ 前缀还原真实最大 epoch；若缺失，接管 epoch 会从 manifest 的 `head.epoch` 起算，覆盖不到失约写者在更高 epoch 目录的滞后段（僵尸段丢失）。备份模块注释（`backup.rs:33`）把这个理由写对了。
- GC 竞态：最新 manifest 引用的对象不可能被墓碑删除（墓碑登记与"停止引用"同版本原子发布，被捕获版本就是最新版本）；WAL 段被并发删除时 `fs::copy` 报 NotFound **响亮失败**而非静默——fail-safe 正确。
- 备份运行中源库并发提交：拷入的 WAL 段可能超出捕获 manifest（晚于一致性点的提交进了段对象被拷走）——回放后恢复点比声称的一致点略新，但仍是**有效一致点**（段原子、事务不跨段），可接受；建议模块 doc 补一句"实际恢复点 ≥ 捕获 manifest 版本"。

**R5-2（P1）撕裂写 + 幂等跳过叠加，备份静默不可恢复**：
- `LocalObjStore::put`（WAL 段/chunk）是 temp+rename 原子写（`local.rs:81-87`），并发备份拷这些对象**不会**读到半写——这部分安全。
- 但 **manifest 提交与 fence acquire 走 `put_if_absent` = 在最终路径 `create_new` + `write_all` + fsync（`local.rs:89-96`、`:31-46`），没有 rename**。备份第二阶段（`backup.rs:36-41`）用裸 `fs::copy` 拷 manifest/ 时，源库一次并发 `update_manifest` 就可能让 `fs::copy` 读到**截断的 JSON**。被撕裂的恰恰是一致性点本身（最高版本 manifest）；后果是恢复时 `serde_json` 解析失败、备份不可用。
- 叠加第二缺陷：幂等跳过以 `target.exists()` 判重（`backup.rs:85-87`），注释假设"append-only ⇒ 同路径同内容"——**上次备份中途被 kill 留下的截断文件也"存在"**，重备永远跳过它，损坏被永久固化。两个缺陷叠加：一次中断的备份 + 一次补备 = 一个永远修不好、直到恢复那天才发现的坏备份。
- 修法（两处都便宜）：① `copy_tree_rooted` 改"拷到 `target.tmp` + rename"（顺带修幂等语义）；② manifest 阶段拷完后对最高版本做一次 `serde_json` 解析校验，失败即整体报错（或重拷一次）。加一个"并发写 + 备份"回归（写线程持续 INSERT，备份线程循环 N 轮，每次备份后解析校验最高 manifest）。

**R5-5（P2）`dendro backup` 失败退出码为 0（实测）**：`main.rs:236-238` 失败分支只 `eprintln!`，`main` 正常返回。实测对非 dendro 目录执行 `dendro backup` → 输出 "backup failed: ..." 后 **EXIT-CODE=0**。cron/脚本/编排无法感知备份失败——对备份工具这是不可接受的默认。改 `std::process::exit(1)`（或 `Err` 上抛）。
- 顺带（P3）：`objects/bytes` 双计数——`backup.rs:84` 对每个见到的文件 `files += 1`，`:94` 拷贝成功**再加 1**，CLI 打印的对象数约为真实的 2 倍（幂等跳过者 1 倍）。纯 cosmetic，但它是用户判断备份规模的数据。
- 顺带（P3）：src == dst / dst ⊂ src 无守卫（自我拷贝递归风险）；建议一行 `dst.starts_with(src)` 拒绝。

### 2.6 format_version 守卫放置点（f）——✅ manifest 覆盖完整 / 🟡 其余格式面仍裸奔（M-2 保持开放）

- **manifest 只有一个反序列化咽喉点** `read_version`（`manifest.rs:117-130`），`load_latest_via_list` 与 `commit` 的 Uncertain 反查都经过它——**守卫放置点覆盖全部读路径** ✅。写路径安全：`commit` 序列化的 Manifest 要么来自受守卫的读取（format_version ≤1）、要么来自 `Manifest::empty`（=1），旧二进制不会写出 format_version>1。回归真实（`manifest.rs:261-273`：format_version=2 拒绝 + 明确升级错误 + 当前版本可读）。
- **尚未覆盖的同族面**（M-2 范围如实保持开放，不算本轮缺陷）：fence Lease JSON（`fence.rs:58`，无版本字段，靠"缺字段报错"兜底——新增可选字段会被旧读者静默忽略）；table entry / schema chunk 的 JSON（`versioned/mod.rs:100/120`，同族）；WAL FRAME_VERSION 有守卫（`wal.rs:193-195`）但"新读旧"回归仍缺（M-2 原文记录在案，未动）。建议 M-2 拆两档：manifest（本轮已闭环）与其余格式面（产品化前）。
