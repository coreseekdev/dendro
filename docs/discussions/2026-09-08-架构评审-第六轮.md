## 2. 专项审查（委托点 a–e）

### 2.1 keepalive 删除回归（R6-1，P0 级，探针 1 实证）

**机制链**：`fence_gate`（`engine.rs:213-220`）先 `check` 后 `renew_if_due`；`renew_if_due`（`engine.rs:173-196`）对已过期租约**直接 return**（"保活无权救活失约者"）——一旦租约过期，全进程再无任何续期路径。原 flush_loop 保活（每 50ms 醒来、自限频 ttl/3）是空闲分支的唯一生命线，e699a49 把这行调用删了。

**探针 1**（MemoryObjStore，ttl=300ms，flush_interval=10ms）：建表 + 写 1 行 → 空闲 800ms → INSERT → **`40001 fencing: branch "main" lease epoch 1 expired — writer must re-open to acquire a new epoch`**。此后每条写全部 40001，进程内永久不可写，直到 reopen（客户端不可达）或重启。

**影响面**：默认 `lease_ttl_ms = 30_000`（`engine.rs:93`、`main.rs:150`）。任何分支空闲 30 秒——夜间、午休、低流量时段、AI Agent 会话间隙——下一次写入即永久失败。这不是边角：这是把"数据库空闲一段时间后拒绝服务"做成了默认行为。slt 8/8 与 196 测试全绿，因为没有任何测试跨过 TTL 空闲后再写——**第三轮修复 keepalive 时就没有留下回归测试**（grep 全库无 idle/TTL 相关断言），本轮回归因此静默落地。

**修法（两处都要）**：
1. 恢复 flush_loop 保活调用，但**置于毒化检查之后**（毒化分支 continue 在前）——这正是回应声称已做而实际没做的事，三行 diff；
2. commit 路径 `fence_gate` 的 `renew_if_due` 增加 poisoned 检查（见 §2.2，委托点 b）——注意这在结构上要求 LeaseKeeper 能看到 writer 的毒化状态（一个 `Arc<AtomicBool>` 共享即可），同时顺手给 R6-1 的回归测试补上："空闲 > TTL 后写入仍成功"（保活在场）与"毒化后 TTL 到期租约对象不再被续"（保活退场）两个方向各一条。

### 2.2 毒化分支的 commit 路径续租（委托点 b，探针 2 实证）

**结论：仍在续。** `commit_tx`（`engine.rs:1160`）、`write_branch_commit`（`:706`）、`checkpoint_branch`（`:786`）三个写入口都是 **fence_gate（check+renew）先于 wal.append**——毒化分支上每次提交尝试：gate 续租一次（至多 ttl/3 一次 PUT）→ append 得 40003。`renew_if_due` 无法感知毒化（LeaseKeeper 看不到 WalWriter 内部状态）。

**探针 2**（ttl=500ms，`wal/` PUT 持续失败毒化后，以 60ms 间隔重试 25 次 ≈ 3×TTL）：**storm 期间 fence/ PUT 计 8 次；1.5 秒后读回 `fence/main/000...1.json`，`expires_at_ms` 仍在未来（renewed=true）**；25 次重试全部 40003（租约被续住，从未过期）。

**影响评估要诚实**：第五轮"续租堵死 TTL 接管"的表述本身就高估了——`FenceStore::acquire = max_epoch+1`，**无条件、不等过期**（`fence.rs:85-102`，模块 doc `:18-19` 自己写明"接管者不等待旧租约过期"）。所以续租真正的影响是：① 毒化写者的自检（`check`）永远通过，错误面恒为 40003 而非 TTL 后翻转的 40001——这一点反而是**对的**（客户端应持续看到 completion_unknown）；② 监控面上租约显示存活，误导运维；③ 违背 §3.5 白纸黑字的"租约保活同时停止"。修不修是语义收口问题而非可用性问题：按 §2.1 修法 2 加 poisoned 共享位即可一并了结。

### 2.4 reopen_branch 语义边界（委托点 a，探针 3/4/5）

**快乐路径 ✅（探针 3）**：毒化（40003）→ `reopen_branch("main")` → 新 epoch=2 → 新会话写入成功、count=2（毒化前 ack 行由回放恢复，失败事务无幽灵行）。机制本身是真的。

**边界 ①（文档失实，探针 4 实证）**：`reopen_branch` doc 注释称被驱逐分支的旧会话"按毒化语义失败"。实测：健康旧 writer 上的一次 Group append 得到 **`58030 io "wal writer stopped"`**，不是 40003。语义上这其实**更强**（close 前 flush 线程已 join，帧确定未上传 = 确定未提交），但文档写的就是错的。另注意：Session 根本不持有 `Arc<Branch>`（每条语句经 `db.branch(name)` 重解析，`engine.rs:1158`），"在途会话拿着旧 Arc"的前提只对单条语句执行中的瞬间成立——文档描述的场景与真实并发结构错位。

**边界 ②（驱逐窗口，代码实证）**：`remove` 到重新 `insert` 之间（fence LIST+PUT、probe_tail HEADs×log、旧 epoch 段 GETs、全量回放——本地 µs 级，OSS 上是数百 ms 到秒级），任何会话对该分支的语句会得到 `undefined_branch`（42P01）或者**自己触发一次完整 branch() 打开**（各自领 epoch、各自起 writer）——后者引出边界 ③。

**边界 ③（同分支并发 reopen 竞态，代码实证、探针 5 未命中）**：两线程同时通过 `branch()` 的 map 检查 → 各自 `fence.acquire` 领到 E+1、E+2 → 各自回放 → `entry().or_insert()` 先到先得，**且 `branch()` 返回的是自己的 b 而非 map 里的**（`engine.rs:561-565`）——落败方的 Branch 带着活 flush 线程 + 有效租约被返回给其调用方，其线程永不停止（stop 无人置位 = 线程泄漏）；若落败方是更高 epoch，则 map 驻留低 epoch writer 而一个高 epoch"孤儿写者"真实存活，二者可同时提交（fencing 自查只看自己租约是否过期），恢复期按 ts 裁决时高 epoch 同键覆盖低 epoch 已 ack 写——**ack 丢失窗口**。探针 5（5 次双线程 barrier 并发）在 MemoryObjStore 上未触发（窗口 ≈µs）；生产 OSS 上该窗口 = 数次网络往返 + 回放，100ms+ 量级，真实并发 reopen 必然踩中。**修法**：per-Database（或 per-name）reopen 互斥 + fence 领取后二次检查 map（若已有驻留者则 close 自己的 writer、返回驻留者）。

**边界 ④（无守卫的调用面）**：`reopen_branch` 对健康分支照搬执行（新加的 `wal.poisoned()` 访问器全库零调用——commit message 说它"engine::reopen_branch 与监控用"，两处都没用）。至少应拒绝驱逐未毒化写者（或打 warn）；metrics 侧毒化信号仍缺（R5-P3 #12 未做，未声称做）。

**边界 ⑤（小）**：被驱逐的未毒化 writer 上，retry 风暴的 append 仍把帧塞进死缓冲（thread 已死、永不 flush、永不上限）——旧分支 Arc 的重试客户端可缓慢推高内存。低危，随边界 ① 的语义收口一并处理（close 后 append 应直接拒绝）。

**fence acquire 覆盖确认（委托点 a 之问）**：新 acquire 取 `max_epoch(LIST).max(manifest.epoch)+1`（`fence.rs:86`），旧 epoch fence 对象只在低位——**覆盖成立** ✅；`branch()` 期间旧 writer 的租约对象与新 epoch 互不冲突 ✅。

## 5. 架构 / 选型 / 测试 / 文档诚信（增量）

### 5.1 架构（增量）

- 毒化语义的设计本身（40003 + 拒绝叠加 + recover-by-reopen）仍是六轮以来最清晰的一段定案；本轮暴露的是它的**交付链**：恢复入口停在 Rust API、恢复前提（保活停止）修出了回归、语义文档写进了实现没有的句子。定案 → 代码 → 测试 → 文档四件套，本轮在 2/4 上失守。
- reopen_branch 的"驱逐 + 重领 epoch + 回放裁决"结构与既有恢复路径零新增概念，方向正确；缺的是并发防护与产品接线（R6-2/R6-3），是收尾不是返工。

### 5.2 技术选型（增量）

- 无新选型风险。`with_extension` 做 tmp 后缀、`fs::copy`+`rename`、尺寸守卫——本地工具语义下都是正确的原语选择。

## 6. 全新扫描：产品级数据库还缺什么（委托扩权项）

本轮按委托扩大视野，以下为代码实证的新面（按重要性排序，编号接 §4）：

### S-1（P2，扩缩容叙事的地基）**启动时全量打开所有分支**
`Database::open → load_open_branches`（`engine.rs:424`、`:1054-1060`）对 manifest 里**每一个**分支执行完整 `branch()`：fence LIST + fence PUT（领 epoch）+ probe_tail（HEAD×log）+ WAL 段下载回放 + **每分支一个常驻 WAL flush 线程**。分支数 N = 启动时 3N+ 次网络往返 + N 个线程 + N 份租约。"AI Agent 沙箱"叙事下分支是快节奏、海量、短生命的（每会话/每任务一分支），万级分支时启动分钟级、线程数万——弹性调度（秒起秒灭的计算节点）被启动成本直接否决。修法方向：惰性打开（首次访问才 `branch()`；`load_open_branches` 只恢复 main 或最近活跃集），配一个"分支数 vs 启动时间"的基准（M-9 候选）。

### S-2（P2，存储泄漏）**DROP BRANCH 永久泄漏该分支全部对象**
`sql/mod.rs:268-291`：close writer → manifest 删 ref → 运行时移除，但 `wal/{branch}/` 全部段、`fence/{branch}/` 全部 epoch 对象**不登记墓碑、永无回收路径**（墓碑只登记在存活分支的 checkpoint 里；ref 删除后该分支再无 checkpoint）。分支生命周期是本产品的核心叙事，删除分支 = 只增不减的存储账单。修法：drop 时对该分支 `list_prefix("wal/{name}/")` + `list_prefix("fence/{name}/")` 逐段登记墓碑（走既有 24h 保留窗）。

### S-3（P2，可观测性）**毒化不可见**：无 `dendro_branch_wal_poisoned` metric（`metrics.rs` 全文无 poison）；/readyz 只看租约过期。R6-1 场景（40001 冻结）与 R5-1 场景（40003 冻结）运维都只能从客户端报错发现。一行 gauge + readyz 附毒化位。

### S-4（P2/P3，资源上界全家无守卫）：连接数（每连接一线程，无上限/无积压配置，`pgwire/lib.rs:87`、`mywire/lib.rs:124`）；分支数（无上限 + S-1 放大）；事务体积（写集/pending_bytes 无上限，单个巨型事务可耗尽内存）；语句大小（wire 层无帧上限复核——pgwire 有协议上限而 SQL 文本无业务上限）。产品级至少要：最大连接、最大事务字节、二者可配 + 超限错误语义（SQLSTATE 54000 系/08M01）。

### S-5（P2，SQL 能力面盘点，如实记录无扣分预期）：支持 FROM 子查询（Derived）、JOIN、聚合、CTE；**无 UNION/INTERSECT/EXCEPT、无标量/IN 子查询（WHERE 内）、无 CREATE VIEW、无权限体系**（双协议各一个口令，无用户/角色/库级授权）。对"SQL 一等公民"目标，前两项是 G5 的硬缺口，权限体系是产品化的硬缺口——建议进 TASK.md 作为 G5 拆解项（M-10 候选），与 slt 语料扩充（P2-1）同一战线。

### S-6（P3，会话模型诚实声明）：`WireSession: Send`（`engine.rs:241`）+ 每连接一线程 + Database: Send+Sync，多客户端并发结构成立；但引擎注释（`engine.rs:4`"Session 单线程使用"）与跨会话并发测试（P1-7）双缺——结构安全未经测试证明。
