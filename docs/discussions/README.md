# docs/discussions — 评审与研发的可持续沟通机制

> 目的：把"评审 → 回应 → 修复 → 复核"变成可长期运转、可审计、低噪音的循环。
> 本机制自 2026-09-07 第二轮复核起生效。评审方与研发方同等受约束。

---

## 1. 目录角色

| 载体 | 角色 | 规则 |
|------|------|------|
| `docs/discussions/` | 沟通频道 | 只放评审报告、回应、复核、机制本身；**不放实现** |
| `TASK.md`（仓库根） | 唯一任务事实源 | 所有待办的登记处；状态只能由研发方修改，且**必须附证据**（见 §3） |
| 提交 + 测试 | 唯一完成事实源 | 文件里的勾选不构成完成，commit + 绿测试才是 |

## 2. 一轮沟通的生命周期（cycle）

```
①评审报告              ②研发回应              ③评审复核              ④关闭
<日期>-<主题>-<第N轮>.md  →  同名-回应.md        →  同名-复核.md         →  TASK.md 状态落账
发现问题(附证据)            认领/反驳/排期          逐项 verdict(附证据)      双方无异议项关闭
```

- **命名**：`YYYY-MM-DD-<主题>-<轮次>.md`；回应 `-回应`、复核 `-复核` 后缀。一轮 = 报告+回应+复核 三件套。
- **频率**：不固定日历节奏，按"研发方完成一批 TASK.md 条目"触发下一轮；每轮聚焦"上轮修复的复核 + 新发现"，不重谈已关闭项。
- **争议**：回应里可以反驳评审（带证据），复核里给出最终 verdict：`维持 / 撤回 / 修正表述`。被撤回的评审发现要在复核里显式认错，双向诚实。
- **单文件一主题**：新架构议题（如 P2' 管线设计、journal 接线）开新主题文件，不塞进架构评审轮次里。

## 3. TASK.md 纪律（核心制度）

1. **ID 稳定**：任务编号只增不改不重排；范围变化写备注，不换号。
2. **完成的定义（DoD）= 三要件**，缺一不算 ✅：
   - a. 修复/实现代码已提交（commit hash 写进备注）；
   - b. **回归测试已提交且覆盖该修复**（坏的先构造故障、再证明修复；测试名写进备注）；
   - c. 相关文档/注释/SPEC 同步更新（同提交或紧随提交）。
3. **证据列**：✅ 必须能回答"哪个 commit、哪个测试、哪行文档"。评审按证据复核，不按勾选信任。
4. **状态词汇**：⬜ 待做 · 🔧 进行中（可有 WIP 提交）· 👀 待复核（三要件齐，等评审）· ✅ 已关闭（复核通过）· 🧊 冻结（决策延后，写原因）。
   👀 是关键新增：**研发说"我做完了"用 👀，评审说"验证过"才 ✅**。避免本轮"TASK.md 已 ✅ 但 FrameIter 未修"的失真。
5. **发现即登记**：评审新发现、研发自查发现，都先落 TASK.md 再动手；完成的勾选与对应 commit 同车入库（本轮 P1-5 的教训）。

## 4. 双方义务

**研发方**：
- 回应文件对每项发现给出 `确认 / 反驳(证据) / 部分确认(说明)`，不做纯表态；
- 提交 CI/基准/文档类改动前**本地实跑一遍**（本轮 `clippy -D warnings` 推送即红的教训）；
- 修复引入的行为变化（如 S4 整数拓宽）在回应中显式声明，并同步 SPEC。

**评审方**：
- 每项发现附 `file:line` 或实跑输出；复核时**亲自读 diff/跑测试**，不做推测性 verdict；
- 区分"错误"与"取舍"：对合理取舍给 👍 并关闭，不用偏好压设计决策；
- 复核结论四选一：`已验证 / 部分修复(列残余) / 未修复 / 回归发现(新问题)`；
- 认可响应速度与修复质量（该表扬就写），保持评审的建设性。
