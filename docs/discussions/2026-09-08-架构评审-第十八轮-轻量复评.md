### 1.3 委托 c：M-3 压缩曲线——机制在，口径双错 ❌

- **JSON 结构**：`[{codec, raw_bytes, compressed_bytes, ratio, enc_mb_s, dec_mb_s}]`，含行数断言自检、best-of-3 计时——骨架合理；缺 rows_n/时间戳/zstd 级别等元数据（复绘 Q 曲线信息不足，R18-6）。
- **raw_bytes 口径** ❌ R18-2(P2)：`bench/mod.rs:383` `batch.get_array_memory_size() * 2 // 两列近似`——arrow 59.3.0 的 `RecordBatch::get_array_memory_size()`（arrow-array-59.3.0/src/record_batch.rs:810-815）**已对全部列求和**，`* 2` 双计。评审本机实跑：raw_bytes=1,529,136，真实值 764,568；**真实比值：Raw 1.06x（非 2.1x）、RleDict 0.97x（非 1.9x，实为负压缩）、Zstd 3.9x（非 7.8x）**——commit message/回应的三个 headline 数字全部虚高 2 倍。
- **吞吐单位** ❌：`rows / secs / 1e6` = **Mrows/s**，标成 `enc_mb_s`/MB/s——评审本机 Raw enc 7.9"MB/s"实为 7.9 Mrows/s（≈295 MB/s @36B/行），差约 37 倍（行宽倍数）。
- **"BitPack 自动跳过"表述失实**：循环列表 `[Raw, RleDict, Zstd]` 根本不含 BitPack（也不含 Delta，尽管代码注释自称 id 列"BITPACK/Delta 友好"）；无任何按列类型适配/跳过逻辑——每 codec 强制作用于整批两列（RleDict 作用于全唯一 id 列正是其比值≈1 的原因）。
