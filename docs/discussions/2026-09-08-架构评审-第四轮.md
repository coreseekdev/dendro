## 2. 专项审查（委托点 a–f）

### 2.1 flush_mu 单飞闭环（a）——✅ 通过

- **锁序**：`flush_now` 持 `flush_mu` → 取 `shared`（`:387-404`）；`await_durable` 超时路径先 `drop(g)` 再调 `flush_now`（`wal.rs:368-370`）；`append` 只短暂持 `shared`、不持 `flush_mu`。全库只有 `flush_mu → shared` 一个方向的嵌套，无死锁。
- **Always 路径**：`append(Always)` = `flush_now()`（排队等在途上传）→ `await_durable`（`:351-354`）。在途上传完成后 `cur_seg` 已推进（`:421-423`），自己的帧以新段号落盘；`await_durable` 里即使缓冲已被别人带走，`advance_durable(seg, max_seq)` 也覆盖其 seq。评审探针场景（慢 PUT + 并发 Always）已被回归固化且绿。
- **await_durable 超时路径**：`drop(g)` 后重入 `flush_now`，失败错误如实上抛、帧留在缓冲——语义正确。
- **close 竞态**：`close()`（`:475-481`）置 stop + join flush 线程；`await_durable` 见 stop 即返回 Err（`:362-364`）。外部线程的 in-flight `flush_now` 不受 close 影响（Arc 保活），无害。
- **失败重试的超集语义**：失败帧放回缓冲头部（`:407-417`），`cur_seg` 不动，同段号重试为超集覆盖——注释 `:384` 的前提现在真的成立（单飞后不存在互不为超集的并发 PUT）。

### 2.2 put_batch 错误传播（b）——✅ 修复真实 / ❌ 引入无界并发（P1-E）

- **权威检查在 join 后**（`cas.rs:96-104`）：正确。首错保留（`:87-90`）、错误时 `session_cache` 不更新（保守正确：重试时 `has()` HEAD 去重，幂等）；部分成功后失败的语义由调用方（checkpoint 归还 pending / put_batch 幂等重传）兜住。
- **P1-E（新，实测）**：错误检查移到 scope 出口后，`for group in jobs.chunks(PAR)` 的分组**只剩摆设**——各组 spawn 完不 join，全部线程堆积到 scope 出口才汇合。`cas.rs:76` 注释仍写"并发 8"。**探针 2**：160 个唯一 chunk × 每 PUT 30ms → 墙钟 40ms、**峰值 160 个并发 PUT**。按默认 checkpoint 阈值 16MB 估算，大 pending 时单次数千线程 + 数千并发 PUT——容器线程耗尽与 S3 限流都是现实路径。修法很小：逐组收集 handle、`join` 后再查 `err`（同时保住"权威检查在 join 后"与有界并发），约 10 行。

### 2.3 checkpoint pending 归还的键覆盖合并（c）——✅ 不可能复活已删除行

- **归并窗口内无并发写者**：`checkpoint_locked` 由 `checkpoint_branch` 在 `commit_mu` 内调用（`engine.rs:751-753`），而 `commit_tx`（`:1129`）、`write_branch_commit`（`:679`）同样持 `commit_mu`——归并 `slot.insert(k, v)`（`:840-847`）期间不可能有新提交写入更新值，纯恢复性写回，"旧值覆盖新值"的场景不存在。
- **pending 的全部写点核查**：`commit_tx`（commit_mu 内）、恢复回放（`recovery.rs:46-81`，打开路径单线程，先于分支发布）、`checkpoint_locked` 归还（commit_mu 内）——三处互斥成立。
- **head.store 之后失败的收敛论证成立**：`covered = b.watermark`（`:923`）在失败路径未变、manifest 未动、`truncate_all` 未执行（`:971` 在 manifest 成功后）；归还的 pending 下次以新 head 为父重新发布。回归 `checkpoint_failure_preserves_committed_data`（`wal_corruption.rs:381-421`）覆盖 cas/ 前缀注入 → 失败 → 可读 → 恢复 → 成功 → 重启完整，真实。

### 2.4 load_latest LIST 回落（d）——✅ 正确性 / ❌ 成本回归 + 三处文档反向（P1-F）

- **正确性**：影子谱系从机制上堵死，回归真实（§1 表）。
- **P1-F（新，实测）**：新逻辑下 `load_latest` **不存在任何不经过 LIST 的返回路径**——`cached+1` 撞 NotFound → LIST（`:143`）；探测窗口 32 次全命中 → LIST（`:148`）；cached=0 → LIST（`:150`）。而"写者已追平最新"（无新提交的常态）恰恰以 `cached+1` NotFound 结束——**探针 1：up-to-date 写者每次 `load_latest` = 2 GET + 1 LIST；落后 1 版同样 2 GET + 1 LIST**。即：探测循环成了纯死重（每次至少 1 次浪费 GET），`cached` 字段退化为只写状态，注释 `:135-136`"LIST 频率 = 空洞命中率 + 探测窗口用尽"**与实现恰好相反**（频率 = 100%）。级联成本：`update_manifest` 每次尝试 1 次 LIST（`:726`）、成功后再 1 次 LIST 刷新快照（`:734`）——一次 manifest 发布 ≈ 2 LIST + 1 PUT；CAS 冲突风暴时最坏 64 尝试 × 2 LIST。影响面：checkpoint / DDL / create-branch / gc_sweep / open（**提交热路径 commit_tx 不碰 manifest，读路径走 ArcSwap 快照，均不受影响**）；100ms RTT 下每次 checkpoint 多 ~300-600ms。三处文档与实现相反：`manifest.rs:3-4`（模块 doc"读最新版不依赖 LIST"）、`manifest.rs:131-136`（函数注释）、`spec/01:112-114`（§5）。修法二选一：① 承认 LIST 为权威路径，**删掉探测循环**（代码更短、成本不变、文档改一句）；② 恢复"探测短路 + GC 版本删除水位 = min(活跃写者 cached)"（`gc_last_sweep_ver` 机制正好是地基），让无洞前提重新成立。任选其一都必须同步上述三处文档。

### 2.5 管线重排（e）——🟡 进程内真实 / ❌ "in-doubt 已消除"不成立（P0-D）

- **进程内语义 ✅**：`validate_only`（`memtx.rs:201-223`）与 `install`（`:227-244`）拆分真实；validate→install 间隙由 commit_mu 保护（`engine.rs:1125-1126` 注释成立）；NoWait 语义不变（缓冲即返回，崩溃丢失是 NoWait 契约）；恢复回放与 install 用同一复合 ts（`recovery.rs:63` vs `engine.rs:1133/1147`），`ts > covered` 才回放，一致。
- **P0-D（新）**：`wal.append` 失败 → `commit_tx` 返回 Err → **帧仍留在 WAL 缓冲**（`wal.rs:407-417` 的失败归还），flush_loop 稍后重试成功 → **帧持久化** → 重启回放（`recovery.rs:65-88`，ts > covered 即安装）→ **"已报错"的事务数据出现**。研发自己的测试把两个互相矛盾的行为同时断言为期望：`wal_corruption.rs:233-241`"失败提交不得产生可见状态（in-doubt 已消除）"（进程内 count=1）与 `:242-255`"故障期'提交失败'的行 2 …… 必须 durable（不丢帧）"（重启后 count=3）。`commit_tx` 注释 `engine.rs:1122-1124`"新顺序下 WAL 失败 ⇒ 无任何可见状态，错误如实"对恢复路径为假——**错误并不"如实"：客户端收到确定性失败，数据却可能在重启后生效**。客户端按"失败 = 未提交"重试（Agent 沙箱的典型行为），重启后将出现双份效果。这是分布式提交最经典的 in-doubt 问题，管线重排把窗口从"立即可见"压窄到"重启后可见"，**是改进但不是消除**；TASK P2'-1 "✅ 消除 in-doubt"（TASK.md:63）应改口径。
  修法定案（三选一，需作为设计决定写进 SPEC 02/04）：
  1. **错误分级**：WAL PUT 失败返回专用"结果未知"SQLSTATE（如 40003/08000 系），文档明示"提交可能已生效，重试前须重查"——最小改动、语义诚实；
  2. **帧回收**：失败时若失败帧仍处缓冲头部且无后继帧（commit_mu 保证 append 串行，常见），从缓冲剔除并回退 `next_seq`；有后继帧时退化为方案 1；
  3. **写者毒化**：WAL PUT 失败 → 该 writer 拒绝一切后续提交直至 reopen（恢复路径按帧回放的语义不变，错误恒为"未知"）。
  无论选哪个，`commit_tx` 注释、`wal_corruption.rs:233-241` 的断言措辞、TASK P2'-1 的证据描述都要统一到同一种语义上。
- **顺带**：`write_branch_commit`（DDL/merge，`engine.rs:671-713`）与 `checkpoint_locked_inner`（`:917` head.store 先于 `:925` ck 帧追加）仍是旧顺序——checkpoint 有收敛论证注释（`:826-829`）✅；`write_branch_commit` 无注释，且失败后进程内 head 已推进（后续 DDL 能看到"报错了的"新表）而 manifest 未动，属同一族的低配版 in-doubt，建议补注释或同样重排。

### 2.6 keepalive 限频与只读占位租约（f）——✅ 语义正确 / 🟡 持锁做网络 PUT

- **限频正确**：`renew_if_due` 内部 `next_renew_ms` 比较（`engine.rs:169`）自限频至 ttl/3；fence_gate 与 flush_loop 并发调用由 `state` 互斥串行化，无竞态（`st.lease = fresh` 仅在 PUT 成功后写回，失败不污染本地状态——与第三轮确认的"本地/远端一致"不变式相符）。
- **安全底线**：过期后 `renew_if_due` 直接返回（`:169-170`），保活无法救活失约者；fence 分区测试真实覆盖。
- **🟡 P2（性能定位扣分）**：`fence.renew` 的 PUT（`:175`）在**持有 `state` 锁的状态下进行**。flush_loop 每 50ms 醒来一次，撞上续期点时，续期 PUT 的整个 RTT 期间会阻塞 `fence_gate`（commit 路径）、`/readyz` 与 `/metrics` 的 `state.lock()`。默认 TTL 30s 时每 10s 一次、每次一个 RTT——不致命，但"性能最优先"的项目不该让网络 I/O 待在提交路径的锁里。修法：保活路径改 `try_lock`（拿不到锁说明 commit 在场，本来就会续期，直接跳过）；或锁内 clone 后锁外 PUT、成功后二次校验写回。
- **只读占位租约**：`engine.rs:496-512`（expires_at_ms=0）；fence_gate 的 `read_only` 检查先于 `check`（`:202-205`）→ 占位租约永远不会触发 40001 误拒；metrics 跳过 TTL、readyz 恒 ready。核查通过。
