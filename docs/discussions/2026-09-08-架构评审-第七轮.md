**但同一轮探针在全新的读路径面上发现了七轮以来第一个纯读侧的 P0：一行已被 checkpoint 物化进树的记录，UPDATE 之后查询返回两行（新旧行并存，主键重复），DELETE 之后查询照常返回被删的行。** 根因是 table_scan 归并循环里一个 `<=` 与 `<` 之差（scan.rs:819）——overlay 中恰好等于当前树键的条目（对既有行做变更的常态）在"支配"判定之前就被消费掉，树旧行于是永远输出。伴生缺陷：点查路径把 memtx 墓碑当"未找到"回退树查找（scan.rs:752-758），同样复活被删行。**200 个测试与 slt 8/8 对此全绿，因为没有任何测试做过"checkpoint → 再变更 → 再行式查询"这个生产上每 30 秒就会发生的组合**——这是第六轮"防线缺在哪里、回归就发生在哪里"教训的读路径翻版：这次不是修复引入回归，而是核心功能从未被测过。

## 2. 专项审查（委托点 a–e）

### 2.1 委托点 a：keepalive 回归修复真实性——✅ 实锤

- 位置与顺序正确：`tick_once`（`wal.rs:482-508`）先查 `stop`（退）→ 读 `poisoned`（**毒化即 return false**：不上传、不保活）→ 再调 keepalive → 有 pending 才 flush。
- **变异测试**（验后已还原）：注释 `wal.rs:499-501` 三行 → `cargo test -p dendro-core --test multi_node idle_writer_stays_writable` → **FAILED**，panic 消息即断言"空闲超过 TTL 的写者必须仍可写（保活职责）"；还原后单测与全量基线恢复绿。该测试能区分"移动/删除 keepalive"与现状，第六轮要求的"能区分新旧行为的断言"成立。
- 一个小残点：`WalConfig.keepalive`（`wal.rs:228`）如今有真实读者，但 `engine.rs:212` 注释仍把保活职责描述为 flush_loop 回调之外的另一路径，措辞可再对齐（P3）。

### 2.2 委托点 b：三处 Weak 化——✅ 正确，附三个边界记录

1. **tick_once 退出条件完备**：`while let Some(w) = w2.upgrade() { if tick_once() { return } sleep }`。退出 = upgrade 失败（外部 Arc 全释放）∨ `stop`（`close()` 显式置位 / `Drop` 兜底置位）。两个条件覆盖了遗弃（reopen/DROP 后 close+join）与回收（外部 Arc 释放）两类场景，无第三种滞留。
2. **健康长驻分支不会被误杀**：驻留分支必被 `branch_locked` 写入 `branches` map（`engine.rs:606-609`），map→`Arc<Branch>`→`Branch.wal: Arc<WalWriter>` 强引用恒在，upgrade 永成功。第六轮"败者不入 map"的缺口已随 per-name 互斥消失。`idle_writer_stays_writable` 本身即"跨 500ms/多次 upgrade 存活"的活证。
3. **checkpoint 线程 interval 语义未变**：核对 `git show 41313be` 的 diff——旧代码顺序本就是 stop-check → sleep → work（sleep 从不在工作段内），本轮只是把强 `Arc<Database>` 改 Weak、sleep 挪到 upgrade 之前。首轮 sweep 时点不变（旧首睡同样不做事）；唯一语义差是 stop_cp 检查延后至多一拍——而 **stop_cp 全库无写者**（grep 仅 `engine.rs:345/430/1118` 三处，创建 false + 线程 load，从未 store true），本就是死字段（P3，随 Weak 退出机制已无存在必要）。
4. 边界记录（可接受，如实入档）：① checkpoint 线程 upgrade 后的**工作窗口**（逐分支 checkpoint，OSS 上可达秒-分钟级）持 Arc<Database>——是有界工作而非睡眠，遗弃 Database 的销毁至多推迟一轮；② flush 线程在 `sleep(flush_interval)` 期间持 Arc<WalWriter>，遗弃 writer 的 Drop 至多延迟一个 interval——"复活 fence 对象"的实际窗口（GC 24h 保留窗后）早已关闭；③ 毒化但被驻留的 writer：tick_once 每 50ms 空转一轮（不上传不保活），直到 reopen/DROP 的 close() join—— fleets of poisoned branches 各自 0.2% CPU 的 idle spin，可与 S-3 资源面一并考虑。

### 2.3 委托点 c：毒化 + REOPEN 组合边界（探针 R7-2）

| 场景 | 实测 | 判定 |

| 不存在的分支 REOPEN | `3D000 branch "nosuch" does not exist` | ✅ |
| 只读库 REOPEN | Ok 幂等（读分支 poisoned()=false → 返回驻留者） | ✅ |

R7-2 详述：`exec_branch_statement` 的 Drop 分支（`sql/mod.rs:272-306`）是**唯一不经 fence_gate 的破坏性路径**——CREATE/MERGE/CHECKPOINT 都先过 `checkpoint_branch` 的 gate（只读 → 25006），DROP 直接 `branch()+close()+update_manifest`，`read_only` 在 sql 层零守卫（grep 0 命中）。后果：一个声明"绝不创建对象"的读副本可以删除分支并把其 WAL 段/fence 对象登记墓碑——24h 后 GC 物理删除。这不是理论洞：弹性调度里副本与主节点共享同一 OSS bucket 是常态。修法一行守卫（25006）+ 回归。

### 2.4 委托点 d：S-2 墓碑化正确性

- **DROP 时 branch() 新领的 epoch fence 被覆盖** ✅：`sql/mod.rs:287`（branch()，内部 fence.acquire 已产生新对象）→ `:295-296` LIST 在其后——顺序正确；既有测试第三段即是"惰性打开后直接 DROP"场景，断言 fence/wal 目录清空。
- **旧 Arc 并发提交**（探针 R7-4）：
  - DROP 后旧 session 新语句 → `3D000 branch "b2" does not exist`（每语句重解析，不持 Branch Arc）✅；
  - DROP 前BEGIN、DROP 后 COMMIT 的在途显式事务 → `3D000`（commit_tx 首行 `db.branch()` 失败），写集静默丢弃，无半截提交 ✅；
  - 已过 gate、阻塞在 await_durable 的单语句 → close 的 stop → `58030`（第五轮边界①同款）。
  - **NoWait 例外（R7-6，P2）**：`append` 不检查 `stop`（`wal.rs:354-374` 只查 poisoned）——对已 DROP 的分支，NoWait 提交帧入缓冲即 **Ok ack**，flush 线程已死、帧永不上传：ack 后静默丢失。NoWait 契约只覆盖"崩溃丢尾"，不覆盖"分支被删"。close 后 append 应直接拒绝（与第六轮 §2.4 边界⑤同修）。
- **跨进程缺口（R7-5，P2，新登记）**：DROP 只对**本进程**生效——不领新 fence epoch、不驱逐其他进程的写者。B 进程驻留的 writer 在 A 进程 DROP 后继续 flush/续租/ack 提交（manifest 引用只在 checkpoint 时才报 "branch vanished"），其新段落落在 A 的墓碑 LIST 之后 → 永久泄漏；若分支日后重建，B 的高 epoch 段被恢复回放 → **僵尸写"复活"为可见行**。fencing 机制（epoch 单调 + 自查）天然支持"DROP 领 epoch + 写者 gate 校验租约仍存在"，属收尾不算返工，但必须入册：多进程多写者正是本产品的弹性叙事。
- **DROP 不持 commit_mu**（`sql/mod.rs:287-294`，对比 reopen 的 `engine.rs:492`）：在途 gate 的续租 PUT 理论上可落在 LIST 之后——但同路径 epoch 文件自 acquire 即存在、必在 LIST 快照内，墓碑仍覆盖；GC 删除后再 recreate 需要"24h 后仍有一次过 gate 的旧 Arc 提交"，实际不可达。可接受，建议随 R7-6 一并对齐 DROP 与 reopen 的防护（commit_mu + close 顺序）。

### 2.5 委托点 e：惰性打开语义——✅，一处残留

- `branch()` 不存在的分支 → `3D000`（`engine.rs:529-533`，探针复核）✅。
- `gc_sweep` on open（无驻留分支）：纯 manifest 操作（load_latest → 删到期墓碑 → 压缩 → keep-16），不触达任何分支 ✅（lazy 测试的打开块即证）。
- **残留（R7-6，P2）**：`Database::open → recover_branches`（`recovery.rs:18-31`）对 manifest 里**每个**有 commit 的分支做一次 HEAD——启动仍是 **O(分支数) 次网络往返**（每分支 1 次）。相比修复前的"3N+ 次 + N 线程 + N 租约"已大幅改善，但万级分支 × 公网 RTT 的启动仍是分钟级，S-1 的"弹性秒起"目标只完成一半。方向：抽样校验 / 后台懒校验 / 仅校验最近活跃集。

## 4. 新增缺陷与工程问题清单（本轮发现）

### P0（读路径正确性）

1. **R7-1 已 checkpoint 行的 UPDATE/DELETE 在读路径失真（§6.1，探针实锤）**：
   - table_scan 归并缺陷：`scan.rs:819` 预刷循环 `ok.as_slice() <= tk.as_slice()` 把**等于**当前树键的 overlay 条目先行消费，`:834-837` 的 dominated 判定随即落空 → 树旧行恒被输出。实测：checkpoint 后 `UPDATE t SET v='new' WHERE id=1` → `SELECT` 返回 `1,new;1,old;2,x`、count=3（**主键重复行**）；`DELETE id=1` → count 不减、明细仍含被删行。
   - 伴生 ①：点查复活——`build_point_view`（`scan.rs:752-758`）把 memtx 墓碑当"未找到"回退树（`TableMem::get` 对 tombstone 返回 None，`memtx.rs:51-62`；`visible_ts` 可区分但未用）。
   - 伴生 ②：`SELECT count(*)` 空输入返回 **0 行**而非一行 `0`（`agg.rs:119-145` 无 GROUP BY 时缺空全局组）。
   - 修法：预刷条件改严格 `<`（等键留给 dominated 消费）+ 点查用 visible_ts 先判墓碑 + 空输入全局组；**配套回归必须走 checkpoint → 变更 → 行式扫描/点查/聚合三组合**。

### P1（权限 / 并发语义）

2. **R7-2 只读副本可执行 DROP BRANCH（§2.3，探针实锤）**：`sql/mod.rs:272-306` 无 read_only 守卫，manifest CAS 写在副本上成功——分支被持久删除 + 私有对象登记墓碑。修法：Drop（及一切 update_manifest 调用面）加 25006 + 回归。
3. **R7-3 显式事务隔离语义混合（§6.2，探针实锤）**：overlay 按 BEGIN 快照（`sql/mod.rs:532-539`），树按 `resolve_table` 时的当前 head（`scan.rs:874`）——同一事务内同一 count(*)，checkpoint 前为空、checkpoint 后为 1：可见性随 checkpoint 进度在事务内翻转，且与 `SHOW transaction_isolation` 报告的 "read committed" 均不相符（RC 每语句取新快照应恒可见；RR 恒不可见）。修法：事务首语句冻结 head（连同快照），或 resolve_table 接受快照并沿父链裁剪。

### P2（弹性叙事 / 语义边界 / 测试）

4. **R7-4 读路径内存与分页全家无上界（§6.3）**：执行器全程物化（扫描/JOIN/ORDER BY/投影各 1-2 份 `Vec<Vec<SqlValue>>`）；LIMIT/OFFSET 在全物化+排序**之后**截断（`scan.rs:154-169`），`LIMIT 10` 照样扫全表；无 DECLARE CURSOR/FETCH、pgwire Execute 全量发 DataRow（`simple_query.rs:73-85`）；AP 路径把 RecordBatch 转行再合并（`scan.rs:464-511`）+ 全表 pk HashSet。与 S-3 同族但值得独立列：**读路径内存上界 + LIMIT 下推 + 游标**。
5. **R7-5 跨进程 DROP 不驱逐外部写者（§2.4）**：僵尸写者持续 ack 提交 + 对象永久泄漏 + 分支重建后高 epoch 段复活。修法方向：DROP 领新 fence epoch（墓碑化前）+ fence_gate 增加租约存在性校验（GET）或 manifest ref 校验。
6. **R7-6 启动仍 O(分支数) HEAD（§2.5）+ NoWait × DROP ack 丢失（§2.4）**：前者抽样/懒校验；后者 close 后 append 直接拒绝。
7. **R7-7 测试语料的结构性缺口（§0/§6.1）**：slt 8 文件与 200 测试均无"checkpoint → 变更 → 查询"组合——P2-1 语料扩展应把该组合列为第一优先；P1-7 并发测试连续六轮 ⬜，本轮混合隔离（R7-3）即并发语义缺陷。

### P3（cosmetic / 文档）

8. **R7-8 杂项**：二级索引缺失未作为产品决策入册（G7 点查叙事的地板：非 pk 谓词恒全表扫——建议在 SPEC 07 明确"v1 无二级索引"或立 M-x 任务）；代码四处 "SPEC 02 §4.1" 幻影引用残留（`wal.rs:245/445`、`engine.rs:477`、`mywire/query.rs:272`）；`stop_cp` 死字段（无写者）；`SET` 任何参数静默 OK 无效果（`sql/mod.rs:481`，兼容性陷阱：客户端设 isolation/timezone 得到成功假象）；`pseudo_tables/pseudo_columns` 恒读 main 分支（`scan.rs:1319/1333`），非 main 会话的 information_schema 显示错表；`has_agg_expr` 不递归 Cast → `count(*)::text` 被当普通表达式报错（`scan.rs:1141-1158`，而 `collect_agg_calls` 有 Cast 分支——两处遍历不对称）。

## 5. 架构 / 选型 / 测试 / 文档诚信（增量）

### 5.1 架构（增量）

- 写路径（WAL/fencing/毒化/GC/reopen）经六轮打磨，本轮全部抽查为真，已是全项目最扎实的部分。**第七轮的证据链把短板明确指向读路径**：引擎的"只写模型"定案把复杂度都推给了写入端，读端（归并可见性、快照一致性、内存上界）仍是 prototype 级——而用户 90% 的交互是读。
- Weak 化三连修方向正确且无新风险；"线程不持强 Arc 睡觉"应作为全库线程编写的通用红线入册（AGENTS.md 候选条款）。

### 5.2 技术选型（增量）

- 无新选型风险。一个值得记录的观察：**memtx overlay + 树的双源读**是当前所有读路径缺陷的共同根源（归并键序、墓碑语义、快照分裂三案皆源于此）。中期方向是把"可见性归并"收敛为单一抽象（一个 merge_two_sources(key, overlay_ver, tree_row) 纯函数 + 全路径复用），让 P0 级的键序错误在结构上无处可写。

### 5.3 测试机制

本轮最重要的机制发现：**slt 语料从不 checkpoint**（runner 关闭自动 checkpoint），因此"树 + overlay 双源读"这条生产主路径（checkpoint 每 30s/16MB 必然发生）**零覆盖**。200 全绿再次与 P0 共存，缺口不在断言强度而在场景覆盖。具体缺口：
1. checkpoint → UPDATE/DELETE → 行式扫描/点查/聚合（R7-1 配套，三组合各一）；
2. 只读副本拒绝一切 manifest 写（R7-2）；
3. 显式事务跨并发提交 + checkpoint（R7-3，P1-7 的第一个具体用例）;
4. 跨进程 DROP（R7-5，两 Database 实例即测）；
5. 既有开放：P1-7（六轮 ⬜）、P1-8、P2-1、M-2 尾巴。

## 6. 全新扫描：读路径与 SQL 面（本轮委托扩权项）

### 6.1 查询可见性：双源归并是缺陷密集区（P0，见 R7-1）

三案同源：归并键序（`scan.rs:815-844`）、点查墓碑回退（`scan.rs:752-758`）、AP 路径 overlay 覆盖（此处实现正确，`scan.rs:487-511` 用 BTreeMap 覆盖写）。同一个"overlay 是否可见"的问题在全库有三种写法、两种对错。修 R7-1 时应一并收敛抽象。

### 6.2 快照与 watermark 的关系（P1，见 R7-3）

- 隐式语句：每语句取当前 watermark（READ COMMITTED 口径，名称相符）；
- 显式事务：snapshot 冻结于 BEGIN，但 **head 不冻结**——overlay 与树按两套时间轴读。探针：`before-ckpt=空 / after-ckpt=1`。
- 附带：树读还可能**越过语句开始时刻**（resolve_table 在语句执行中段取 head），单语句内也非一致快照。
- `SHOW transaction_isolation` 恒报 "read committed"：当前实现既非 RC 也非 RR，报告值在三案中全部失真。

### 6.3 大结果集：无游标、无 LIMIT 下推、内存无界（P2，见 R7-4）

全物化管线（`TableView.rows` → project → order → Arrow batches → `text_rows()` 再整体转文本）意味着一个 1000 万行结果 = 引擎 2-3 份内存拷贝 + wire 层第 4 份文本。产品定位（AI Agent 沙箱）里 agent 拉大结果集是常态。最低交付序列：① LIMIT/OFFSET 下推到扫描层（ Trees 有序，range 扫描天然支持）；② `text_rows` 流式化（逐批编码）；③ DECLARE CURSOR/FETCH（sqlparser AST 已有）。

### 6.4 索引：只有主键（P3 决策项，见 R7-8）

pk 等值/IN 有直查快路径，pk 范围有列存 zone map 剪枝；**非 pk 谓词一律全表扫**（行式逐行 eval）。`CREATE INDEX` 在解析层即 unsupported。对"性能最优先"叙事：TP 点查（pk）达标，任何业务键查询（email→user）是 O(表)。可以作为产品决策明确"v1 无二级索引，业务键查询请用分支物化/列存"，但必须写进 SPEC 07 而不是留白。

### 6.5 错误消息质量：骨架合格，两处陷阱（P3）

SQLSTATE 体系完整、多数消息带修正指引（40003 指引 reopen、40001 指引 re-open、25P02 指引 ROLLBACK）——这部分是合格的。陷阱：① `SET` 静默无效（6.5/R7-8）；② pgwire `rows_to_batches` 里 `expect("record batch build")`（`scan.rs:1433`）是服务进程内 panic 点——当前构造方式不可失败，但它是未来列型改动时把坏数据变成断连的地雷，建议换 `SqlError::internal`。

### 6.6 其余核查项（无缺陷记录）

- `EXPLAIN` 恒返回占位但有诚实标注；`information_schema`/`pg_catalog` 三视图可用（跨分支错表见 R7-8）；`commit_log` 父链遍历有 1000 层守卫（`scan.rs:1364`）；ORDER BY NULL 序（ASC 末/DESC 首）与 PG 默认一致（`scan.rs:1278-1287`）。
