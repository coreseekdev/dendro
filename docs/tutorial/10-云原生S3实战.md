# 10 · 云原生 S3 实战（RustFS 实录）

> 代码：`objstore/s3.rs`、`objstore/cached.rs`、`engine.rs::materialize_delta`
> 环境：Docker `rustfs/rustfs:latest` @127.0.0.1:19000，桶 dendro-test/dendro-live

## 1. 启动一套完整环境

```bash
docker run -d --name dendro-rustfs -p 19000:9000 \
  -e RUSTFS_ACCESS_KEY=dendrokey -e RUSTFS_SECRET_KEY=dendrosecret \
  rustfs/rustfs:latest

```

## 2. 前提验证：条件写

manifest 乐观提交与分支 CAS 全部押在 `If-None-Match: *` 上。上适配器之前
先用 boto3 探测后端能力（实测 RustFS/MinIO 均支持）：

```python
s3.put_object(Bucket="dendro-test", Key="cond.txt", Body=b"v1")
s3.put_object(Bucket="dendro-test", Key="cond.txt", Body=b"v2", IfNoneMatch="*")
# → ClientError: PreconditionFailed   ✓ 支持
```

适配层映射：`object_store::PutMode::Create`（发送 `If-None-Match: *`），
服务端 412 → `Err(Exists)`。

## 3. 不确定写消解——payload 内嵌 putid

对象存储超时后"可能成功可能失败"。S3 SDK 层没有用户元数据可查，于是把
凭证写进 payload 本身（仅 manifest 需要消解）：

```
PUT manifest/…0008.json (含 writer_putid="8-3f2a") 超时 ──┐
                                                        │ 结果未知
GET manifest/…0008.json                                  │
  ├─ 200 且 writer_putid == "8-3f2a" ⇒ 其实成功 ⇒ Ok    ◀┘
  ├─ 200 但 putid 不同              ⇒ 别人写赢 ⇒ Exists（重试）
  └─ 404                            ⇒ 确实失败 ⇒ 重试
```

chunk/WAL 段不用消解：内容寻址或 fence 独占 ⇒ **同字节重试幂等**。

## 4. 慢网络实测——组提交的价值

`DENDRO_S3_RTT_MS=100` 注入每次请求 100ms±20% 延迟（模拟跨地域公网 OSS），
真实 PG 客户端逐行插入：

```
本地 RustFS（RTT≈0）        单行提交 p50 ≈ 21ms   （= wal_interval 20ms）
注入 100ms RTT              单行提交 p50 = 76ms   p90 82ms
```

解读：group 模式的延迟上限 ≈ max(组提交间隔, RTT)，p99≈p50——**尾延迟不放大**。
吞吐场景（多连接/批写）下组提交把 N 次 PUT 合成 1 次，这正是"慢网络友好"的
结构性来源。基准 JSON 见 `benches/results/commit_latency.json`。

## 5. 网络字节审计——慢/贵网络的记账

S3 适配器内置计数器（`S3Stats`），12k 行 lifecycle 实测：

```
gets=9   ranges=0   puts=152   conditional_puts=3
bytes_get=1,026      bytes_put=1,136,008
```

读侧仅 9 次远端请求——磁盘 LRU 缓存（512MiB 预算）把 prolly 节点、footer、
列存块的重复读全部本地化。写侧 152 次 PUT = WAL 段（组提交切分）+ 列存段 +
manifest 版本 + chunk 批。

## 6. 增量分段列存——慢/贵网络的正确姿势

对比两种 checkpoint 物化策略（1 亿行表、每 checkpoint 写 1 万行）：

```
全量重建（已废弃）：
  读整表（~GB 级远端读/缓存未命中）+ 编码 + PUT ~GB
增量分段（现状）：
  读 memtx overlay（纯内存）+ 编码增量 + PUT 增量段（KB~MB 级）
  段级 pk min/max 记入 TableEntry → 扫描时整段跳过
  段数≥8 或删除>1 万 → 一次性全量压缩（低频摊销）
```

扫描端的三层剪枝都发生在"发出网络请求"之前：

```
WHERE id BETWEEN 1e6 AND 2e6：
  TableEntry.col_segments[].pk_min/max  → 整段跳过
  footer.rgs[].cols[0].blocks[].min/max → 整行组跳过
  剩余块按列 range-GET（列裁剪：SELECT 少列 = 更少请求）
```

## 7. 杀进程恢复实录

```
① 写入：12k 行 + CHECKPOINT + 再插 1 行（仅 WAL）+ kill -9
② 重启：指向同一桶
   manifest/…N.json → main.head = commit → catalog 树 → 列存段列表
   WAL 段 HEAD 探测尾部 → 回放 seq > covered_seq 的 TXN
③ 验证：count = 12001（12k 列存 + 1 行 WAL 尾）
        分支合并结果完好（count=11 sum=145 同款用例）
```

存储桶里的全部家当（`aws s3 ls --recursive`）：39 个对象 =
manifest 版本链 + WAL 段 ×17 + prolly chunk + CBF 段。**桶即数据库**。

## 8. 诚实边界（v2）

- GC 清扫器：孤儿 chunk/旧 manifest/WAL 段会累积（标记 + min_age 已设计）
- 跨进程 fence：同分支单写者目前限单进程（epoch 字段已留）
- 冷热分层再编码（热块 RAW/DELTA → 冷块 ZSTD）
- 段内多块 range-GET 细分（v1 段内单块，1M 行 ≈ 8MB 上限）
