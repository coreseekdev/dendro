# 01 · 总览与一次提交的旅程

## 1. 分层鸟瞰

Dendro 是五层堆栈，**每层的输出是上一层的只读输入**——这是"数据只写"的结构性保证：

```
┌─────────────────────────────────────────────────────────────┐
│  L5  wire 层       pgwire(PG v3)   mywire(MySQL v10)        │  字节 ↔ SqlValue
├─────────────────────────────────────────────────────────────┤
│  L4  SQL 层        sqlparser(PG/MySql 方言) → exec          │  AST → 行
│      ┌────────────────┬───────────────────┐                  │
│      │ TP 行路径       │ AP 列式路径        │                  │
│      │ 点查下推/行扫    │ CBF 段扫描+剪枝    │                  │
│      └────────────────┴───────────────────┘                  │
├─────────────────────────────────────────────────────────────┤
│  L3  事务/版本                                                │
│   memtx(内存 OCC MVCC) ──checkpoint──▶ prolly 树(内容寻址)    │
│   64 分片版本链                          │                    │
├───────────────────────────────────────  │  ─────────────────┤
│  L2  日志层   WAL 段(组提交, 24B 帧头)    │  列存(CBF 段)      │
├─────────────────────────────────────────┴───────────────────┤
│  L1  对象存储   ObjStore trait                               │
│      Local │ Memory │ S3(object_store: RustFS/MinIO/OSS)     │
│      (+ CachedObjStore 读缓存 + ThrottledObjStore 延迟注入)    │
└─────────────────────────────────────────────────────────────┘
```

核心不变量：**L1 之上没有任何本地数据文件**。计算节点崩溃，换个进程指向同一个
存储根，L3 的恢复器能把一切重建（第 05、10 章）。

## 2. 存储根里有什么（全部家当）

```
{root}/                          ← 本地目录 或 S3 桶
├── manifest/00000000000000000001.json    元数据根（分支头、表目录指针）
├── objects/ab/abcdef....chunk            内容寻址 chunk：
│     0x01 前缀 = prolly 节点（行数据权威）
│     0x02 = commit 对象         0x03 = 表 schema
├── wal/{branch}/00000000000000000042.wal 提交日志段（一段=一个对象）
└── col/{table}/f3a9b2c81d4e.cbf          列存投影段（AP 加速，可重建）
```

注意 **没有** `data.db`、`ibd`、`WAL 文件句柄`——对象存储没有 append，
所以 WAL 的单位是"不可变段对象"（第 05 章）。

## 3. 一条 INSERT 的完整旅程

以 `INSERT INTO t VALUES (42, 'hi')` 为例（`t(id BIGINT PRIMARY KEY, v TEXT)`）：

```
 客户端                pgwire            SQL 层                    memtx                WAL/OSS
   │  Query("INSERT…")   │                  │                        │                     │
   ├────────────────────▶│ parse+exec       │                        │                     │
   │                     ├─────────────────▶│ translate→Stmt::Insert │                     │
   │                     │                  │ 1. resolve_table:      │                     │
   │                     │                  │   catalog 树查 schema   │                     │
   │                     │                  │ 2. encode_key([42])    │                     │
   │                     │                  │   = 10 80000000 0000002A        ┐            │
   │                     │                  │ 3. PK 冲突检查          │                     │
   │                     │                  │   (memtx.get + 树 lookup)│                    │
   │                     │                  │ 4. encode_row ─────────┤ 写集(会话本地)        │
   │                     │                  │    = 02 00 03 2A000000  │                    │
   │                     │                  │      05 01000000 68 69  │                    │
   │                     │                  │ 5. commit_tx ──────────▶│                    │
   │                     │                  │                        │ OCC 验证            │
   │                     │                  │                        │ install VerCell     │
   │                     │                  │                        │ pending 登记 ───────▶ 帧入组提交缓冲
   │                     │                  │                        │                     │
   │                     │                  │                        │   [组提交线程 50ms]   │
   │                     │                  │                        │                     │ PUT wal/…seg.wal
   │                     │                  │                        │ durable_seq+=1      │
   │◀────────────────────┤ CommandComplete("INSERT 0 1")             │                     │
```

五个关键点（后续章节逐个展开）：

1. **主键 → 保序字节键**（03 章）：`42i64` 编码为 `10 | 80 00 00 00 00 00 00 2A`——
   符号位翻转后大端，保证字节序=数值序。
2. **行 → 紧凑值编码**（03 章）：`02 00` 列数=2，`03` = Int64 tag…
3. **写集先落内存（memtx install），WAL 段后上传**，但**事务 ACK 等在段上传成功之后**
   （`Durability::Group` 默认档），所以"已确认 = 已在对象存储"。
4. **`pending` 登记是 checkpoint 的原料**：checkpoint 只把这个增量写成列存段，
   不扫全表（07 章）。
5. 全程**没有任何原地更新**——UPDATE = 旧版本 tombstone + 新版本追加。

## 4. 一条 SELECT 的路由

```
                 SELECT …
                     │ sqlparser 解析
                     ▼
            ┌─ WHERE 是 pk = 字面量？──是──▶ TP 直查：memtx.get → 树 lookup
            │        （6µs 级，零扫描）                      （p50 5.0µs）
            │
            ├─ 表有 col_segments 且 ≥1 万行？──是──▶ AP：CBF 段扫描
            │        （段级剪枝→行组剪枝→按需解码列块）      （200k 行聚合 53ms）
            │
            └─ 否则 ──▶ TP 行扫描：树迭代 ∪ memtx overlay（键序归并）
```

路由代码在 `dendro-core/src/sql/scan.rs` 的 `try_pk_pushdown` / `try_ap_scan`。
`SET dendro.force_engine` 的调试旋钮见 SPEC 07。

## 5. 进程视角

```
                    ┌────────────────────────── 进程 ──────────────────────────┐
 客户端连接 ────────▶│ 连接线程 ── WireSession ── Session{branch, txn, prepared} │
                    │                                                          │
                    │ WAL flush 线程（每分支 1 个）── 组提交/段上传/durable 通知    │
                    │ checkpoint 线程（1 个）── pending 超阈值时物化              │
                    └──────────────────────────────────────────────────────────┘
```

连接线程独占一个 `Session`（非线程共享）；引擎同步执行，阻塞点只有 WAL 等待
与对象存储 IO。线程模型见 SPEC 10 §7。
