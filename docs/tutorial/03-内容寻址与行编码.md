# 03 · 内容寻址与行编码

> 代码：`crates/dendro-core/src/format/hash.rs`、`format/row.rs`

## 1. 内容寻址：地址即校验，地址即身份

```
addr(chunk) = SHA-512( bytes )[ ..20 字节 ]        // 160 bit
文本形式     = base32( addr )                       // 32 字符，字母表 "0-9a-v"
```

三个为什么：

1. **为什么 SHA-512 不是 SHA-256？** 64 位机上 SHA-512 快约 50%
   （整数运算友好）。取前 20 字节——dolt 的实证选择：碰撞概率 2^-160 可忽略，
   而地址越短，树节点里能塞的扇出越大。
2. **为什么 base32("0-9a-v")？** 160 bit = 32×5bit 整除，零填充无浪费；
   字母表单调 ⇒ 编码后文本序 = 字节序（排序/前缀分桶直接用字符串比较）；
   比 hex 省 20% 体积。
3. **为什么首字节放类型标签？** 类型是内容的一部分——同一字节串
   不会被解释成两种类型，杜绝跨类型混淆攻击。

```
chunk 字节布局（全部类型通用）:
┌──────┬──────────────────────────────┐
│ 0xNN │ payload …                    │
└──────┴──────────────────────────────┘
  ▲ 类型标签：0x01 prolly 节点 / 0x02 commit / 0x03 schema
  addr = SHA-512( 完整字节含标签 )[..20]

例（Rust/Python 等价）：
  addr("hello" + 0x01) 的 base32 = j…（32 字符）
```

存储路径即地址的分桶（第 02 章）：`objects/j/jk3n….chunk`。

## 2. 保序键编码——字节序 = 逻辑序

prolly 树按 key 字节序排列。要让 `ORDER BY`、范围扫描、二分查找直接工作，
主键必须编码成**字节比较结果与逻辑比较完全一致**的字节串
（`encode_key`，`format/row.rs`）。

每列一个 tag 字节 + 载荷：

```
tag    类型        编码                                    字节数
────────────────────────────────────────────────────────────────
0x00   NULL       （无载荷）                                1
0x10   数值族      见下（int/float/date/timestamp 统一 8B）   1+8
0x20   字节串族    0x00→0x00 0xFF 转义 + 终止符 0x00 0x01    变长
0x30   BOOL       0x00=false / 0x01=true                    2
```

**数值的符号翻转技巧**（`i64` 保序的经典解法）：

```
raw = value XOR 0x8000000000000000        （翻转符号位）
编码 = raw 的 big-endian 8 字节

  i64::MIN  = 0x8000…0000  → XOR → 0x0000…0000  （最小 → 全 0）
  -1        = 0xFFFF…FFFF  → XOR → 0x7FFF…FFFF
   0        = 0x0000…0000  → XOR → 0x8000…0000
   1        = 0x0000…0001  → XOR → 0x8000…0001
  i64::MAX  = 0x7FFF…FFFF  → XOR → 0xFFFF…FFFF  （最大 → 全 F）
→ 无符号字节比较 == 有符号数值比较 ✓

float64（IEEE754 全序变换，f64_to_orderable）：
  正数：原 bits | 0x8000…    负数：原 bits 取反
  （同样达成"无符号比较 == 浮点比较"；-0.0/+0.0 归并）
```

**字节串的转义终止**：内容里的 `0x00` 写成 `0x00 0xFF`，串尾追加 `0x00 0x01`。
效果：`"ab" < "abc" < "ad"` 的前缀序在字节比较下严格成立。

### 2.1 完整示例：`id BIGINT = 42`

```
encode_key([Int64(42)])：

  tag 0x10                              ┌─ 42 = 0x2A
  ▼                                     ▼
  ┌────┬─────────────────────────────────┐
  │ 10 │ 80 00 00 00 00 00 00 2A         │   共 9 字节
  └────┴─────────────────────────────────┘
         42 ^ i64::MIN = 0x800000000000002A

多列键 (id=42, region="ab")：
  10 80..2A | 20 61 62 00 01            ← 0x20 tag + "ab"+终止符
```

解码是逐字段的逆过程（`decode_key`），按 schema 列型解释 tag 后的载荷。

## 3. 行值编码——WAL 与树共用的紧凑格式

行**不按列存**（列存在 CBF，07 章），而是 tag+载荷 的紧凑串
（`encode_row`）。WAL 的 TXN 帧与 prolly 叶节点的 value 用同一格式，
回放时零转换。

```
encode_row([Int64(42), Utf8("hi")])：

偏移  字节                                  含义
──────────────────────────────────────────────────────────
 0    02 00                                列数 = 2 (u16 LE)
 2    03                                    tag V_I64
 3    2A 00 00 00 00 00 00 00              42 (i64 LE)
11    05                                    tag V_UTF8
12    02 00 00 00                           长度 = 2 (u32 LE)
16    68 69                                "hi"
──────────────────────────────────────────────────────────
共 18 字节（对照：PG 行头至少 23 字节 + null 位图）
```

全部 tag：

| tag | 类型 | 载荷 |
|-----|------|------|
| 0 | NULL | 无 |
| 1 | Bool | 1 字节 |
| 2 | Int32 | 4B LE |
| 3 | Int64 | 8B LE |
| 4 | Float64 | 8B LE (IEEE754) |
| 5 | Utf8 | u32 LE 长度 + UTF-8 字节 |
| 6 | Bytes | u32 LE 长度 + 原始字节 |
| 7 | Date32 | 4B LE（自 1970-01-01 天数）|
| 8 | TimestampMs | 8B LE（自 Unix epoch 毫秒）|

**schema 演化的宽容性**：解码后按当前 schema `resize`——列多了补 NULL，
列少了截断。这就是 `ALTER TABLE ADD COLUMN` 不需要重写历史数据的原因
（旧行读到新列自然得到 NULL）。

## 4. 在整条链路里的位置

```
INSERT (42,'hi')
   │
   ├─ encode_key  ──▶ 10 80..2A ──────────▶ prolly 树的 key（04 章）
   │                                  ────▶ memtx 分片查找的 key（06 章）
   │                                  ────▶ WAL TXN 帧里的 op key（05 章）
   │
   └─ encode_row  ──▶ 02 00 03 2A.. 05 .. ─▶ prolly 叶 value（04 章）
                                     ────▶ WAL TXN 帧里的 op value（05 章）
                                     ────▶ checkpoint 时转 Arrow（07 章）
```

一个编码，三处消费；一个行编码，两处落盘。**格式即契约**。
