# 08 · 分支与合并

> 代码：`crates/dendro-core/src/sql/mod.rs::exec_branch_statement`、
> `engine.rs::merge_branches`、`versioned/merge.rs`
> 一个分支 = manifest 里的一条 ref；一个 commit = 一棵 catalog 树的根。

## 1. 两级树：catalog 树里挂着每张表的树

库级树（catalog map）的 key 是表名，value 是 `TableEntry` 的 JSON 字节；
表级树的 key 是行主键编码，value 是行编码（04 章）。

```
commit(main, h3) root
   │
   ▼ catalog map (prolly 树)
   ├─ "t"     → TableEntry { id:1, schema_addr:…, table_root: R_t,
   │                          row_count: 12000, col_segments:[S0,S1], … }
   └─ "other" → TableEntry { … }
                    │
                    ▼ table map (prolly 树, key=pk 编码)
                    ├─ [10 80..01] → row(id=1,…)
                    ├─ [10 80..02] → row(id=2,…)
                    └─ …

commit 对象（chunk 类型 0x02，紧凑二进制）：
  01 20B(root) 02 00 20B(p1) 20B(p2) 08B(height) 08B(ts) len+branch len+author len+msg
     └ parents 数量 u16；多父 = merge commit
```

分支之所以是 **O(1)**：`CREATE BRANCH` 只做两件事——
① 强制 checkpoint 源分支（把未物化写冻结成树）；② manifest 里写一条新 ref
指向同一个 commit。**零数据复制**，实测 225µs（1 万行库），与库大小无关。

## 2. 一次分支生命周期的时序

```
main ────C1────────C2────────C3──────────▶
                    │
                    │ CREATE BRANCH feat FROM main
                    │   = checkpoint(main) → C2
                    │   = manifest.refs.feat = {commit: C2, fork: (C2,…)}
                    ▼
feat ──────────────C2────C4────────▶        （C4 = feat 上的 checkpoint）
                    │ fork    │ 88888 写入
                    │
（feat 上的一切写入只动 feat 的 WAL/树/pending）
                    │
MERGE BRANCH feat INTO main：
  checkpoint(feat) → C4
  checkpoint(main) → C5
  base = common_ancestor(C4, C5)          按 height 收敛后同步上溯
  merge_map(base.root, C4.root, C5.root)  catalog 级（见 §3）
  → 新根 R*，commit C6{parents:[C5, C4]}（两父 = merge commit）
  main.head = C6                          manifest CAS
```

## 3. 三方合并：chunk 级 diff + 归并

```
merge_map(base_root, left_root, right_root)：

  if left == right        → NoOp            （内容寻址：同根即同状态）
  if base  == right       → FastForward(left)（right 无变更）
  if base  == left        → FastForward(right)

  patch_L = diff(base, left)      地址相同子树整棵跳过
  patch_R = diff(base, right)

  按 key 归并两路 patch：
    仅左改        → 采纳左
    仅右改        → 采纳右
    两边同改同值   → 采纳（收敛；注意：两树完全相同时内容寻址直接 NoOp）
    两边同改不同值 → CONFLICT(key, left_val, right_val)   ← 行级
    一删一改      → CONFLICT

  无冲突：把合并变更基于 left 树应用（chunker，结构共享）
        → 新根 + 双父 commit
```

三个实测行为（e2e 测试 `smoke_conflict_merge` / `smoke_branch_and_merge`）：

| 场景 | 结果 |
|------|------|
| 两分支各改不相交 100 行（1 万行表）| 合并成功，新建 chunk 3/172 |
| 两分支改同一 key 不同值 | MERGE 报 40001 + 冲突键清单 |
| 两分支改同一 key 同一值 | 收敛无冲突（若两树因此完全相同则 NoOp）|

## 4. 冲突的粒度与 Agent 实践

冲突检测在**两个粒度**同时生效：

1. catalog 级（表目录）：同名表两边都建 / 表目录演化不一致 → 表级冲突
2. 表内行级：`merge_map` 对双方都改动的表递归做行树三方合并

Agent 的标准作业流：

```
CREATE BRANCH agent42 FROM main;   -- 沙箱 0 成本
USE BRANCH agent42;
-- 随意 DDL/DML，甚至搞坏
-- 满意：
USE BRANCH main; MERGE BRANCH agent42 INTO main;
-- 冲突（40001）：
--   选项 A：重开分支 FROM main 重放改动
--   选项 B：DROP BRANCH agent42 丢弃
SELECT * FROM cambium.branches;            -- 分支列表
SELECT * FROM cambium.commit_log('main');  -- 提交历史（父链回溯）
```

## 5. checkpoint 与合并的协同（容易踩的坑）

merge 前会**双向强制 checkpoint**（src 和 dst），原因有二：

1. 合并算法作用于**树**（不可变、可 diff），memtx 里的增量必须先冻结
2. fork 语义需要"精确的父状态"——`CREATE BRANCH` 同理

这也是本章实现中修过的真 bug 的教训：checkpoint 必须绑定**正确的分支句柄**
（曾按表名找分支失败后静默回退 main，导致 feat 的增量段没物化——
测试用真 S3 + 全行数断言才暴露）。
